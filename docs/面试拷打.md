## 一、30 秒开场（⭐ 必须流畅）

### Q1. 一句话介绍 Query 项目，不能超过 30 秒。

**答案：** 这是一个 **Planner-centric 的 Agent Runtime Framework**——不是 RAG 应用，RAG 只是其中一个 Capability。核心流程：用户问题 → Planner LLM 动态生成任务 DAG（谁、做什么、依赖谁）→ 确定性执行运行时拓扑调度、按 Capability 分派、port_bindings 注入数据、Critic 触发重试 → SSE 实时透传到前端。Python（FastAPI）做规划与执行，Java（Spring Boot）做统一网关（鉴权 + SSE 透传 + 持久化），前端实时渲染 DAG 状态与 Agent Trace。

> **和 LangChain Agent 的区别：** LangChain Agent 是"单 Agent 串行调工具"（ReAct 范式：think→act→observe→think）；我这是"多 Agent 并行执行预规划 DAG"（Plan-and-Execute 范式）。LangChain 像全能员工自己决定用哪个工具；我这是项目经理拆任务排计划，多个专职员工并行干活。

### Q2. 为什么说它不是 RAG 项目？

**答案：** RAG 项目以"检索增强生成"为系统范式，检索是核心。这里检索只是 `retrieval` 这一个 Agent 的能力，系统的核心是 **LLM 动态规划任务图 + 确定性运行时执行**。数值求和问题直接 analysis 算，画图直接 code 跑，简单对话直接 chat——都不需要检索。RAG 是骨架上的肌肉，不是骨架本身。

> **RAG 扮演的角色：** 被封装在 MCP Server 进程里，暴露为 5 个工具（search_documents / read_all_rows / calculate_sum / calculate_rank / list_documents）。RetrievalAgent、AnalysisAgent、CodeAgent 消费这些工具，但不知道底层是向量库还是数据库还是 API。
>
> **去掉 RAG 系统还能跑吗？** 框架本身（Planner + DAG + Runtime + Critic）完全不依赖 RAG，ChatAgent 不受影响。但没 RAG 时，所有需要文档数据的任务（检索/分析/代码）都会产出空结果，系统退化成只能闲聊。RAG 是轮子不是发动机——换一套数据源，发动机照常工作。

## 二、Planner 与 DAG 生成（⭐⭐ 必须流畅）

### Q3. 从用户提问到 DAG 可执行，中间经过哪些步骤？六层校验各查什么？为什么这个顺序？

**答案：** LLM 输出 JSON → `_parse_task_graph` 解析成 TaskGraph（缺 agent 字段直接抛错）→ `_validate_task_graph` 过六层校验 → 通过后 `_post_process_plan` 三条规则兜底修正 → 返回可执行 plan。任一步失败都会 fallback 到 `_fallback_plan`。

六层校验顺序：
1. **validate_structure** — 空图 + 依赖存在性 + 循环检测
2. **validate_capabilities** — agent 注册 + 同层 output 冲突 warning + control_action 不能由 Planner 指定
3. **validate_controller_usage** — Controller 不能当 DAG 根节点
4. **validate_goal_capability** — goal_output 至少被某 agent 的 output_keys 包含
5. **validate_goal_reachability** — 按拓扑层传播 outputs，当前 DAG 能产出 goal_outputs
6. **validate_port_bindings** — 格式/上游存在/上游关系/output_key 存在/port 存在+类型兼容/必选端口齐全

> **为什么这个顺序：** 结构不合法（依赖坏了、有环）后面没法算，所以 1 不过就跳过 2-6。

### Q4. `_post_process_plan` 三条规则分别触发什么条件？规则 1 的关键词表有什么缺陷？

**答案：** 三条规则：
- **规则 1**：检测到数值问题（求和/排名关键词）但没有 analysis → 自动插入 analysis task 并接到 generator
- **规则 2**：纯数值问题 → 移除多余 extractor（extractor 90-160s 太慢）
- **规则 3**：非纯 chat DAG 没有 critic → 强制追加 critic

> **规则 2 不兜底会怎样：** "统计各品牌的花费金额占比"这种数值+文本混合问题，Planner 若误保留 extractor，会白白多跑 90-160s 的文本提取，而 answer 只需要计算结果。
>
> **关键词表缺陷：** 关键词表是手工枚举的（"花了多少钱/总共/合计/最贵/排名"），枚举之外的表达就漏。典型反例："给我看看这个季度的销售情况"——没有 sum/rank 关键词，LLM 漏了 analysis 也没人拦。完备性取决于开发者枚举能力，永远追不上语言表达空间。

### Q5. Planner 的 prompt 里注入了哪些上下文？加新 Agent Planner 会自动用它吗？

**答案：** `{available_executors}`（所有 Executor 的能力声明：输出 key + 工具）、`{available_controllers}`（Controller 及其 control_actions）、**可用文档列表**（`list_documents` 实时查）、**长期记忆**（memory_context）、**最近 5 轮对话历史**。

> **加新 Agent 会：** 会。能力是**注册表驱动**的——`create_default_registry` 里注册后，`format_executors_for_prompt()` 自动把新 Agent 的能力声明拼进 prompt，Planner 下次规划就会尝试用它。六层校验自动识别它、Runtime 自动能分派它。这就是热插拔。

### Q6. 一个 5 节点 DAG 大概调多少次 LLM？为什么不能合并？

**答案：** 典型 **9-13 次**：Planner 1 + Retrieval 2（搜索词生成 + 相关性判断）+ Extractor 按文档数×批次数（每 15 chunk 一批）+ Analysis 3-5（ReAct 每轮工具调用 1 次）+ Code 1-3（生成+执行+重试）+ Generator 1（流式）+ Critic 0-1（RuleValidator 通过才走 LLM）。

**三条硬理由为什么不能合并：**
1. **重试粒度** — Critic 返回 retry_target，只重跑子图。节点越细，失败重跑成本越低；合并=一次失败整段重跑=成本翻倍
2. **蒸馏漏斗（token 预算）** — 数据流逐级缩小：原始文档 → 知识+证据（精简）→ 计算结果（几十字）→ 答案。合并 Extractor+Generator = Generator 直接塞全文档 → 上下文爆炸 + 幻觉率上升
3. **可选节点** — Code 只在算数时出现、Analysis 只在数值题出现、Extractor 在纯数字题被删。动态 DAG 按需装配，合并=全都要跑

> **最不该并：** Generator 和 Critic——Critic 的价值恰是独立于"写答案的模型"之外的判断，自检有确认偏差（写错答案的模型自己看不出错）。

### Q7. 为什么 analysis 和 code 都能做计算，Planner 怎么区分？

**答案：** prompt 里写死了判断标准：**analysis = 固定工具调用（求和/排名），只能单一数值计算**；**code = 任意 Python 计算（分组/筛选/占比/统计）**。按问题模式映射：求和/最贵 → analysis；按X分组/占比/分布 → code + extractor。

> **混用的代价：** 拿 code 做简单求和是过度（引入代码执行风险 + 重）；拿 analysis 做分组统计是能力不足（analysis 工具只支持 sum/rank）。prompt 里用大段篇幅写"三个 Agent 的区别"就是怕 Planner 混用。

### Q8. 一条问题两次执行，DAG 会一样吗？测试怎么做？

**答案：** 大概率相似但不保证相同——Planner 是 LLM，temperature 非零时同一问题可能产出不同 agent 组合或不同 port_bindings。这就是动态 DAG 让单测穷举变难的根因（同问题两次执行可能不同 DAG），也是六层校验必须存在的原因——每次的 DAG 都是"新的"，必须每次都验证它可执行。

> **测试策略：** LLM 输出打桩/录制回放（把一次真实 DAG 录下来，测试时回放，不走 LLM）+ 依赖真实 LLM 的集成测试放慢速 CI。当前依赖真实 LLM 是已知缺点（CI 成本高不稳定）。

## 三、DAG 执行引擎（⭐⭐ 必须流畅）

### Q9. 执行引擎的 while 循环每一轮做了什么？return_exceptions=True 为什么必须用？

**答案：** `_execute_plan` 用一个外层 `for _ in range(max_iterations=10)` 循环 + 内层拓扑调度：每轮计算"依赖全部完成"的 ready 任务，用 `asyncio.gather` 并行执行，失败的任务把下游标记 `SKIPPED`。内层 pending 清空后检查还有没有 Controller 触发的 RETRYING 任务，有就再来一轮，直到没有可执行任务或超迭代上限。

> **return_exceptions=True 必须用：** 否则第一个 task 抛异常会立刻取消整个 gather，把"一个分支失败"放大成"整批都跑不完"。设了之后各 task 照常执行完，异常在 zip(ready, results) 里逐个判断。
>
> **并行为什么安全：** ① 无依赖的任务才同时 ready（DAG 约束天然无写冲突）；② set_output 按 contextvar `_task_id_var` 隔离，每个 asyncio Task 有独立 Context 副本；③ outputs 写操作有 `_lock` 保护。

### Q10. 一个 task 失败后，下游级联跳过怎么实现？为什么跳过而不是终止？

**答案：** task 抛异常 → 状态置 `FAILED` → **所有下游（BFS 找 get_descendants）标记 `SKIPPED`**，避免以空输入继续执行产生"自信但错误"的回答。

> **为什么跳过而不是终止：** 跳过一个分支不影响其他并行分支继续（比如 extractor 失败，analysis→generator 分支还能产出数值答案）。正确性由两层兜底：Critic 可能发现内容问题触发重试，goal_outputs 校验保证"该产出的没产出会报错"。比一刀切终止更优雅，但确实允许"半成品"流过（这是缺点边界）。

### Q11. Controller 触发 retry 后，invalidate_subgraph 具体标记哪些 task？

**答案：** Critic 返回 `ControlAction(retry, target_task_id)` → RetryHandler 按 **agent 名**匹配所有 task，调 `plan.invalidate_subgraph(task_ids)` 把目标及其**所有下游**标为 `RETRYING` → 外层 for 循环检测到有 RETRYING 任务继续下一轮，拓扑调度重新执行它们。不需要真的回溯，把受影响子图状态重置重新调度即可。

> **retry_target="retrieval" 时：** retrieval 的所有下游（extractor/generator/critic）都会被重跑——因为 invalidate_subgraph 包含所有后代。但并行分支（如果 analysis 不依赖 retrieval 的话）不受影响。

### Q12. 同一个 output key 被多个 task 写，怎么合并？merge_policy 优先级？

**答案：** 存储结构 `outputs: key → {task_id: AgentOutput}`，多 task 写同一 key 时**不覆盖、共存**。走 port_bindings 读 = 精确拿指定 task 的；未限定读（`get_output(key)`）按 merge_policy 合并：
- **replace** — 取最后一个（critic 的 critique 每次重新覆盖）
- **append** — 多证据源拼接（evidence_list 来自多个 extractor 分支）
- **dedup** — 拼接但按 key 去重（DocumentBundle 按 `(source, content[:200])` 去重）

policy 优先级：显式传参 > `context.merge_policies[key]` > 默认 append。

### Q13. 执行完全成功的标准是什么？goal_outputs 校验失败会怎样？

**答案：** 三件套：① 所有 task 走完 pending 清空（或 Controller 不再触发 retry）；② 没有未处理的异常；③ `context.has_output(o)` 覆盖所有 goal_outputs。③ 不满足会抛 `WorkflowExecutionError`，前端收到 runtime_error——防止"执行成功但没产出 answer"的静默失败。

> **answer 是空字符串会怎样：** goal_outputs 校验只查 `has_output`（key 存不存在），不查值。空字符串也是"有输出"，校验会过。但 RuleValidator 会拦——`len(answer.strip()) < 3` → 判定"回答过短或为空" → 触发重试。所以空 answer 不会静默通过，是两层防线。

## 四、Agent 体系与数据契约（⭐⭐⭐ 深挖区）

### Q14. AgentContext.outputs 的存储结构是什么？set_output 时 task_id 从哪来？

**答案：** `outputs: dict[key] → {task_id: AgentOutput}`——一个 key 对应一个 dict，dict 的键是 task_id，值包一层 AgentOutput(value/producer/version/timestamp)。`set_output` 时 `task_id = _task_id_var.get()`（每个 task 跑前 `_task_id_var.set(task.id)`）。**并行分支各写各桶不互相覆盖。**

> **读取怎么区分是哪个 task 写的：** 精确读 `get_output_entry(key, task_id=source_task_id)` 命中指定 task 的输出；聚合读 `get_output(key)` 按 merge_policy 合并所有 task 的值。两种读取并存。

### Q15. port_bindings 的值 `"task1.document_bundle"` 执行时怎么解析？

**答案：** `_run_plan_task` 开头遍历 task.port_bindings：按 `.` 拆成 source_task_id + output_key → `context.get_output_entry(output_key, task_id=source_task_id)` 精确取指定上游的输出 → value 非 None 就放进 `upstream_kwargs[port_name]` → `agent.execute(context, **upstream_kwargs)`。**没有 BFS 回退、没有"就近找"，数据通道唯一且显式。**

> **上游没完成会怎样：** 理论不可能——拓扑排序保证上游先 COMPLETED、数据必然已写入（三层前置保证：拓扑序 + 六层校验引用合法 + auto_wire 补缺失）。如果强行假设，`get_output_entry` 会拿到 None → 该端口不注入 → Agent 内部 `kwargs.get()` 拿到 None → 可能出现空输入回答。

### Q16. _type_matches 的类型匹配怎么做？支持哪些模式？

**答案：** `_type_matches(declared_type, expected_type)` 支持 4 种模式：
1. **精确匹配** — `declared is expected`（`DocumentBundle == DocumentBundle`）
2. **Union/Optional** — expected 是 `X | None`，declared 是 X 则匹配
3. **参数化泛型** — `list[KnowledgeObject] == list[KnowledgeObject]`（比较 origin + args）
4. **泛型→bare** — `list[dict]` 满足 `list`（declared 有 origin，expected 无 origin）

> **`DocumentBundle` 和 `list[DocumentChunk]` 能匹配吗？不能。** DocumentBundle 是 dataclass 不是泛型，走完四条规则全 False。设计正确——DocumentBundle 是包装类，有语义，不能直接当 list 用。
>
> **`AnalysisResult | None` 和 `AnalysisResult`？看方向。** 单向性：declared=`AnalysisResult` expected=`AnalysisResult | None` → 匹配（expected 是 Union）；反过来 declared=`AnalysisResult | None` expected=`AnalysisResult` → 不匹配（expected 不是 Union）。当前代码 AnalysisAgent 产 `AnalysisResult`，Generator 要 `AnalysisResult | None`，所以 auto_wire 能自动绑定。**设计原则：接收方声明可选（Union）能兜住，产出方声明可选会让 auto_wire 失效。**

### Q17. contextvar _task_id_var 在并行分支里怎么隔离？

**答案：** contextvar 是 asyncio 的 Task 本地变量——每个 asyncio Task 有独立的 Context 副本，`set()` 只影响当前 Task。项目用它隔离三样东西：`_task_id_var`（当前 task_id，set_output 时按它归属）、`_search_ctx_source_var`（检索源 task_id）、`_task_objective_var`（各分支自己的 objective）。

> **不用 contextvar 用全局变量会怎样：** 并行分支会互相覆盖。比如 task2 和 task3 并行，task2 执行中把 `task_id` 全局变量设成 "task2"，task3 的 set_output 读到的是 "task2" 而不是自己的 "task3"——两个分支的输出都归到 task2 桶里，task3 下游拿不到数据。**没有 contextvar，共享字段被任意分支覆盖，数据流错乱。**

### Q18. 加一个"文档翻译"Agent，要改哪些文件？

**答案：** 只需：① 新建类实现 BaseAgent.run + 声明 capability（inputs/outputs/tools/merge_policy）② 在 `create_default_registry` 里注册。**不用改 Orchestrator、不用改 prompt 里硬编码的 agent 清单、不用改任何分支逻辑。** Planner prompt 自动带上它、六层校验自动识别它、Runtime 自动能分派它。

> **auto_wire 自动绑定吗？** 会——只要新 Agent 的某个输入端口类型和上游某个输出类型兼容，`_auto_wire_port_bindings` 扫描上游 task 输出，找类型兼容的第一个输出建绑定。比如翻译 Agent 声明 `document_bundle: DocumentBundle` 输入，retrieval 产出 `document_bundle: DocumentBundle`，就自动绑上。

### Q19. required_inputs 为空和不为空有什么区别？

**答案：**
- **校验层**（validate_port_bindings Step B）：required 端口**必须**有 port_bindings，没有就报错 → 整张 DAG fallback；非 required 没有 port_bindings 不报错，静默跳过
- **执行层**（_run_plan_task）：没有 port_bindings 的端口不进 upstream_kwargs → Agent 内部 `kwargs.get("xxx")` 拿到 None

> **Generator 为什么是空（set()）？** 因为它要适配多种 DAG 结构：纯数值问题只有 analysis_result，文档对比才有 knowledge_objects/evidence_list，对比+画图才有 code_result。如果把 knowledge/evidence 设为 required，纯数值问题的 DAG 校验就过不了。设为空，Generator 内部自己处理"有什么用什么"（`kwargs.get(...) or []`）。
>
> **一句话：required_inputs 是"没有这个数据我活不了"的声明。Generator 什么场景都能跑（只是质量不同）所以全部可选；Extractor 没有文档什么都提不出来，所以 knowledge_document 是 required。**

## 五、Critic 与质量保障（⭐⭐⭐ 深挖区）

### Q20. RuleValidator 的 `_value_present_in_answer` 怎么判断数值体现？

**答案：** 对 analysis.calculations 里每个 result，检查计算结果是否在回答里体现，**支持 95/95.0/95%/0.95 跨格式互转**（normalize 后比对）。

> **result=95，回答写"百分之九十五"能拦住吗？** 不能。RuleValidator 只做字符串/数值层面的确定性检查（95/95.0/95%/0.95），"百分之九十五"是中文数字表达，不在 normalize 范围内。这是已知边界——确定性规则只能覆盖可枚举的格式，语义判断交给 LLM Critic。

### Q21. slim_evaluate prompt 写了哪些标准？为什么说"有覆盖标准但软"？

**答案：** 三条标准：**准确性**（回答是否与证据矛盾）、**完整性**（是否回答了用户的问题）、**逻辑一致性**（回答是否自洽）。输出 JSON：`{"score": 8, "problems": [], "need_retry": false, "retry_target": "all"}`。

> **"软"在三处：** ① 主观判断——完整性只是三条标准之一，交给 LLM 一眼扫，无结构化核对；② 宽容倾向——prompt 两处软化（"不要因 evidence 缺细节判编造""evidence 只是摘要 generator 可能提取更多"），等于教它倾向放行；③ 非结构化——判定"没覆盖"也不定位到具体缺失点。
>
> **第二轮不复核第一轮：** 第二轮用同一 prompt 重新评估，不拿第一轮的 problems 逐条验证"是否已修复"——"重新评估"而非"收敛式修复"。解法方向：第一轮输出结构化 requirement 清单，第二轮逐条核对（对应 Q92 的三步升级方案）。

### Q22. retry_target="generator" 和 "all" 分别触发什么？

**答案：** `"generator"`（表达问题，只重生成）；`"retrieval"`（检索有问题，重跑检索）；`"all"`（严重问题全部重来）。RuleValidator 拦截时固定 `retry_target="generator"`。RetryHandler 把 target 当 **agent 名**在 plan 里匹配（不是 task ID），匹配到后调 `invalidate_subgraph` 把该 agent 的 task + 所有下游标 RETRYING。

> **"all" 重跑哪些：** 匹配 agent 名为目标的所有 task，invalidate 目标 + 所有后代。所以 "all" 实际是重跑匹配到的那个 agent 及其下游，不是字面上的"所有 task"。具体范围取决于 plan 里 agent 名匹配到了谁。

### Q23. 六层校验和 Critic 的分工？六层全过但答案错误，Critic 能修吗？

**答案：** 六层校验保**可执行性**（DAG 结构/数据流/类型合法，前置一次性）；Critic 保**内容质量**（答案准确/完整/自洽，结果级）。一个管"跑不跑得起来"，一个管"答得好不好"。两者都不管"任务分解是否答对题"——那是 Planner 能力决定的天花板。

> **真实场景：** "对比三份实验报告差异" → LLM 规划 `retrieval → generator`（漏 extractor）。六层校验全通过（类型匹配/数据流合法/goal 可达），但没有规则说"对比类必须用 extractor"，结果 generator 没有结构化知识可引用，产出不引用证据的泛泛回答。
>
> **Critic 能修吗？不能。** Critic 审的是"答案 vs 证据"的一致性，它的重试范围是 retrieval/generator/all——都发生在同一张 DAG 里。DAG 本身漏了 extractor，重跑 generator 也只是用同一套不完整的输入再答一次。**Critic 能修执行质量，修不了规划质量。** 解法是执行中 Replanning + 结果级自动评估。

### Q24. Critic 的 LLM 调用失败会怎样？失败安全偏向重试有什么问题？

**答案：** catch 异常后构造 `CriticResult(score=0, need_retry=True, retry_target="all", problems=["Critic 调用失败: ..."])`——**宁可重跑全部也不要放过**。解析失败（LLM 输出非合法 JSON）同理返回 need_retry=True。失败安全偏向重试。

> **潜在问题：** 重试 = 重调 LLM = 成本翻倍。如果 Critic 长期故障，会触发多轮无意义的重跑烧 token。**不希望它重试的场景：** 答案其实很好但 Critic 服务临时抖动，无脑重跑整条链路（可能重跑 retrieval 2-3 次）。解法方向：区分"服务故障"和"内容不合格"——前者应短路重试或跳过 Critic，后者才触发子图重跑。

## 六、数据传输演进（⭐⭐⭐ 加分题）

### Q25. 从 hardcoded fields 到 port_bindings，经历了哪几个阶段？

**答案：** 五阶段演进：
1. **hardcoded fields** — AgentContext 写死 evidence/analysis/answer 字段，set_evidence()/set_answer() 固定 setter。加新数据要改 dataclass + 加 setter，耦合重
2. **set_output/get_output** — 泛型 key-value，key 由各 Agent 约定。问题：上下游必须**约定同一个 key 名**，否则对不上
3. **input_mapping + BFS** — 自动搜索上游找数据。问题：BFS 就近找可能拿错上游的数据，无精确性
4. **port_bindings** — 声明式数据通道，`"task1.document_bundle"` 全限定引用，类型匹配校验。解决命名解耦（上游输出名和下游输入名可以不同）+ Agent 互不知道彼此
5. **contextvars** — 并行分支隔离（_task_id_var / _task_objective_var / _search_ctx_source_var），解决并行写冲突

> **演进驱动力：** 解耦、命名独立、并行安全。当前实际很多数据绕过 port_bindings（_task_objective_var 传问题、MCP session 共享数据、required_inputs 校验），port_bindings 是架构预留，当前 DAG 模式用得少但架构上是对的。

### Q26. SearchContext 和 AgentContext 的区别？

**答案：** 名字像但一个在 Python 主进程、一个在 MCP 子进程，作用域完全不同。
- **AgentContext**：一个 run（一次问答）一个，跨整个 DAG。管 Agent 与 Agent 之间的数据交换（question/plan/evidence/analysis/answer + SSE 的 run_id/event_bus + traces）
- **SearchContext**：一个 MCP session 内、单个 Agent 的工具调用循环里用，管工具与工具之间的状态接力（last_search_chunks/filtered/all_chunks/sources、search_count、agg_count）。让 calculate_sum/rank/read_all_rows 复用上次 search_documents 搜到的数据

> **改成 per-user 复用会怎样：** SearchContext 存在 MCP server 的 per-session 状态里（session.search_ctx 共享 + session.search_contexts[task_id] 隔离）。若 MCP session 改成 per-user 复用，SearchContext 就跨 run 残留——上一个 run 的检索状态污染下一个 run，search_count/agg_count 计数串台，甚至拿到别的 run 的文档数据。这违反"每 run 新建 + 用完即焚"的无状态纪律。

## 七、SSE 与无状态架构（⭐⭐ 进阶）

### Q27. Python "无状态"具体指什么？哪些是进程内瞬态？

**答案：** 指 Python 进程**不持有跨请求存活的状态**：MCP session 每 run 新建用完即焚、AgentMemory 每 run 从 Java 重建、RuntimeEventBus 事件 run 结束即清理。状态全部在外部存储（Redis/MySQL/MinIO/Java 内存），进程可以被杀/重启/复制而不丢数据。

> **逐个判断：**
> - **AgentMemory** — 不是持久化（进程内内存），但可从 Java `rebuild_from_history` 幂等重建 → 算无状态
> - **RuntimeEventBus** — 进程内瞬态（per-run 事件流，run 结束 cleanup），不承载跨 run 业务状态 → 不算有状态，但它是多实例问题所在
> - **MCP session** — 每 run 新建 + finally cleanup → 不算有状态

### Q28. 双端心跳怎么实现？为什么两端都要发？

**答案：** Java 侧 `heartbeatScheduler` 每 15s 发一个 SseEmitter comment（`: ping`）；Python 侧 `stream_runtime` 的 queue 15s 无事件也发 `: ping\n\n`。注释行不产生事件但维持 TCP/代理连接存活。

> **为什么两端都要：** 两端各自保活自己那一段链路。Java 发给自己前端的客户端（SseEmitter），Python 发给自己代理方（Java 转发器）。只一端发，另一端到代理之间的连接还是会被 nginx 空闲超时掐断。
>
> **15s 怎么定的：** 经验值：大于 nginx 常见空闲超时（60s）但又不至于太频繁刷流量。两端一致 15s，在超时窗口内必然有事件。

### Q29. callback 鉴权容错完整链路？Java 校验失败前端看到什么？

**答案：** Python 携带 `X-Callback-Token` 调用 Java `/qa/callback`，Java 比对配置里的 `ai-service.callback-token`，**校验失败返回 403** → `_callback_java` 返回 False → `_run_and_emit` 抛 `RuntimeError("callback 持久化失败")` → emit `RUNTIME_ERROR` → 前端收到错误。**持久化失败 = 整个 run 报错，不静默成功。**

> **callback 失败会重试吗？当前不会。** 单次 HTTP POST，失败就丢。不重试的后果：对话结果没写进 MySQL，用户刷新历史看不到这条问答；但 SSE 实时回答不受影响（答案已通过事件流推给前端）。解法方向：指数退避重试 + 死信队列。

### Q30. 用户手动停止的完整链路？

**答案：** 前端点「停止」→ `POST /qa/stop/{runId}` → Java 转发 Python → Python **先发 `RUNTIME_CANCELLED`**（SSE 流干净结束）再 `task.cancel()`。取消的 run 不持久化、不更新记忆，无半成品记录。

> **停止后 run 会出现在历史里吗？不会。** 取消后不 emit completed/error，半成品不持久化、不更新记忆。历史里看不到，无法从停止点恢复——这是"手动停止不持久化"缺点的直接体现。用户又问新问题不受影响（新 run 独立）。

## 八、MCP 与安全（⭐⭐ 进阶）

### Q31. MCP Server 独立进程怎么通信？挂了会怎样？

**答案：** **stdio 通道**。主进程 MCPClient（stdio client → ClientSession → initialize）通过标准输入输出与 MCPServer 进程通信，call_tool 把工具名+参数发过去、收 result.content[0].text。进程间只走文本协议，内存完全隔离。

> **每 run 新建 session？是的。** `run()` 里 `mcp_client.create_session()` 生成 uuid4 新 session，finally 里 cleanup。每 run 新建 + 用完即焚是无状态三条纪律之一。
>
> **改成 per-user 复用会怎样：** SearchContext 跨 run 残留（见 Q26），MCP session 变成多实例共享状态，无状态边界被打破。
>
> **MCP 进程挂了会怎样：** 工具调用抛异常 → Agent run 抛异常 → task FAILED → 下游 SKIPPED → 走失败链路。不会崩主进程（stdio 通信失败只是调用异常）——隔离的意义正在于此。

### Q32. CodeAgent 代码执行有哪些安全约束？白名单绕过风险？

**答案：** 四道闸：① **独立子进程**执行（隔离崩溃）；② **模块白名单**——允许 json/math/datetime/collections/itertools/functools/operator/statistics/re/decimal/fractions/copy，**禁用 os/subprocess/socket/shutil**；③ **512MB 内存 + 60s 超时**硬限制；④ 运行环境移除 builtins 里的 compile/exec/eval。

> **`__builtins__` 间接调 os.system 能拦住吗？** 有可能拦不住。纯白名单挡得住"直接 import os"，挡不住 import 技巧（通过 `__builtins__`、`__import__` 间接、或从白名单模块 access 危险属性）。这是已知边界（缺点 7）。
>
> **怎么彻底防：** 网络/文件系统白名单 + seccomp（限制系统调用）或直接容器化（只读根文件系统 + 无网络 namespace）。当前是"进程级沙箱"够 demo、不够生产。

### Q33. search_documents 完整搜索流程？各步解决什么问题？

**答案：** 五步：
1. **embedding 相似度搜索**（k=60 候选）— 语义召回
2. **阈值过滤**（余弦距离 < 0.92 才算相关）— 挡无关内容
3. **关键词搜索补充**（embedding 召回不足时 jieba 关键词精确匹配补）— 补精确项（专有名词/数值/表格列名 embed 不到一起）
4. **合并 + 多样性选取**（轮询各文档保证覆盖）— 防止一篇文章占满结果，对比类问题的保命设计
5. **文件名回退**（文件名 bigram/单字重叠匹配）— 处理"问题没语义但指名道姓要某文档"

> **0.92 阈值：** 太高（0.95）召回少，相关内容漏掉；太低（0.80）召回多但噪音大。0.92 是实测调出来的平衡点。

## 九、架构缺点深挖（⭐⭐⭐ 必考）

### Q34. 项目最大缺点？讲 3 个，每个跟解法。

**答案：** 我讲 3 个最有代表性的：
1. **无状态 Python vs 进程内事件总线** — RuntimeEventBus 是进程内 pub-sub，多实例下 SSE 消费者必须连到执行该 run 的实例。解法：Redis Streams 事件总线（Java 直接订阅）或 Java run 级 sticky 路由
2. **六层校验是结构校验不是语义校验** — 保证 DAG 可执行，保证不了"任务分解正确"，后者由 Planner 能力决定（系统上限）。解法：执行中 Replanning + 结果级自动评估
3. **Critic 无量化评估** — 无 golden set，准确率/漏报率不可量化、不可回归。解法：沉淀 golden set 做离线评测

> **为什么"结构校验 ≠ 语义校验"最深：** 它触及系统**上限**而非 bug——唯一把"用户问题"翻译成"任务"的是 Planner LLM，六层校验只保证"翻译出来的 DAG 能跑"，手写规则只补"已知场景的缺失"。Planner 能力 = 任务分解的天花板，校验永远追不上 LLM 的错误空间。它和 Critic 的关系：六层校验和 Critic 都发生在"同一张 DAG 里"，DAG 分解错了，两者都修不了。

### Q35. 多实例部署时，哪些地方会出问题？排查清单？

**答案：** 排查清单（凡是"进程内存里的 run 级状态"和"嵌入式单写者资源"都要审查）：
- **RuntimeEventBus**（run→事件）— 受影响，必须外置（Redis Streams）
- **_active_tasks**（run→asyncio.Task，Python 内存）— 受影响
- **Java SseEmitter 登记表** — 受影响（Java 多实例时）
- **Chroma 向量库** — 受影响，嵌入式单写者，多 worker = 多 MCP server 子进程并发写同一目录；compact() 非原子，崩溃丢全库（解法：换 Redis Stack / pgvector）
- **AgentMemory 进程内缓存** — 每 run 从 Java 重建，OK
- **MCP session** — 每 run 新建，OK

> **"两个浏览器 ≠ 多实例"：** 浏览器是客户端，实例是服务端进程。两浏览器连同一进程没问题；多实例 = 多个进程，负载均衡把 SSE 请求分到非执行实例就收不到事件。单实例不暴露，多实例才暴露。
> **排查口诀：** 凡是"只存在于进程内存、不落盘、不走网络"的状态，多实例都会出问题；凡是"由独立服务持有、通过网络访问"的资源（Redis / MySQL / RabbitMQ），多实例天然安全。Chroma 是例外——它嵌入在 MCP Server 子进程里，本质是"进程内资源"但被多进程共享，属于隐性单点。

### Q36. Redis 事件总线该用 pub/sub 还是 Streams？为什么？

**答案：** 用 **Streams 不用 pub/sub**。pub/sub 发完即焚，迟到订阅者丢历史；Streams 可 `XREAD` 从 0 读历史，**复刻进程内总线的"迟到订阅不丢事件"**（RuntimeEventBus 有 history 回放）。推荐 Java 直接订阅 Redis，否则又回到"Java 该连哪个 Python"的 circular 问题。

> **写 Redis 还算无状态吗？** 更无状态。无状态 = 状态在外部存储不在进程内存。事件从进程内存搬 Redis = 事件不跟进程共存亡 = 更无状态。Redis 是共享基础设施，所有实例都能读写。"写 Redis 变成有状态"是把存储介质误当状态本身。

### Q37. 正在跑的 run 崩溃了能续命吗？checkpoint 难点？

**答案：** 当前不能（已知边界）。要做 = **checkpoint**：每个节点/agent 完成时把执行状态（plan+completed+outputs+in_flight）序列化到 Redis，新实例读 checkpoint 重建 AgentContext 从断点续跑。粒度 = 每节点完成时，非每 token。**当前不做**：分钟级 run + 低崩溃率，收益不成比例。

> **难点：** ① **幂等**——已完成节点不能重跑（LLM 调用贵）；② **in-flight 节点**用"至少一次"重跑（可能重复调用，要接受）；③ **MCP session 也是内存态**要一并 checkpoint；④ **前端事件回放衔接**——续跑后事件流要能接上。三条纪律（每 run 新建）与 checkpoint 冲突，需要专门设计。

### Q38. 三层递进怎么讲？

**答案：** ① **SSE 串流** → Redis 事件总线解决；② **新 run 接管** → 无状态设计解决（从 Java 重建）；③ **正在跑的 run 续命** → 需要 checkpoint，当前不做。**"无状态边界在第二层、不含第三层"就是这个含义。**

## 十、LangGraph 对比（⭐⭐⭐ 必考）

### Q39. 为什么不用 LangGraph？一句话 + 三个理由。

**答案：** 一句话：**图的来源不同 + 运行时职责不同 + Python 无状态架构**，抽象层不匹配。
1. **图是"数据"还是"代码"** — LangGraph 的图是开发者写死的 Python 代码（静态拓扑）；我的 DAG 是 LLM 每轮动态生成的（Planner → TaskGraph），运行时还要过六层校验 + 规则兜底。把动态图翻译成 LangGraph 静态定义 = 隔层翻译、绕过自研校验
2. **DAG vs 状态机** — Planner 产出 DAG，拓扑排序 + asyncio.gather 一次扁平执行；重试是 Controller 子图重执行（外层 max_iterations 循环），非图内环。LangGraph 的核心价值（cycles/time-travel/human-in-the-loop）项目当前都不需要
3. **Python 无状态 + Java 网关** — 持久化/鉴权全在 Java，Python 只做进程内瞬态。LangGraph 的 checkpointer 强绑定 Python 进程内状态，破坏"崩溃从 Java 重建"的无状态设计

> **"代码即图"和"数据即图"：** LangGraph 是开发者手写节点/边的 Python 代码；项目是 LLM 输出的 JSON 数据（每轮生成、过六层校验）。一个代码即图，一个数据即图。

### Q40. 项目的重试算"图内环"吗？和 LangGraph cycles 区别？

**答案：** **不算。** 重试是 Controller 触发 `invalidate_subgraph` 把子图标记 RETRYING，外层 `for _ in range(max_iterations)` 循环重新调度——是"控制流循环"不是"图结构上的环"。图本身保持 DAG。LangGraph 的 cycles 是在图结构里画环，两者机制不同。

### Q41. LangGraph 全局 State 和你的 AgentContext 差在哪？

**答案：** LangGraph 全局共享 State（所有节点读写同一个 dict）；项目是 **task 级隔离**：`AgentContext.outputs` 按 task_id 分桶（`key → {task_id: AgentOutput}`），并行分支靠 contextvar 隔离写冲突，按 merge_policy 合并。**共享内存态难以表达 task 级隔离上下文**——这是自研数据契约的动机之一。

### Q42. 什么情况下你会改用 LangGraph？

**答案：** 标准 agent 工作流（ReAct/多 agent supervisor）、跨会话持久化（checkpointer）、图内循环的 Replanning、human-in-the-loop。README「后续优化」里的"动态 Replanning"若需图内环，LangGraph 是候选技术路线。**当前项目落在它弱项上，选型才合理。**

> **纠正误区：** LangGraph 完全能做多 Agent（Supervisor/Handoff/Swarm 是官方模式）。不用它 ≠ 它做不了，而是抽象层（动态拓扑 + Python 无状态 + 自研数据契约）不匹配。**选型是"是否需要"，不是"能不能"。**

### Q43. 你项目里还保留 LangChain，它负责什么？边界在哪？

**答案：** LangChain（兄弟库）用于 **RAG/LLM 集成**（ChatOpenAI 客户端、LangChain Agent 包装 MCP 工具），编排层自研。**边界清晰：LangChain 管"和模型/工具打交道的胶水"，自研管"多 Agent 任务编排"**。不是排斥生态，是把生态用在合适层。

## 十一、通用技术题（⭐ 基础）

### Q44. hm-dianping 点赞为什么用 Redis Set？数据库 count 有什么问题？

**答案：** Set 天然去重 + O(1) 判断是否已点赞 + O(1) 获取点赞用户列表。数据库 count + distinct 在高并发下性能差，且每次都查库压力大。Redis Set 还能配合 **sortset** 做点赞排行榜。**Redis 做缓存，异步落库到 MySQL**，兼顾性能和持久化。

### Q45. 缓存穿透/击穿/雪崩？怎么解决？

**答案：**
- **穿透**（查不存在的 key，每次都打到 DB）→ 布隆过滤器 + 缓存空值（带短 TTL）
- **击穿**（热点 key 过期瞬间大量请求打 DB）→ 互斥锁（Redisson 分布式锁），只有一个线程去重建缓存
- **雪崩**（大量 key 同一时间过期）→ 过期时间加随机值 + 多级缓存

### Q46. JWT 登录完整流程？Token 放哪？每次请求怎么校验？

**答案：** 登录成功后服务端生成 JWT（header + payload + signature），返回给前端存 localStorage/header。前端每次请求带 `Authorization: Bearer <token>`。后端拦截器拦截请求 → 解析 token → 验证签名 + 过期时间 → 通过则放行，失败则返回 401。**无状态认证**（服务端不存 session），适合分布式。

## 十二、场景设计（⭐⭐⭐ 开放题）

### Q47. "把三份实验报告翻译成英文"会设计什么 DAG？

**答案：** 现有 DAG：`retrieval → extractor → generator` 能检索 + 抽取，但 **translation 不是现有 7 个 Agent 的能力**。方案：
- **新增 TranslationAgent**：声明 `inputs: {knowledge_document: DocumentBundle}`, `outputs: {translated_document: DocumentBundle}`，在 create_default_registry 注册
- **DAG**：`retrieval → translation → generator`（跳过 extractor，翻译不需要结构化抽取）
- 不需要改 Orchestrator/Planner prompt——注册即用，Planner 自动学会用它
- 这正体现**框架可复用**：换掉领域 Agent 就能适配新领域（客服/财务/文档审计）

### Q48. 支持"多轮迭代修改文档"（写→审→改→审），当前架构能支持吗？

**答案：** **当前不能。** 当前只支持 DAG（无环），无图内循环/条件分支/图内重规划。写→审→改→审是迭代循环，需要"执行中间态"回到图中。解法方向：
- **当前近似方案**：用 Critic 的 retry 机制（审不过 → 重跑 generator），但那是"重跑同一输入"不是"迭代修改"
- **根本方案**：执行中 Replanning（把校验从前置一次性变执行中反应式，用中间产物验证规划），需要图内环——这正是 LangGraph 的强项（cycles），README 后续优化方向

### Q49. 并发 100 用户同时提问，瓶颈在哪？怎么优化？

**答案：** 瓶颈：
1. **无队列/无背压/无并发上限** — 请求直连 asyncio，多用户同时跑时 token 与资源无保护
2. **长 run（45-74s）占双端长连接** — SSE 连接被占满
3. **LLM API rate limit** — DeepSeek 并发限制，超了报 429

**优化方向：** 任务队列 + 并发上限（信号量/限流）+ 全局退避重试；LLM 客户端连接池限制（httpx.Limits max_connections=20 已有）；token budget 复用 / 便宜模型兜底 / 相似问题结果缓存。**诚实点：这是"规模没到"不是"没想到"——没上 Celery/队列是因为当前并发量不需要。**

### Q50. 如果从零重写，最想改架构哪一处？

**答案：** 我会把**事件总线外置 + 执行中 Replanning** 作为 v2 骨架：事件总线用 Redis Streams（Java 直接订阅，多实例就绪），执行层加"每节点完成后检查中间产物质量、不合格就地调整子图"（把语义校验从前置猜变成执行中验）。**这两条把当前最深的两条缺点（事件总线实例绑定 + 结构校验≠语义校验）从根上解决。**

### Q51. 多实例部署时，向量库 Chroma 的一致性怎么保证？

**答案：** 现在所有 VectorStore 操作都收敛到**唯一 MCP server 子进程**（FastAPI 主进程、stream_consumer 都通过 MCP 转发），是单写者，单 worker 下安全。一旦 uvicorn 开 `--workers N`，每个 worker 会在 lifespan 里拉起自己的 MCP server 子进程，N 个进程并发写同一个 `./chroma_db` 目录，`compact()` 的"清空+重灌"三步非原子操作就会丢数据，底层 SQLite 也会报 `database is locked`。

> **为什么 threading.Lock 没用：** `compact()` 里的 `_rebuild_lock` 是 `threading.Lock`，只在单进程内互斥线程；跨进程时每个进程各有一把、互不感知。要跨进程互斥必须用**分布式锁**（Redis）。
> **Redis 分布式锁怎么加：** 只锁 `compact()` 三步，单条 add/delete 不加（Chroma 内部原子）。关键坑是 **TTL 必须配合续期（watchdog）**——数据量大时 compact 可能跑几十秒，TTL 设短锁提前释放等于没锁，设长进程崩溃会阻塞别人直到超时。正确做法是每隔 1/3 TTL 续一次，崩溃由 TTL 兜底。
> **为什么说换库是根治：** 锁只是把并发写变成串行，是缓解；Chroma 是**嵌入式单写者库**（SQLite + 文件），从架构上就不支持多进程并发写，真正多实例要换分布式向量库。优先级：pgvector（有 SQL 基建、语义接近现有查询）、Redis Stack（已有 Redis、零新增组件）、Milvus（专用分布式、运维重）。MySQL 8.0 无原生向量（9.0 才有 VECTOR）。
> **换库成本低：** VectorStore 是唯一封装层，RAGEngine/MCP 只依赖它的接口，重写实现层（约 100 行）即可，上层全不动。
> **判断标准：** 单用户场景不需要换——锁住 compact + 保持单 worker 就够；真到多实例并发入库，才是换库时机。

### Q52. compact() 这个"重建索引"机制有必要吗？会不会反而有风险？

**答案：** 单用户规模下**不是必要**的，而且风险大于收益。compact() 解决的是 Chroma delete 留下的 tombstone 占磁盘，但删除的向量本来就被 tombstone 排除在检索结果外——不 compact 功能完全正确，只是磁盘慢慢涨。而 compact 是"读全部 → reset_collection 清空 → 重灌"三步**非原子**操作，reset 那一下是全库删除，中途进程崩溃整个向量库就空了。触发阈值是删满 50 个文档，单用户场景要攒很久，这个空间收益根本不值得押上全库数据安全。

> **为什么不 compact 也正确：** Chroma 的 delete 会打 tombstone，查询时自动过滤这些 ID，用户无感；代价只是 SQLite 磁盘不收缩、索引里死条目变多、查询略慢，规模小可忽略。
> **它真正的风险：** reset_collection() 是清空集合，紧接着才批量重灌。三步不是原子操作，万一在 reset 之后、重灌之前进程崩溃，库就是空的，没有任何恢复手段。而且它是"删满 50 个文档就在请求线程里同步触发"，删除接口会被全量重建拖慢。
> **怎么改：** 默认关掉自动触发，接受墓碑膨胀；真要回收空间，低峰期停机备份后离线重建，比在请求路径里同步重建安全。根治还是换库（pgvector/Redis Stack 的 delete 真正释放空间）。
> **面试加分点：** 主动指出自己代码里的过度工程——"知道什么时候不需要一个优化"比"堆了一堆优化"更能体现设计判断。

### Q53. 项目里用了几种通信协议？分别用在哪？

**答案：** 5 种。

**① HTTP / SSE（占大头）**
- 前端 → Nginx → Java：HTTP REST API 请求
- Java → 前端：**SSE**（Server-Sent Events）长连接，一条流承载 plan/agent/token 三类事件
- Java ↔ Python：POST /qa/query + SSE 流式响应；Python → Java callback POST `/qa/callback`（X-Callback-Token 鉴权）
- Stream-consumer → Python：POST `/ingest/document`（文档入库）
- Python → Ollama：HTTP REST（embedding 推理 + LLM 推理）
- Stream-consumer → MinIO：HTTP（S3 兼容 API，文件上传下载）

**② stdio（MCP 协议）**
- Python 主进程 ↔ MCP Server 子进程：JSON-RPC 格式，通过进程标准输入输出传输，不走网络端口。用 stdio 而不是 HTTP 的原因：避免端口竞争、同一进程内延迟最低、子进程生命周期由主进程管理

**③ AMQP 0-9-1（消息队列）**
- Java → RabbitMQ：发布文档处理任务
- Stream-consumer → RabbitMQ：消费任务。异步解耦：文档上传后立即返回，后台消费者处理向量化

**④ RESP（Redis 协议）**
- Python → Redis：记忆读写、历史缓存、文档摘要缓存
- Java → Redis：Spring Data Redis 读写

**⑤ MySQL Wire Protocol**
- Java → MySQL：会话、消息、文档元数据持久化（JDBC/TCP）

> **为什么选 SSE 不选 WebSocket：** SSE 是单向推送（服务端→客户端），天然适合"服务端生成回答实时推给前端"的场景；WebSocket 是双向的，这里前端不需要向服务端推数据，用 SSE 更轻量，且 SSE 走标准 HTTP，不需要额外协议升级，Nginx 反向代理天然支持。
> **为什么 MCP 用 stdio 不用 HTTP：** MCP Server 是 Python 主进程拉起的子进程（不是独立服务），stdio 是进程间最直接的通信方式——零网络开销、零端口占用、主进程退出子进程自动回收。如果 MCP Server 是独立部署的微服务，才需要走 HTTP。
> **协议选择的判断标准：** 实时推送用 SSE，异步解耦用 AMQP，工具调用用 stdio（进程内）或 HTTP（跨服务），缓存用 RESP，持久化用 MySQL。没有一种协议通吃，按场景选。
