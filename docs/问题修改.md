# 面试准备 —— 项目缺点分析（逐个看）

> 定位：这十条不是"系统有 bug"，而是**设计取舍的边界**。面试讲缺点挑 2-3 个，每个必跟解法方向，展示"知道自己系统的边界"，而不是"系统有 bug"。
>
> 记住一句心态话：**背不出缺点的项目 = 没深度的项目；讲得清缺点的项目 = 你想过怎么做的项目。**

---

## 第一类：架构矛盾（最深，优先讲）

### 1. 「无状态 Python」与「SSE 长连接事件总线」冲突

**问题描述**
- 设计目标是多实例水平扩容、无会话粘滞
- 但 `RuntimeEventBus` 是**进程内 pub-sub**，`run_id → 事件` 全在内存
- SSE 消费者必须连到"执行这个 run 的那个 Python 实例"，否则收不到事件
- 扩到 2 个 Python 实例后，Java 侧必须做 **sticky 路由**（run 固定打到某实例）
- 所以粘滞没消失，只是从"状态粘滞"变成"连接路由粘滞"。单实例不暴露，多实例才暴露
- 进程崩溃：进行中的 run 事件随进程丢失，只能冷启动重建记忆，**无续跑能力**

**解法方向**
- 事件总线外置为 Redis pub/sub / 跨进程消息，或 Java 网关做 sticky 路由

**面试话术**
> 当前单实例下不暴露，多实例部署时需要把事件总线外置为 Redis pub/sub，或在 Java 网关做 sticky 路由，这是演进方向。

### 2. 六层校验是「结构校验」，不是「语义校验」

**六层校验到底在查什么（对照实际代码 `_validate_task_graph`，agent_orchestrator.py:598）**

| # | 层 | 代码位置 | 查什么 |
|---|---|---|---|
| 1 | 结构 | validate_structure（workflow_validator.py:13） | 空图 + 依赖存在性 + 循环检测（拓扑排序） |
| 2 | 能力 | registry.validate_capabilities | agent 在不在注册表、cap 满足度 |
| 3 | 策略 | validate_controller_usage（:72） | controller 不能当 DAG 根节点 |
| 4 | goal 能力 | validate_goal_capability（:100） | goal_outputs 至少被某个 agent 的 output_keys 包含 |
| 5 | goal 可达 | validate_goal_reachability（:110） | 按拓扑序传播 outputs，DAG 能产出 goal_outputs |
| 6 | 数据流 | validate_port_bindings（:183） | 格式 / 上游存在 / 上游关系 / output_key / 类型兼容 / 必选端口齐全 |

共性：**全部是"这个 DAG 能不能执行、执行时会不会崩、数据类型对不对"，没有一层回答"这个 DAG 是不是用户问题的最优解"。**

**核心鸿沟：能执行 ≠ 应该执行**

打个比方：**六层校验是编译器，不是代码评审。**
- 编译器（六层）：保证类型正确、不崩溃、接口对得上 → 拦不住"逻辑 bug"
- 代码评审（缺失）：判断"这个程序是不是真解决了需求" → 需要语义理解

"任务分解正确性"本质是"问题语义 → 任务"的映射，这个映射**只存在于 Planner 的 LLM 里**，结构校验够不着它。

**`_post_process_plan` 是"打补丁"的证据（agent_orchestrator.py:502）**

- 规则 1（:511）用 `sum_keywords`/`rank_keywords`/`rank_patterns` **关键词+正则**触发，补 analysis
- 它触发的是"**问题文本里有没有关键词**"，不是"**LLM 生成的 DAG 哪里错了**"——根本不在检查规划质量
- 规则 3（:567）任何非 chat DAG 强制补 critic——不管答案质量多好，只要没有 critic 就补，纯**形式检查**
- 注释（:515）"裸'第'会把'第二个文件'/'第一季度'误判为排名"——**规则自己还要修规则来防误判**，维护是发散的
- 三条规则都是**事后**从真实失败里总结的（"检测到数值问题但无 analysis，自动修正"），不是事前设计——这就是补丁

**溜过去的真实场景（面试最有力）**

- **场景 A（LLM 规划错 agent）**："对比三份实验报告差异" → LLM 规划 `retrieval → generator`（漏 extractor）。六层校验全通过（类型匹配/数据流合法/goal 可达），但没有规则说"对比类必须用 extractor"→ 生成不引用证据的泛泛回答。结构对，语义错
- **场景 B（关键词表盲区）**："给我看看这个季度的销售情况" —— 无 sum/rank 关键词，规则不触发，LLM 漏 analysis 也没人拦
- **场景 C（规则误判）**：rank_patterns 自己会把"第二个文件"误判成排名，需要注释里的修正
- **场景 D（goal_outputs 假通过）**：validate_goal_reachability 只查"某个 agent 的 output_keys 含 answer"——chat 和 generator 都能产 answer，**都可达，但一个是真分析一个是硬答**，校验器分不出

**为什么是"系统上限"不是"实现 bug"**

唯一把"用户问题"翻译成"任务"的是 **Planner LLM**。六层校验只保证"翻译出来的 DAG 能跑"，手写规则只补"已知场景的缺失"。所以：
- Planner 能力 → 决定任务分解的天花板
- 六层校验 → 只能防止天花板以下的结构错误
- 手写规则 → 补丁完备性由开发者枚举能力决定，**永远追不上 LLM 的错误空间**

这是**所有 LLM 规划系统的共同宿命**（OpenAI 也靠 heuristic 兜底），关键是你意识到边界在哪。

**解法方向**
- 执行中 Replanning：把校验从"前置一次性"变成"执行中反应式"——**用中间产物验证规划**（retrieval 没返回预期数据？Analysis 输出不满足下游？当场调整子图），把"语义对错"从"猜"变成"用真实数据验证"
- 结果级自动评估：Critic 升级为**答案对照问题的语义充分性评估** + golden set 离线评测集，让 Critic 质量可量化、可回归

> 这两个正是 README「后续优化」里的"动态 Replanning"——缺点后面跟解法，且解法是既有规划，逻辑自洽。

**面试话术**
> 六层校验保证的是**可执行性**，不是**正确性**——它验证 DAG 类型合法、数据流通、goal 可达，但不验证"这个任务分解是否回答了用户问题"。后者取决于 Planner 的能力，是我的系统上限。`_post_process_plan` 的 3 条规则是事后从真实失败里总结的关键词启发式，本质是给"LLM 掉线"打补丁，规则覆盖不到的场景就漏。我的解法方向是执行中 Replanning——用中间结果验证规划对不对，而不是前置猜一次；加上结果级自动评估，让"答案是否答对题"可量化。

## 第二类：运行时问题

### 3. 无队列、无背压、无并发上限

**问题描述**
- 请求直连 FastAPI asyncio，每个 run 一串 LLM 调用（5 节点 DAG ≈ 8-10 次）
- 多用户同时提问时进程资源、token 消耗没有保护
- 没有 Celery/任务队列，长 run（实测 45-74s）全程占 Java↔Python 双端长连接
- 120s 超时只是"防止 SDK 重试空转"，不是全局退避重试策略

**解法方向**
- 引入任务队列 + 并发上限（信号量/限流）+ 全局退避重试

---

### 4. SSE 单流单点 + 手动停止不持久化

**问题描述**
- 单流链条上 Java / Python / Nginx 任一处断开，流就断了
- 双端心跳只能"检测到断开"，不能"恢复"
- 用户点停止的 run 直接不持久化：历史里看不到半成品，无法从停止点恢复

**解法方向**
- 断点续传 / 持久化部分状态；心跳升级为自动重连

---

### 5. Callback 持久化无重试

**问题描述**
- `_callback_java`（qa.py:209）是单次 HTTP POST，失败直接返回 False → `RuntimeError("callback 持久化失败")`
- 失败场景：Java 服务重启/网络抖动/超时（30s）/非 200 响应
- 失败后果：对话结果没写进 MySQL，用户刷新历史看不到这条问答；SSE 实时回答不受影响（已推给前端）
- dirty 标记只在成功时清除（`:234`），但不会触发重试——下次请求只持久化当次结果，不补上一次
- 游客（无 session_id）直接跳过，不持久化

**解法方向**
- 指数退避重试（2-3 次，1s/2s/4s），覆盖 Java 短暂重启
- 失败后写入 Redis 死信队列，后台定时重试，覆盖长时间故障

## 第三类：正确性问题

### 6. Critic 深度有限 + 重试成本高

**问题描述**
- **确定性层（RuleValidator）不查覆盖**：只查空 answer + 数值一致性（95/95%/0.95 normalize），对"答没答对题"无能为力
- **LLM 层有覆盖标准但软**：`slim_evaluate` prompt（prompts.yaml:148）含"完整性：是否回答了用户的问题"标准，每轮（含第二轮）都用同一 prompt；软在三处：
  - 主观判断：完整性只是三条标准之一，交给 LLM 一眼扫，无结构化核对
  - 宽容倾向：prompt 两处软化（"不要因 evidence 缺细节判编造""evidence 只是摘要，generator 可能提取更多"），等于教它倾向放行
  - 非结构化输出：判定"没覆盖"也不定位具体缺失点
- **第二轮不复核第一轮**：重试后 Critic 用同一 prompt 重新评估，不拿第一轮的问题清单逐条验证"是否已修复"
- **无 golden answer 评估集**：Critic 质量无法量化、无法回归
- **重试成本高**：重跑子图 = 重调 LLM，失败一次成本翻倍；仅外层 `max_iterations=10` 防死循环，无"值不值得重试"的细粒度判断

**解法方向**
- 结构化覆盖检查：把问题拆成明确要求（requirement 列表）逐条核对，输出缺失项清单——让"没覆盖"从模糊判断变成可定位的硬证据
- 第二轮验证闭环：拿第一轮的问题清单逐条验证是否修复，未修复继续 retry——从"重新评估"变成"收敛式修复"
- golden set 离线评测：测覆盖判断的 recall/precision，让 Critic 可回归
- 成本对冲：确定性规则优先（能规则化的覆盖检查走 RuleValidator）+ retry_target 精准重跑 + 值得重试判断

**面试话术**
> 确定性层（RuleValidator）确实不判断覆盖，但 LLM 层 prompt 有"完整性"标准、每轮（含第二轮）都会跑。局限在软：主观判断、prompt 倾向放行、输出非结构化——判定"没覆盖"也不定位到具体缺失点，且第二轮是重新评估、不复核第一轮发现的问题。真要闭环，需要结构化覆盖检查 + 第二轮问题清单验证。

### 7. 防御性代码未被测试覆盖

**问题描述**
- 并行分支检索隔离（`ctx_source_id`、`search_contexts`）标注"防御性保留：当前 planner 单检索 DAG 下实际不触发"
- 这套复杂的并发隔离逻辑**从未被真实场景跑通过**
- 一旦将来出现多检索分支，风险裸奔，而这恰是最难测的并发逻辑

**解法方向**
- 构造多检索分支的测试用例 / 集成测试覆盖

## 第四类：安全边界

### 8. CodeAgent 沙箱缺层级

**问题描述**

**解法方向**

## 第五类：工程与演进

### 9. 动态 DAG 让测试和可观测性变难

**问题描述**
- 同一问题两次执行可能产生不同 DAG → 单测无法穷举、回归困难
- 依赖真实 LLM API，CI 里跑测试成本高且不稳定
- Python/Java/前端日志分散，只有 Token Metrics、没有统一 tracing，跨层排查慢

**解法方向**
- LLM 输出打桩（mock）/ 录制回放；引入 OpenTelemetry 统一链路

### 10. 领域覆盖窄，只支持 DAG 子集

**问题描述**
- 无循环、无条件分支、无图内重规划
- 需要"迭代反思"的任务（写代码 → debug → 改，多轮修改文档）不支持
- 7 个领域 Agent 之外的用户意图，Planner 可能**强行拆出错误 DAG**，而校验拦不住语义错误

**解法方向**
- 动态 Replanning（后续优化项）；按需扩展领域 Agent

### 11. 成本线性叠加

**问题描述**
- 每轮固定成本：Planner 1 次 + 每 Agent 至少 1 次 + Critic 1-2 次
- 45-74s 延迟绝大部分是 LLM 时间
- 换更贵的模型成本线性上涨；重试再翻倍

**解法方向**
- token budget 复用 / 便宜模型兜底 / 结果缓存

### 12. Chroma 单写者：多实例扩容的向量库天花板

**问题描述**
- 与缺点 1 同源：设计目标是多实例水平扩容，但向量库 Chroma 是**嵌入式单写者**库（SQLite + 文件），原生只支持一个进程打开写
- 当前全仓库 `VectorStore()` 只在 MCP server 子进程实例化一次（server.py:260），FastAPI 主进程和 stream_consumer 都通过 MCP 转发 —— 这是 7/29 修复后收敛出的**单写者架构**，单 worker 下安全
- 隐患在扩容时暴露：uvicorn 开 `--workers N`，每个 worker 都会在 lifespan 里拉起**自己的 MCP server 子进程**，每个子进程各自 new VectorStore 指向同一 `./chroma_db` → N 个进程并发写
- 关键缺陷：`compact()`（vector_store.py:46）是"读出全部 → reset_collection 清空 → 批量重灌"三步非原子操作，并发 compact 必然丢数据；而它的 `_rebuild_lock` 是 **threading.Lock（进程内），跨进程形同虚设**
- Chroma 底层 SQLite 多进程同时写会报 `database is locked`；进程崩溃留下的半写状态可能让整个库打不开

**解法方向**
- 锁（缓解）：Redis 分布式锁只罩 compact() 三步，单条 add/delete 不加（Chroma 内部原子）；锁必须带 TTL 续期（watchdog），否则 compact 耗时 > TTL 锁提前释放等于没锁
- 换库（根治）：pgvector（语义接近现有 SQL）/ Redis Stack（已有 Redis）/ Milvus（专用分布式）；MySQL 8.0 无原生向量（9.0 才有 VECTOR）
- 迁移成本低：所有 Chroma 操作被封装在 VectorStore 类里，RAGEngine 和 MCP 工具只依赖接口 → 换库只重写一个 ~100 行实现层，上层全不动

**面试话术**
> 所有向量库操作都收敛到唯一 MCP server 子进程 —— 这是单写者设计，单 worker 下安全。但 Chroma 是嵌入式单写者库，一旦 uvicorn 开多 worker，每个 worker 拉起自己的 MCP server 子进程，多个进程并发写同一目录就会出问题：compact 是"清空+重灌"非原子操作，线程锁跨进程又不管用。解法分两层：锁是缓解（Redis 分布式锁只锁 compact、TTL 必须续期），换库是根治（pgvector / Redis Stack）。而且因为 VectorStore 是唯一封装层，换库成本只在一个文件。

> 判断标准：单用户场景锁或单写者就够了；真要多实例并发入库，才是换库时机。

### 13. compact() 非原子重建：为省磁盘押全库数据

**问题描述**
- `compact()`（vector_store.py:46）是"读全部 → reset_collection 清空 → 原样重灌"三步**非原子**操作，reset 那一下是全库删除，中途进程崩溃 = 整个向量库清空
- 触发阈值是删满 50 个文档（`_compact_threshold=50`，按文档数计不是 chunk 数），且删除的向量本来就被 Chroma tombstone 排除在检索外——**不 compact 功能也正确**，只是磁盘慢慢膨胀
- 单用户规模下 50 次删除要攒很久，墓碑膨胀量级很小 → 这是**过度工程**，用全库数据安全换一点磁盘空间，不划算
- 触发链路：delete_by_document_id → `_delete_count` 累加 → 到达阈值在**请求线程里同步**触发全量重建，删除接口被拖慢
- 与缺点 12 同源：多进程并发 compact 必然丢数据，`threading.Lock` 跨进程无效

**解法方向**
- 默认关掉自动 compact，接受 tombstone 膨胀（单用户规模完全可接受）
- 真要回收空间：低峰期停机备份 → 离线重建，比请求路径里同步重建安全
- 根治回到缺点 12：换分布式向量库（pgvector/Redis Stack 的 delete 真正释放空间）

**面试话术**
> compact 解决的是 Chroma delete 留下的 tombstone 占磁盘，不是正确性问题——删掉的向量搜索时本来就不返回，不 compact 只是磁盘慢慢涨。我当初加了"删满 50 个文档全量重建"，但它的风险是 reset 清空后重灌这一步非原子，中途崩会丢全库。单用户规模其实可以不要它，真要回收空间，低峰期离线重建更安全。

## 面试怎么讲（不塌房版）

挑 **2-3 个**讲，别全倒出来。最佳组合：

1. **无状态 vs 事件总线** —— 跟解法：Redis pub/sub 外置 或 Java sticky 路由
2. **结构校验 ≠ 语义校验** —— 跟解法：执行中 Replanning + 结果级自动评估
3. **Critic 无量化评估** —— 跟解法：沉淀 golden set 做离线评测

> 这 3 个恰好对应 README 后续优化里的"动态 Replanning"，逻辑自洽。每个缺点后面**必须跟一个解法或改进方向**，面试官听到的是"这个人知道自己系统的边界"。

## 心态锚点（答自己）

- 这些"缺点"里，大半是**取舍**（无队列/单实例/进程内事件总线 = 单机规模不需要），不是错误
- 真正需要改进的只有一两个（启发式兜底 / 防御性代码没测过）
- 21 岁 solo 写完 Python 后端 + Java 网关 + 前端 + Docker 编排，复杂度已超 90% 校招 CRUD 项目
- 面试官最怕的不是项目有缺点，是**项目没什么好问的**
