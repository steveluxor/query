# 一、架构总览与项目定位（Q1-18）

### Q1. 30 秒介绍这个项目。
**答案：** 这是一个 **Planner-centric 的 Agent Runtime Framework**——不是 RAG 应用，RAG 只是其中一个 Capability。核心流程：用户问题 → **Planner LLM 动态生成任务 DAG**（谁、做什么、依赖谁）→ **确定性执行运行时**拓扑调度、按 Capability 分派、port_bindings 注入数据、Controller（Critic）触发重试 → 实时 SSE 透传到前端。Python（FastAPI）做规划与执行，Java（Spring Boot）做统一网关（鉴权 + SSE 透传 + 持久化），前端实时渲染 DAG 状态与 Agent Trace。

### Q2. 为什么说它不是 RAG 项目？
**答案：** RAG 项目以"检索增强生成"为系统范式，检索是核心。这里检索只是 `retrieval` 这一个 Agent 的能力，系统的核心是 **LLM 动态规划任务图 + 确定性运行时执行**。面试官第一印象要在 30 秒内识别它是 Agent Runtime，而不是"基于 LangChain 的问答系统"。

### Q3. 系统分哪三层？请求链路是什么？
**答案：** 三层：前端（Nginx :8080，原生 HTML/CSS/JS）→ **Java 统一网关**（Spring Boot :8085）→ **Python AI 服务**（FastAPI :8000）。链路：前端提问 → Java `/qa/ask` 鉴权后转调 Python → Python 异步启动任务、立即返回 `run_id` → 前端连 Java `/qa/runtime/{runId}` SSE → Java 透传 Python 的 `/qa/runtime` 流 → 执行完成后 Python 调 Java `/qa/callback` 持久化（X-Callback-Token 鉴权）。

### Q4. "LLM 决定做什么，Runtime 保证怎么执行"这句话怎么展开？
**答案：** "LLM 决定做什么"= Planner 每轮把用户问题翻译成一张任务 DAG（节点是 agent、边是 depends_on、port_bindings 是数据契约）。"Runtime 保证怎么执行"= 这张 DAG 不是裸跑的：先过**六层结构校验**保证可执行、`_post_process_plan` 三条规则兜底修正、拓扑排序保证顺序、asyncio.gather 并行执行、Controller 按需重试、失败跳过下游。**LLM 负责语义，Runtime 负责确定性。**

### Q5. 为什么不用固定 Workflow，而要 Planner 动态生成？
**答案：** 固定 Workflow 是预定义流程，适合"问题模式已知"的场景。这里用户问题千变万化——有的是简单问候（单 chat 节点）、有的是纯数值求和（retrieval→analysis→generator）、有的是对比+画图（retrieval→extractor+code→generator→critic）。用固定流程要么过度（普通问题也跑全链路浪费 token），要么不足（复杂问题拆不开）。Planner 每轮动态生成 DAG 才能按问题匹配能力。

### Q6. 说说你项目里 7 个 Agent 的分工。
**答案：** 三个 Executor + 一个 Controller + 三个交互型：
- **retrieval**：把问题翻译成搜索关键词，调 `search_documents`/`list_documents`，产出 `document_bundle` + `retrieval_report`
- **extractor**：把检索到的文档提取成结构化知识对象 + evidence（每条 50-80 字断言）
- **analysis**：固定工具调用，`calculate_sum`/`calculate_rank`/`read_all_rows`，只做数值计算（最多 8 次工具调用）
- **code**：生成 Python 代码做任意计算（分组/占比/统计），支持 matplotlib 画图存 PNG
- **generator**：综合 knowledge_objects + evidence + analysis/code 结果组织最终答案
- **critic**：Controller，两级审核（RuleValidator 确定性 + LLM 语义），产出 retry 控制信号
- **chat**：问候/上下文可答的简单对话

### Q7. Agent 之间是怎么通信的？为什么不共享一个对象？
**答案：** 不是共享对象，而是**声明式 Capability 契约 + port_bindings 数据流**：每个 Agent 声明 `inputs`（端口名→类型）和 `outputs`（产出 key→类型），Planner 用 `port_bindings` 把上游 output 绑到下游 input。Runtime 执行时从 context 按端口取数据注入。这样 Agent 之间**零直接依赖**，新增 Agent 只注册能力即可，符合"声明式解耦"。

### Q8. 数据是怎么在 Agent 间流动的？靠什么存？
**答案：** 靠 `AgentContext.outputs`（`key → {task_id: AgentOutput}`）。每完成一个 Agent，Runtime 把它的 outputs 写进 context，带 producer/version/timestamp 元数据。下游 Agent 通过 `port_bindings` 指定的"来源 task + output_key"从 context 取，**不自动注入、不自动拿所有上游数据**，只拿声明的。多 task 写同一 key 时按 `merge_policy`（replace/append/dedup）合并。

### Q9. Context 是谁在读写？权限边界在哪？
**答案：** `AgentContext` 分两类字段：**系统字段**（question/session_id/plan 等）初始化后只读；**outputs 交换容器**由 Runtime 统一写入（Agent 只返回 AgentResult，不直接改 context 输出），Agent 之间靠 port_bindings 显式取。读写有 `_lock`（RLock）保护线程安全，`set_output` 按 contextvar 里的 task_id 隔离存储。

### Q10. 一个 5 节点 DAG 大概会调多少次 LLM？
**答案：** 典型 9-11 次，但 **9-11 是低值不是上限**——多个环节不是每次都只调 1 次：
- **Planner** 1 次（问题 → DAG）
- **Retrieval** **2 次**：① 搜索词+类型（`retrieval_agent.py:99`，temperature=0/max_tokens=200，全链路最便宜）② 文档相关性判断（`mcp/server.py:229` `_judge_relevance`，search_documents 内部批量 1 次，用文档摘要过滤无关文档，prompt 见 `prompts.yaml:385` relevance.judge）
- **Extractor** **按文档数 × 每 15 chunk 一批**，多文档并行（`extraction_agent.py:129` batch_size=15）——3 份文档就是 3+ 次，token 大头在这
- **Analysis** **ReAct 循环，每轮工具调用 1 次**（`analysis_agent.py:54`，recursion_limit=15）——简单求和 2-3 次，复杂更多
- **Code** **最多 3 次**（生成代码+执行，失败重试 2 次，`code_agent.py:20`）
- **Generator** 1 次，流式输出（`answer_generator.py:67` astream，所以首字快但总时长长）
- **Critic** 0-1 次：先走 RuleValidator（确定性，0 次 LLM），通过才走 LLM 语义审（`critic_agent.py:65`）

所以「对比 3 份实验报告」≈ Planner 1 + Retrieval 2 + Extractor 3 + Analysis 3-5 + Generator 1 + Critic 1 = **11-13 次**。这就是实测 45-74s 延迟的主要来源——绝大多数时间花在 LLM 上，不是代码执行。

**每个 LLM 调用干什么（为什么不能合并）：**

| # | 调用 | 干什么 | 能否省/并 |
|---|---|---|---|
| 1 | Planner | 唯一做"问题语义→任务"翻译，系统编译器 | 不可省；可结果缓存（相似问题复用 DAG） |
| 2 | Retrieval 搜索词 | 分类(aggregation/comparison)+扩写检索词 | **最值得砍**——已有关键词兜底（`:131` sum_kw/rank_kw），代码自己承认可被规则替代 |
| 3 | Retrieval 相关性判断（`_judge_relevance`） | 用文档摘要批量过滤无关文档（1 次判断全部），写回 search context 让下游只看到相关文档 | 不可省——**1 次换省 N 次 extractor 调用**，成本杠杆最高；可换便宜模型 |
| 4 | Extractor | 全量文档 → 结构化 KnowledgeObject + 50-80 字精简证据 | 不可省；可换便宜模型（机械提取） |
| 5 | Analysis | 决定调哪个计算工具+解读结果 | 纯求和可确定性化，LLM 只做决策 |
| 6 | Code | 数据摘要 → Python 代码（执行是确定性沙箱，只生成是 LLM） | 不可省；重试合理但可减次数 |
| 7 | Generator | 知识+证据+结果 → 最终答案，唯一面向用户 | **不可省**——最终交付物 |
| 8 | Critic | 答案+证据 → score/need_retry/retry_target | 可并进 Generator（自检），但**最不该并** |

**三条硬理由为什么不能合并：**
1. **重试粒度**：Critic 返回 `retry_target`，Orchestrator 只重跑子图（invalidate_subgraph）。节点越细，失败重跑成本越低；合并=一次失败整段重跑=成本翻倍。分离的本质是给"哪步错了重跑哪步"留空间
2. **蒸馏漏斗（token 预算）**：数据流逐级缩小 `原始文档(全量) → 知识+证据(精简) → 计算结果(几十字) → 答案`，每节点只吃上一步的浓缩产物。合并 Extractor+Generator=Generator 直接塞全文档→上下文爆炸+幻觉率上升。**这是蒸馏管道不是调用串**
3. **可选节点**：Code 只在算数时出现、Analysis 只在数值题出现、Extractor 在纯数字题被删。动态 DAG 按需装配，合并=全都要跑

**真能减的**：① Retrieval 搜索词→并进 Planner 或纯关键词兜底（最便宜+已有确定性 fallback，最优砍点）② Extractor→换便宜模型 ③ Critic→换便宜模型或 RuleValidator 通过时跳过 LLM 审 ④ Planner→相似问题缓存。

**最不该并**：Generator 和 Critic——Critic 的价值恰是独立于"写答案的模型"之外的判断，自检有确认偏差（写错答案的模型自己看不出错）。

### Q11. Python / Java / 前端各自负责什么？为什么这么拆？
**答案：** Python 负责**有 AI 的部分**（规划、执行、检索、生成）；Java 负责**无 AI 但有状态/安全的部分**（登录鉴权、SSE 透传、MySQL/Redis/MinIO 持久化、会话管理）；前端负责实时渲染（DAG 图 + Agent Trace + token 流）。拆的关键是**无状态**：Python 全程无持久状态，崩溃可从 Java 重建记忆，这让 AI 层可横向扩。

### Q12. 项目里用到了哪些中间件？各自干什么？
**答案：** MySQL（Java 持久化会话/历史/用户）、Redis（记忆快照 + 历史缓存 + 会话历史，**Python 只读、Java 写入**）、MinIO（文档文件 + 图表图片存储）、ChromaDB（向量库）、RabbitMQ（文档入库异步任务队列）、MCP（Agent 工具调用协议，独立进程）。

### Q13. 什么是 MCP？为什么用它而不是直接 import 工具函数？
**答案：** MCP（Model Context Protocol）是把工具做成**独立进程**的标准协议，Agent 通过 stdio 调用 `search_documents` 等工具。好处：工具崩溃不影响主进程、工具可独立启停、将来可用任意语言实现工具、安全边界清晰（代码执行/数据库访问隔离在工具进程内）。

### Q14. 请求是同步还是异步？用户怎么拿到结果？
**答案：** 异步。`/qa/ask` 只负责建 channel + 后台 `create_task` 执行，**立即返回 `run_id`**。用户拿 run_id 连 SSE（`/qa/runtime/{run_id}`），事件流推送 `runtime_started → plan_generated → agent_started/completed → runtime_completed`。好处是长任务不占 HTTP 连接、前端能实时渲染过程。

### Q15. 为什么 RAG 在项目里只是"一个能力"？
**答案：** 检索对某些任务（数值求和、画图、简单对话）根本不是主路径——数值问题直接 analysis 算，画图直接 code 跑。RAG 只是 `retrieval` Agent 的工具之一。项目真正的骨架是 **Planner + DAG 运行时**，RAG 是骨架上的肌肉，不是骨架本身。

### Q16. 简单说下 Critic 是怎么"审答案"的？
**答案：** 两级：**RuleValidator**（纯确定性、<100ms）查空答案 + 数值一致性（计算结果 95/95%/0.95 是否在回答里体现）；**LLM slim_evaluate** 按准确性/完整性/逻辑一致性三条标准审，输出 JSON（score/need_retry/retry_target）。判定要改时返回 ControlAction，Runtime 重跑指定子图。

### Q17. 前端能实时看到什么？
**答案：** 实时 DAG 状态（每个节点 pending/running/completed/failed）、Agent Trace（谁在执行、耗时、调了哪些工具）、token 流（generator 阶段）、Critic 重试的控制信号。全部来自 SSE 事件流。历史页通过 Java `/qa/history` 读 Redis 缓存 / MySQL。

### Q18. 项目最核心的 3 个设计决策是什么？
**答案：** ① **动态 DAG + 确定性执行**——语义归 LLM、正确性归 Runtime；② **声明式 Capability 契约**——Agent 热插拔，编排层不感知 role；③ **Python 无状态 + Java 有状态网关**——AI 层可扩、崩溃可从 Java 重建。这三点串起来就是整个项目的骨架。

# 二、Planner 与 DAG 生成（Q19-40）

### Q19. Planner 完整产出流程是什么？
**答案：** LLM 输出 JSON → `_parse_task_graph` 解析成 TaskGraph（缺 agent 字段直接抛 WorkflowValidationError）→ `_validate_task_graph` 过六层校验 → 通过后 `_post_process_plan` 三条规则兜底修正 → 返回可执行 plan。任一步失败都会 fallback 到 `_fallback_plan`（问候→单 chat 节点；其他→retrieval→extractor→generator）。

### Q20. Planner 的 prompt 里放了哪些上下文？
**答案：** `{available_executors}`（所有 Executor 的能力声明：输出 key + 工具）、`{available_controllers}`（Controller 及其 control_actions）、**可用文档列表**（`list_documents` 实时查，格式 `- [123] 文件名`）、**长期记忆**（memory_context）、**最近 5 轮对话历史**。还支持短追问补全：检测到"结果/继续/然后"等词 + memory 有数值计算上下文时，自动把问题补全为完整链路描述。

### Q21. 六层校验各查什么？按什么顺序？
**答案：** ① `validate_structure`（空图 + 依赖存在性 + 循环检测）；② `validate_capabilities`（agent 注册 + 同层 output 冲突警告 + control_action 不能由 Planner 指定）；③ `validate_controller_usage`（Controller 不能当 DAG 根节点）；④ `validate_goal_capability`（goal_output 至少被某 agent 的 output_keys 包含）；⑤ `validate_goal_reachability`（按拓扑层传播 outputs，当前 DAG 能产出 goal_outputs）；⑥ `validate_port_bindings`（格式/上游存在/上游关系/output_key 存在/port 存在+类型兼容/必选端口齐全）。① 不过则跳过 ②-⑥（依赖存在性坏了后面没法算）。

### Q22. 校验失败会怎样？
**答案：** `_validate_task_graph` 返回 False → `_plan` 返回 None → `run` 走 `_fallback_plan` 兜底，保证任何情况都有一张可执行的图。校验错误全部打 warning 日志，便于排查 Planner 为什么没遵守规则。

### Q23. `_post_process_plan` 三条规则是什么？为什么叫"打补丁"？
**答案：** 规则 1：数值问题（求和/排名关键词）但没有 analysis → 自动插入 analysis task 并接到 generator；规则 2：纯数值问题 → 移除多余 extractor（extractor 90-160s 太慢）；规则 3：非纯 chat DAG 没有 critic → 强制追加 critic。叫"打补丁"是因为它们**不看 DAG 哪里错，只按问题文本关键词触发**，是事后从真实失败里总结的启发式。

### Q24. 规则 1 的关键词表有什么缺陷？
**答案：** 关键词表是手工枚举的（"花了多少钱/总共/合计/最贵/排名"），枚举之外的表达就漏。典型反例："给我看看这个季度的销售情况"——没有 sum/rank 关键词，LLM 漏了 analysis 也没人拦。这是**关键词启发式的通病：完备性取决于开发者枚举能力，永远追不上语言表达空间**。

### Q25. 裸"第"字会被误判吗？
**答案：** 会，所以规则里用了正则 `第\s*\d+\s*(高|低|名|贵|便宜|位)` 而不是裸"第"——注释里明确写着"裸'第'会把'第二个文件'/'第一季度'误判为排名"。**这是"规则自己要修规则来防误判"的证据，说明启发式维护是发散的。**

### Q26. port_bindings 是什么？格式长什么样？
**答案：** 任务的数据契约：`key = 下游 Agent 输入端口名`，`value = "source_task_id.output_key"` 全限定引用。例：`{"knowledge_document": "task1.document_bundle"}` 表示本任务的 `knowledge_document` 端口从 task1 的 `document_bundle` 输出取数据。**所有数据传递必须显式声明，不存在自动注入。**

### Q27. 如果 Planner 忘了写 port_bindings 怎么办？
**答案：** 校验层会报"必选端口缺少 port_bindings"，但更智能的是 `_auto_wire_port_bindings`：执行前根据 Capability 的 inputs/outputs **类型匹配**自动补齐缺失绑定——扫上游 task 的输出，找类型兼容的第一个 output 建绑定。不依赖硬编码的 agent/port 映射，是数据驱动推断。

### Q28. DAG 里 agent 写错了（比如 planner 编了个不存在的 agent）会怎样？
**答案：** 六层校验第 2 层 `validate_capabilities` 直接报 `Agent 'xxx' 未注册` → 校验失败 → fallback。即使绕过校验进了执行，`_run_plan_task` 里 `registry.get(task.agent)` 拿不到 cap 也会跳过该 task 并打 warning。**两层防线**。

### Q29. Planner 输出非法 JSON 怎么办？
**答案：** `_parse_json` 用 `extract_json`（兼容 markdown 代码块包裹），解析失败抛 `PlannerError` → 被 run 捕获 → `_fallback_plan`。缺 `tasks` 字段也会抛 `PlannerError`。**Planner 任何异常都不会让用户空手而归**。

### Q30. 什么是 goal_outputs？执行完要验证它吗？
**答案：** Planner 声明的 DAG 必须产出的最终输出 key 列表（通常 `["answer"]`）。执行结束后 `_execute_plan` 会检查 `context.has_output(o)`，缺了就抛 `WorkflowExecutionError("DAG 未产生目标输出")`——**防止"执行成功但没产出 answer"的静默失败**。

### Q31. Planner 怎么知道有哪些 agent 可用？
**答案：** prompt 里注入 `registry.format_executors_for_prompt()`（Executor 名 + 描述 + 输出 key + 工具）和 `format_controllers_for_prompt()`（Controller + control_actions）。**能力是注册表驱动的**：新增 agent 注册进 registry，prompt 自动带上，Planner 自动学会用它。

### Q32. `analysis` 和 `code` agent 都能做计算，Planner 怎么区分？
**答案：** prompt 明确写了判断标准：**analysis = 固定工具调用（求和/排名），只能单一数值计算**；**code = 任意 Python 计算（分组/筛选/占比/统计）**。并按问题模式映射：求和/最贵 → analysis；按X分组/占比/分布 → code + extractor。两套能力边界写死在 prompt 里，Planner 按问题特征选。

### Q33. 为什么 analysis 必须 depends_on retrieval？
**答案：** analysis 的工具（calculate_sum/rank/read_all_rows）是消费者，依赖 retrieval 先 `search_documents` 填充数据。不依赖就会拿空数据算——所以 prompt 明确禁止两者并行，校验层也通过 port_bindings/依赖检查兜底。code agent 同理必须依赖 retrieval。

### Q34. 纯数值问题为什么可以省略 extractor？
**答案：** extractor 是文本提取，纯求和/排名只需要 analysis 的数值结果，generator 直接引用计算即可回答。省略 extractor 能省 90-160s。prompt 里写了这条规则，`_post_process_plan` 规则 2 又在代码层强制兜底（LLM 忘了也帮你删）。

### Q35. 什么时候必须用 extractor？
**答案：** 需要文本素材的问题："查询信息/是什么/有哪些/总结/对比"。因为 generator 组织答案要引用结构化知识，extractor 负责从文档提取。prompt 末尾有一条强规则："**所有数据类问题都必须包含 extractor**"。

### Q36. Controller（critic）在 DAG 里是什么角色？
**答案：** 特殊节点：它产出的是**控制信号**而非数据。`AgentCapability.control_actions=["retry"]`、`control_outputs=["need_retry","retry_target"]`。Planner 只负责安排 critic 节点在 generator 之后，**不指定它的控制行为**（校验层会拦截 Planner 输出里混入的 control action 字段），行为由运行时根据审核结果决定。

### Q37. Planner 的输出会被校验层怎样"约束控制权"？
**答案：** `validate_capabilities` 里有一条契约校验：如果 Planner 的 task 数据里带了 `action`/`control_action`/`retry_target` 字段，直接报错——**"Planner 不应指定 control action，应由 Controller 运行时决定"**。把"规划"和"控制"的职责在数据契约层面切开。

### Q38. DAG 的循环依赖怎么防？
**答案：** 两层：① `validate_structure` 用**拓扑排序**检测（visited != task 数 → 循环）；② 执行时 `_execute_plan` 的 while 循环里如果没有 ready 任务会打 warning 跳过剩余任务——**校验层拦下大部分，执行层兜底防死循环**。再加上外层 `max_iterations=10` 防 Controller 死循环。

### Q39. Planner 生成 10 个节点会不会太重？
**答案：** 会，但没有上限保护，靠 prompt 约束 + 实际 fallback。这是已知边界（见缺点 9：领域覆盖窄）。当前 prompt 的示例 DAG 都是 3-5 节点，Planner 倾向生成合理大小。若要加保护，可以在校验层加节点数上限。

### Q40. 一条问题两次执行，DAG 会一样吗？
**答案：** 大概率相似但不保证相同——Planner 是 LLM，temperature 非零时同一问题可能产出不同 agent 组合或不同 port_bindings。**这就是动态 DAG 让单测穷举变难的根因**（缺点 8），也是为什么六层校验必须存在：每次的 DAG 都是"新的"，必须每次都验证它可执行。

# 三、DAG 执行引擎（Q41-58）

### Q41. DAG 是怎么被执行的？
**答案：** `_execute_plan` 用一个外层 `for _ in range(max_iterations=10)` 循环 + 内层拓扑调度：每轮计算"依赖全部完成"的 ready 任务，用 **`asyncio.gather` 并行执行**（`return_exceptions=True` 不互相拖死），失败的任务把下游标记 `SKIPPED`。内层 pending 清空后检查还有没有 Controller 触发的 RETRYING 任务，有就再来一轮，直到没有可执行任务或超迭代上限。

### Q42. 并行是怎么实现的？为什么安全？
**答案：** ready 任务扔进 `asyncio.gather` 并发跑。安全性靠三点：① 无依赖的任务才同时 ready（DAG 约束天然无写冲突）；② `set_output` 按 **contextvar `_task_id_var`** 隔离，每个 asyncio Task 有独立 Context 副本；③ outputs 写操作有 `_lock` 保护。所以并行分支写同名 key 时是"每个 task 写自己那份，读取时按 merge_policy 合并"。

### Q43. 失败的任务会怎样？下游会继续吗？
**答案：** 不会。task 抛异常 → 状态置 `FAILED` → **所有下游（BFS 找 get_descendants）标记 `SKIPPED`**，避免以空输入继续执行产生"自信但错误"的回答。这也意味着一个上游崩了，整条支路静默跳过，最终靠 Critic/goal_outputs 兜底发现。

### Q44. 为什么用 `asyncio.gather` 而不是多线程？
**答案：** 整个 AI 调用栈是 async 的（FastAPI + `self.llm.invoke`/`ainvoke` + httpx），协程切换成本极低，天然适合 IO 密集的 LLM 调用。多线程会引入 GIL 竞争 + 线程安全成本。纯 CPU 的同步段（如 CodeAgent 子进程执行）用 `asyncio.to_thread` 或子进程隔离，不阻塞事件循环。

### Q45. Controller 触发 retry 后，DAG 怎么"回到过去"重跑？
**答案：** Critic 返回 `ControlAction(retry, target_task_id="generator"/"retrieval"/"all")` → `RetryHandler` 按 agent 名匹配所有 task，调 `plan.invalidate_subgraph(task_ids)` 把目标及其**所有下游**标为 `RETRYING` → 外层 for 循环检测到有 RETRYING 任务继续下一轮，拓扑调度重新执行它们。**不需要真的回溯，把受影响子图状态重置重新调度即可。**

### Q46. retry_target 的值分别代表什么？
**答案：** 来自 LLM Critic 的 JSON：`"retrieval"`（检索有问题，重跑检索）；`"generator"`（表达问题，只重生成）；`"all"`（严重问题全部重来）。RuleValidator 拦截时固定 `retry_target="generator"`（空答案/数值缺失通常是生成问题）。RetryHandler 把 target 当 **agent 名**在 plan 里匹配，不是 task ID。

### Q47. 重试会不会无限循环？
**答案：** 不会。外层 `max_iterations=10` 硬上限防死循环。但注意：`_run_critic_with_retry`（旧版简单模式）是 `MAX_CRITIC_RETRIES=2`，DAG 模式靠的是 10 次迭代上限。**这是"防死循环"不是"值得重试判断"**——哪怕重试 10 次都不过，也会停止。

### Q48. TaskNode 上会记录哪些执行元数据？
**答案：** `duration_ms`（执行耗时）、`summary`（agent 自报摘要）、`tools_used`（capability 声明的工具名）、`artifacts`（产出物）。这些由 `_run_plan_task` 从 AgentResult 收集回填，供前端 Agent Trace 展示和历史页回放。还用于把工具名映射成可读描述写入记忆。

### Q49. 执行中如何知道"该给这个下游哪个上游的数据"？
**答案：** 只认 `port_bindings`：`_run_plan_task` 遍历 task.port_bindings，`get_output_entry(output_key, task_id=source_task_id)` 精确取指定上游的输出，None 就跳过该端口。**没有 BFS 回退、没有"就近找"**——数据通道唯一且显式。

### Q50. `_resolve_search_provider` 是干什么的？为什么标注"防御性保留"？
**答案：** 消费者工具（calculate_sum/rank/read_all_rows）需要知道自己该读哪个上游检索产生的 SearchContext。它沿依赖链向上找"capability.tools 含 search_documents"的最近上游并锁定。注释明确写：**当前 planner 所有示例都是单检索 DAG，此函数恒解析到唯一检索，与共享 ctx 等价；仅当未来生成多并行检索分支时才有实际作用，勿删**。这是"防御性代码未被真实场景测过"的典型（缺点 6）。

### Q51. 什么叫 contextvar？它解决了并行分支的什么问题？
**答案：** contextvar 是 asyncio 的 Task 本地变量——每个 asyncio Task 有独立的 Context 副本，`set()` 只影响当前 Task。项目用它隔离三样东西：`_task_id_var`（当前 task_id，set_output 时按它归属）、`_search_ctx_source_var`（检索源 task_id）、`_task_objective_var`（各分支自己的 objective）。**没有它，并行分支会互相覆盖共享字段**（如 context.question 被分支 objective 覆盖）。

### Q52. 同一 output key 被多个 task 写，怎么合并？
**答案：** `get_output` 按 `merge_policy` 合并：`replace` 取最后一个；`append`/`dedup` 对 list/DocumentBundle 合并，dedup 用 `dedup_key_func` 去重（DocumentBundle 按 (source, content[:200])）。policy 优先级：显式传参 > `context.merge_policies[key]` > 默认 append。policy 表在 Capability 里声明，执行前从 registry 收集到 context。

### Q53. 执行完全成功的标准是什么？
**答案：** 三件套：① 所有 task 走完 pending 清空（或 Controller 不再触发 retry）；② 没有未处理的异常；③ **`context.has_output(o)` 覆盖所有 goal_outputs**。③ 不满足会抛 `WorkflowExecutionError`，前端收到 runtime_error。

### Q54. 执行过程中事件是怎么发出去的？
**答案：** `context.emit(EventType, data)` → 若 context 有 event_bus + run_id → `RuntimeEventBus.publish(RuntimeEvent(run_id, type, data))` → fan-out 到该 run 的所有 subscriber queue，同时缓存进 history 供迟到订阅者回放。事件类型分两层：Workflow 层（低频状态变化：runtime_started/plan_generated/agent_started/completed/failed/control_action/runtime_completed）和 Generation 层（高频 token_chunk）。

### Q55. 失败为什么要"跳过下游"而不是"终止整个 DAG"？
**答案：** 跳过一个分支不影响其他并行分支继续（比如 extractor 失败，analysis→generator 分支还能产出数值答案）。只有下游依赖它的任务被跳过。最终正确性由两层兜底：Critic 可能发现内容问题触发重试，goal_outputs 校验保证"该产出的没产出会报错"。**比一刀切终止更优雅，但确实允许"半成品"流过**（缺点边界）。

### Q56. `asyncio.gather` 的 `return_exceptions=True` 有什么讲究？
**答案：** 让某个 task 抛异常时其余 task 照常执行完，然后统一检查每个结果。否则第一个异常会立刻取消整个 gather，**把"一个分支失败"放大成"整批都跑不完"**。异常在 zip(ready, results) 里逐个判断，标记 FAILED 并级联 SKIPPED。

### Q57. 执行是"一步一等待"还是"一口气到底"？
**答案：** 一口气到底（按层推进）：内层 while 每轮取所有 ready 任务 gather 并行，一轮跑完再看下一批 ready。不等待单任务间的中间反馈（那是 Replanning 的事，当前没做）。**所以当前是"预规划 + 确定性执行"，不是"执行中重规划"**（缺点 2 的解法方向）。

### Q58. 你能手画一个"对比类 + 数值计算 + 画图"的 DAG 吗？
**答案：** 典型（prompts.yaml 多步分析示例）：`task1 retrieval →（并行）task2 extractor + task3 analysis + task4 code → task5 generator（depends task2/3/4）→ task6 critic`。retrieval 铺数据，extractor 提文本、analysis 算求和/排名、code 算占比画饼图，generator 综合三者，critic 把关。**同一层可并行的节点数 = 一次 gather 的并发度**。

# 四、Agent 体系与数据契约（Q59-76）

### Q59. Agent 是怎么"注册"进系统的？
**答案：** 每个 Agent 类声明一个 `capability: AgentCapability`（name/description/inputs/outputs/tools/merge_policy/control_actions...），`create_default_registry` 实例化后逐个 `registry.register(capability, instance)`。注册表同时维护**能力声明**和**实例绑定**，Planner prompt 和 Runtime 分派都从注册表读。

### Q60. AgentCapability 的 inputs/outputs 类型有什么作用？
**答案：** 三重作用：① Planner 的 port_bindings 数据契约校验（`_type_matches` 类型兼容）；② `_auto_wire_port_bindings` 类型匹配自动补绑定；③ prompt 里向 Planner 展示"这个 agent 吃什么吐什么"。**类型即接口**，把 Agent 间的耦合从"约定"变成"可校验的契约"。

### Q61. 加一个新 Agent（比如"文档翻译"）要改哪些代码？
**答案：** 只需：① 新建类实现 BaseAgent.run + 声明 capability；② 在 `create_default_registry` 里注册。**Planner prompt 自动带上它、六层校验自动识别它、Runtime 自动能分派它**——这就是热插拔。不需要改 Orchestrator、改 prompt 里硬编码的 agent 清单、改任何分支逻辑。

### Q62. Executor 和 Controller 的区分标准是什么？
**答案：** `capability.control_actions` 非空就是 Controller（能输出控制信号改变流程，如 critic 的 retry），否则是 Executor（普通数据节点）。注册表用 `find_executors()`/`find_controllers()` 分类，prompt 里分开展示，策略校验层对 Controller 有额外约束（不能当根节点、control 字段不能由 Planner 指定）。

### Q63. 为什么 critic 是 Controller 而不是普通 Agent？
**答案：** 因为它不只"产出数据"，还要**决定流程走向**——`parse_actions` 从 context 读 need_retry/retry_target 生成 ControlAction。ControllerAgent 基类的 execute 会调用 `parse_actions` 并把 actions 放进 AgentResult，由 ActionRegistry 分发执行。**普通 Agent 无法影响控制流**，这是架构上把"审核"和"执行"解耦的设计。

### Q64. merge_policy 的 replace/append/dedup 各自适用什么场景？
**答案：** replace：重试后覆盖旧值（critic 的 critique 每次重新覆盖）；append：多个证据源拼接（evidence_list 来自多个 extractor 分支时拼接）；dedup：拼接但按 key 去重（DocumentBundle 多分支合并按 (source, content) 去重）。声明在 Capability 里，读取端自动应用。

### Q65. Agent 的执行返回什么？Runtime 怎么用它？
**答案：** 返回 `AgentResult`：`summary`（执行摘要）、`outputs`（dict，写进 context）、`actions`（ControlAction 列表，交给 ActionRegistry）、`tools_used`/`artifacts`（回填 TaskNode 元数据）。**Agent 不直接改 context.outputs——它返回数据，Runtime 统一写入**，职责清晰。

### Q66. BaseAgent 和 ControllerAgent 的区别？
**答案：** BaseAgent.execute 只跑 run 然后返回 `AgentResult(summary)`；ControllerAgent.execute 跑 run 后额外调 `parse_actions(context)` 把控制信号放进 `AgentResult(actions=[...])`。两者都统一做日志、计时、加 trace、异常上抛。**继承树只有两棵：普通执行型 和 控制型**。

### Q67. retrieval agent 的产出是什么？
**答案：** `document_bundle`（DocumentBundle，检索到的文档 chunk 集合）+ `retrieval_report`（检索报告，给 critic 用）。它本身把问题转成搜索关键词（prompt 约束"只输出关键词"），然后调 MCP 的 `search_documents`/`list_documents` 工具，最多 2 次搜索。

### Q68. extractor 的产出和规则是什么？
**答案：** `knowledge_objects`（结构化知识对象：topic/attributes/source/confidence）+ `evidence`（50-80 字核心断言）。规则：表格/行数据**每行提取为一个独立知识对象**（不做汇总）、attributes 用短语不用句子、宁少勿滥 3-5 个关键属性、JSON 双引号必须转义。输出纯 JSON。

### Q69. analysis agent 和 code agent 的边界为什么必须切清楚？
**答案：** 因为能力成本不同：analysis 是固定工具（求和/排名，最多 8 次调用），可靠但单一；code 是任意 Python，灵活但引入代码执行风险（沙箱）。prompt 里用了大段篇幅写"三个 Agent 的区别"和 code 使用判断标准，就是怕 Planner 混用——**拿 code 做简单求和是过度，拿 analysis 做分组统计是能力不足**。

### Q70. code agent 生成代码有哪些硬性约束？
**答案：** 可用变量只有 `data`/`upstream`/`question`；结果必须赋值给 `result`；**禁用 os/subprocess/socket/shutil**（沙箱白名单）；必须处理 KeyError 等异常；要画图时必须 matplotlib Agg + 中文字体 + 只允许 `plt.savefig` 写文件；**每个 task 的执行有独立子进程 + 512MB + 60s 上限**。

### Q71. generator 的组装规则是什么？
**答案：** 基于 knowledge_objects + evidence 组织回答（分析结果可参考）；**纯数值场景**：analysis 非空且 knowledge_objects 为空时直接基于计算结果组织数值答案（不等 extractor）；图表已生成时不要提文件路径（图单独展示）；知识不足要明说"在已检索到的内容中未找到"，不编造。

### Q72. chat agent 什么时候被 Planner 选中？
**答案：** ① 问候/闲聊（prompt 明确：只使用 chat agent 任务）；② **上下文可回答的问题**——"总结一下""你说的 XX 是什么意思""继续""然后呢"，这些不需要检索文档，直接根据对话历史/长期记忆回答。这是省 token 的关键分支：**不总是跑 DAG**。

### Q73. 所有 Agent 都依赖 LLM 吗？
**答案：** 不是。retrieval 用 LLM 生成关键词（temperature=0 的搜索词）；analysis 用 LLM 选列 + 工具计算（结果来自工具非 LLM）；**critic 的 RuleValidator 层完全不依赖 LLM**（纯正则/数值比较，<100ms）；code 用 LLM 生成代码但计算结果来自子进程执行。**确定性计算尽量交给工具/代码，LLM 只做决策**。

### Q74. Agent 的执行摘要（summary）和 trace 有什么区别？
**答案：** summary 是每个 Agent 自报的一句话摘要，进 `steps`（前端展示 + 记忆）；trace 是 `AgentTrace`（agent/start_time/end_time/tools_called/input_summary/output_summary），进 context.traces 用于审计回放。**一个面向展示，一个面向追溯**，两者都从执行元数据生成。

### Q75. 工具调用的名称是怎么变成记忆里的可读描述的？
**答案：** `_update_memory` 从所有 capability 的 `tool_descriptions` 收集 `工具名 → 中文描述` 映射，`context.tools_called`（收集自执行时的 cap.tools）映射成描述后写入记忆。这样历史里显示"调用了求和工具"而不是"calculate_sum"。

### Q76. 一套 Capability 声明支撑了哪四条链路？
**答案：** ① **Planner prompt**（告诉 LLM 有哪些能力可用）；② **六层校验**（agent 存在性/输出可达性/port_bindings 类型）；③ **Runtime 分派**（按 name 找实例执行，按 inputs/outputs 注入数据）；④ **自动接线**（_auto_wire_port_bindings 按类型匹配补绑定）。**一个声明四端复用，这就是"数据驱动运行时"的载体。**

# 五、Critic 与质量保障（Q77-92）

### Q77. Critic 的两级审核分别是什么？
**答案：** **第一级 RuleValidator**（纯确定性、无 LLM、<100ms）：查空/过短答案 + 数值一致性（计算结果 95/95%/0.95 是否在回答中体现）。**第二级 LLM slim_evaluate**：按准确性/完整性/逻辑一致性三条标准语义审核。第一级不过直接拦截（省一次 LLM 调用），过了才进 LLM 精审。

### Q78. RuleValidator 具体查哪两件事？
**答案：** ① `len(answer.strip()) < 3` → "回答过短或为空"；② 对 analysis.calculations 里每个 result，调 `_value_present_in_answer` 检查计算结果是否在回答里体现（支持 95/95.0/95%/0.95 跨格式互转）。**它不判断语义、不判断覆盖，只做字符串/数值层面的确定性检查。**

### Q79. RuleValidator 拦截后会发生什么？
**答案：** 直接设置 critique（问题列表 JSON）+ `need_retry=True` + `retry_target="generator"`，**跳过 LLM 精审**，返回 context。这条路径快（<100ms）且省一次 LLM 调用——**确定性规则能判的，绝不让 LLM 判**（成本对冲思路）。

### Q80. LLM Critic 的评估标准是什么？
**答案：** prompt（slim_evaluate）里三条：**准确性**（回答是否与证据矛盾，不是逐 claim 验证据）、**完整性**（是否回答了用户的问题）、**逻辑一致性**（回答是否自洽）。输出 JSON：`{"score": 8, "problems": [], "need_retry": false, "retry_target": "all"}`。

### Q81. 为什么说"LLM 有覆盖标准但软"？（勘误后的准确表述）
**答案：** prompt 确实包含"完整性：是否回答了用户的问题"，每轮（含第二轮重试）都跑。但**软在三处**：① 主观判断——完整性只是三条标准之一，交给 LLM 一眼扫，无结构化核对；② 宽容倾向——prompt 两处软化（"不要因 evidence 缺细节判编造""evidence 只是摘要 generator 可能提取更多"），等于教它倾向放行；③ 非结构化——判定"没覆盖"也不定位到具体缺失点。**所以"完全不能判断覆盖"是过度表述，"判断但软"才是准确现状。**

### Q82. Critic 判定要改后，怎么决定重跑哪里？
**答案：** LLM 返回 `retry_target`：`"retrieval"`（检索阶段问题）、`"generator"`（表达问题）、`"all"`（全部重来）。RuleValidator 固定返回 `"generator"`。这个值经 `parse_actions` 变成 `ControlAction(retry, target_task_id=...)`，RetryHandler 按 agent 名匹配子图重跑。

### Q83. 第二轮 Critic 会复核第一轮的问题清单吗？
**答案：** **不会**（这是已知缺点，见缺点 5）。第二轮用同一 prompt 重新评估，不拿第一轮的 problems 逐条验证"是否已修复"。这意味着"重新评估"而非"收敛式修复"。解法方向是：第一轮输出结构化 requirement 清单，第二轮逐条核对。

### Q84. 为什么重试成本高？
**答案：** 重跑子图 = 重调 LLM（重跑 generator 1 次、重跑 retrieval 整个链路 2-3 次）。失败一次成本翻倍。外层只有 `max_iterations=10` 防死循环，**没有"值不值得重试"的细粒度判断**——可能 10 轮都在同一个问题上打转烧 token。

### Q85. Critic 的 LLM 调用失败会怎样？
**答案：** catch 异常后构造 `CriticResult(score=0, need_retry=True, retry_target="all", problems=["Critic 调用失败: ..."])`——**宁可重跑全部也不要放过**。解析失败（LLM 输出非合法 JSON）同理返回 need_retry=True。**失败安全偏向重试**。

### Q86. 有没有 golden set 来量化 Critic 质量？
**答案：** **没有**（已知缺点 5）。Critic 的准确率/漏报率不可量化、不可回归。解法方向是沉淀 golden set 做离线评测（测覆盖判断的 recall/precision），让 Critic 质量可量化、可回归。这是面试要主动承认的边界。

### Q87. Critic 和六层校验在质量保障上的分工？
**答案：** **六层校验保"可执行性"**（DAG 结构/数据流/类型合法，前置一次性）；**Critic 保"内容质量"**（答案准确/完整/自洽，结果级）。一个管"跑不跑得起来"，一个管"答得好不好"。两者都不管"任务分解是否答对题"——那是 Planner 能力决定的天花板（缺点 2）。

### Q88. "结构校验 ≠ 语义校验"怎么理解？
**答案：** 六层校验保证的是"这个 DAG 能不能执行、执行时会不会崩、数据类型对不对"，**没有一层回答"这个 DAG 是不是用户问题的最优解"**。打个比方：六层校验是编译器（保证类型正确不崩溃），缺的是代码评审（判断程序是否真解决需求）。"任务分解正确性"本质是"问题语义→任务"的映射，只存在于 Planner 的 LLM 里，结构校验够不着。

### Q89. 举一个"六层校验全过但答案错误"的真实场景。
**答案：** 场景 A："对比三份实验报告差异" → LLM 规划 `retrieval → generator`（漏 extractor）。六层校验全通过（类型匹配/数据流合法/goal 可达），但没有规则说"对比类必须用 extractor"，结果 generator 没有结构化知识可引用，产出不引用证据的泛泛回答。**结构对，语义错。**

### Q90. 为什么 critic 重试解决不了"任务分解错"？
**答案：** Critic 审的是"答案 vs 证据"的一致性，它的重试范围是 `retrieval/generator/all`——都发生在**同一张 DAG 里**。如果 DAG 本身漏了 extractor/analysis（分解错了），重跑 generator 也只是用同一套不完整的输入再答一次。**Critic 能修"执行质量"，修不了"规划质量"**。解法是执行中 Replanning + 结果级自动评估。

### Q91. `_post_process_plan` 和 Critic 的边界在哪？
**答案：** `_post_process_plan` 是**规划后置**（LLM 生图后的代码层兜底修正，看问题文本关键词）；Critic 是**结果后置**（看生成答案的质量）。前者管"图里有没有 analysis/critic"，后者管"答案好不好"。但两者都**没检查"分解对不对"**——一个管形式兜底，一个管内容兜底，语义正确性仍是空白。

### Q92. 如果要你把 Critic 升级成"硬核覆盖闭环"，怎么做？
**答案：** 三步：① **结构化覆盖检查**——把用户问题拆成明确的 requirement 列表，逐条核对答案是否覆盖，输出缺失项清单（把"没覆盖"从模糊判断变成可定位硬证据）；② **第二轮验证闭环**——拿第一轮问题清单逐条验证是否修复，未修复继续 retry（从"重新评估"变"收敛式修复"）；③ **golden set 离线评测**——量化 Critic 的 recall/precision 可回归。这三步正是 README「后续优化」的方向。

# 六、RAG 检索与计算引擎（Q93-108）

### Q93. `search_documents` 的搜索流程是什么？
**答案：** 五步：① embedding 相似度搜索（k=60 候选）；② **阈值过滤**（余弦距离 < 0.92 才算相关）；③ **关键词搜索补充**（embedding 召回不足时用 jieba 关键词精确匹配补）；④ 合并 + **多样性选取**（轮询各文档保证覆盖）；⑤ 文件名回退（文件名 bigram/单字重叠匹配兜底）。返回带 available_actions 的 JSON，指引下一步能做什么。

### Q94. 0.92 阈值怎么理解？低了高了各有什么影响？
**答案：** 0.92 是余弦距离阈值——小于它才认为 chunk 相关。**阈值定太高**（如 0.95）召回少，相关内容漏掉；**定太低**（如 0.80）召回多但噪音大。0.92 是实测调出来的平衡点。它是"冷启动阶段挡无关内容的闸门"。

### Q95. 为什么还要关键词搜索补充 embedding？
**答案：** embedding 对语义相似强、对精确匹配弱（专有名词、数值、表格列名经常 embed 不到一起）。关键词精确匹配（评分 = 匹配数/总关键词数）能补上 embedding 漏掉的精确项。**语义召回 + 精确补充，双通道合并**是召回质量的关键。

### Q96. 多样性选取（轮询各文档）解决什么问题？
**答案：** 纯相似度取 top-k 容易**一篇文章占满结果**（同一文档多个高分 chunk）。轮询各文档保证每个文档都有代表 chunk 进入结果，防止"只回答了一个文档而漏了其他文档"。**这是对比类问题（多个文档）的保命设计**。

### Q97. 文件名回退是什么时候触发？
**答案：** 当用户问题里带了具体文件名（"看看万代的账单"）但 embedding 没召回时，用文件名 bigram 匹配 / 单字重叠降级，找到匹配文档后**取该文档全部 chunk**。这是检索的最后一层兜底，专治"问题没语义但指名道姓要某文档"的场景。

### Q98. AnalysisContext/SearchContext 是什么？
**答案：** 工具间共享的状态容器（chunks/filtered/all_chunks/sources/search_count/agg_count/document_ids）。`_ctx_chunks` 等方法做上下文兼容（从 SearchContext 或 AnalysisContext 统一取字段）。**注意：这是 MCP 进程内的工具状态，和 Python 主进程的 AgentContext 是两套**——MCP server 独立进程持有 RAG 引擎和工具状态。

### Q99. calculate_sum 是怎么"找到对的那一列"的？
**答案：** prompt 强制 analysis agent **先调 read_all_rows 看列名，再选列计算**，不许猜列名。工具侧 `_sum_by_key` 还支持找不到 key 时自动回退到数值最多的列、支持行号过滤（"前10行"→ le,10）和内容过滤（"品牌=万代"）。结果带公式和明细，不是裸数字。

### Q100. calculate_rank 和 calculate_sum 有什么共性设计？
**答案：** 都：先 read_all_rows 确认列名、找不到 key 自动回退到数值最多的列、支持 row_filter/content_filter 精确定位、返回格式化结果（公式 + 数据）。**它们共享 `_execute_sum/_execute_rank` 的 key 定位与过滤逻辑**，把"对 Excel 式表格的精确数值计算"做成确定性工具而非 LLM 估算。

### Q101. 为什么说"求和/排名必须用工具，不能用 LLM 算"？
**答案：** LLM 是概率模型，算大数求和/排名会算错（幻觉数值）。工具 `_sum_by_key` 用 Python 精确计算 + 公式展示。所以 prompt 明确"必须通过工具获取计算结果，不要自行编造数值"、且"数值计算问题必须使用 analysis agent"。**确定性计算归工具，LLM 只做选列决策**。

### Q102. `_determine_top_k` 和动态 top_k 是什么？
**答案：** 不固定 k，而是根据分数间隔动态决定：分数断崖明显就少取，分数平缓就多取，保证进入结果的 chunk 都是"确实相关的"。配合 `_select_by_diversity` 轮询，**召回数量由数据质量驱动而非写死**。

### Q103. ChromaDB 里存的是什么？怎么切片的？
**答案：** 存文档的向量 chunk。DocumentProcessor 用 `RecursiveCharacterTextSplitter`（chunk_size=1000, overlap=200）切片，Excel 行按"行号: N\n列名: 值"逐行成 Document（跳过空行和汇总行），统一加 `[文件: name]` 前缀。支持 .pdf/.docx/.doc(COM)/.txt/.md/.xlsx。

### Q104. 文档是怎么入库的？流程完整链路？
**答案：** 上传 → MinIO 存文件 → Java 发 RabbitMQ 消息（documentId/filePath/fileName）→ **独立 stream_consumer 容器**消费：MinIO 下载 → 调 Python `/ingest/document` 向量化（解析→切片→删旧向量→add_texts）→ 更新状态 → ack。**异步解耦，上传不等向量化**。

### Q105. 向量删了之后有空间问题吗？
**答案：** 有。`delete_by_document_id` 删除后 Chroma 产生 tombstone，累计删除 50 次触发 `compact()`（get all → reset → re-add）释放空间。这是对 Chroma 无自动压缩机制的补偿。

### Q106. RAG 引擎在项目里的地位和 Agent 的关系？
**答案：** RAG 引擎（vector_store + rag_engine）被包在 **MCP server 进程**里，通过 `search_documents` 等工具暴露给 Agent。Python 主进程的 Agent 不直接调向量库——**一切检索/计算走 MCP 工具调用**，这是 Agent 与底层数据的隔离层，也让 CodeAgent 沙箱进程可以安全地只暴露白名单工具。

### Q107. 为什么 RAG 引擎要放进独立的 MCP 进程？
**答案：** 隔离（工具崩溃不影响主进程）+ 生命周期（独立启停）+ 安全（检索/计算/文件访问隔离在工具侧）+ 扩展（将来可用任何语言实现工具）。**这和 CodeAgent 沙箱是同一个"进程隔离"思路**——不信任的代码/能力放进独立边界。

### Q108. 一次 analysis 任务最多能调几次工具？
**答案：** 8 次（`agg_count > 8` 限制）。read_all_rows 先看列 + calculate_sum/rank 若干次，都在 8 次内。检索侧 search_documents 最多 2 次。**工具的调用上限是防 LLM 空转烧 token 的硬闸**，也是"无背压/无并发上限"缺点的对侧——工具层有上限，进程层没有。

# 七、记忆系统（Q109-122）

### Q109. 记忆系统存什么？分几层？
**答案：** 每个 session 一份 `SessionMemory`：**对话里程碑**（每 10 轮或累积 3+ 新事实时 LLM 重写的摘要）、**已知事实**（FACT_HARD_LIMIT=50 条，超 40 条触发压缩）、**用户偏好**（LLM 判断新增/修改/删除）、最近 N 轮 history。**进程内纯内存，重启后从 Java 重建**——Memory 不是持久层，Redis/MySQL 才是。

### Q110. Python 的 AgentMemory 和 Redis/MySQL 怎么分工？
**答案：** AgentMemory 是**运行时内存**（加速上下文拼装）；持久化在 Java 侧：Redis 存 memory 快照 + 历史缓存，MySQL 存 QaHistory 完整记录。**Java 是 source of truth**，Python 崩溃后重启通过 `rebuild_from_history` 从历史重建记忆，**幂等**（仅首次生效）。

### Q111. `rebuild_from_history` 怎么工作的？
**答案：** 幂等重建：仅当 session 不在内存时首次生效，逐轮 `_apply_turn` 重放历史（里程碑/事实/偏好逐轮重建），并用 Java 传来的 preferences **覆盖**本地偏好。**它是"无状态"承诺的核心实现**——记忆不在 Python 进程里"活着"，需要时能原样重建。

### Q112. 记忆是每轮都更新还是懒更新？
**答案：** 分层：`to_dict` 仅在 **dirty 时**返回序列化（非每轮全量）；`update` 在每轮问答后调用（含里程碑压缩 + 事实提取 + 裁剪）；**偏好检测是独立的**（`update_preferences` 后台线程跑，不与主流程串行）。**`_update_memory` 串行化在偏好检测之后执行，消除并发竞态。**

### Q113. 里程碑压缩的触发条件？
**答案：** `_compress_summary` 每 **10 轮**或累积 **3+ 条新事实**时用一次 LLM 调用重写里程碑（`_rewrite_summary_and_extract` 一次调用同时做：摘要 + 偏好提取/删除 + 事实提取）。**一次 LLM 调用干三件事，省 token**。

### Q114. 事实是怎么提取和裁剪的？
**答案：** `_extract_facts` 基于**关键词规则**提取（求和/排序/筛选/对比/趋势等模式，规则化而非 LLM 每轮提）；`_extract_doc_facts` 从 document_names/document_ids 提文档事实。裁剪：超过 40 条触发 `_compress_old_facts` LLM 压缩旧条目为摘要，硬上限 50 条，**保留最近 15 条**（FACT_KEEP_RECENT）。

### Q115. 记忆怎么被 Agent 使用？
**答案：** `format_context` 把记忆拼成文本块：**[对话里程碑] + [已知事实]（最近 20 条）+ [用户偏好]**。这个 memory_context 注入 Planner prompt，让 Planner 理解追问上下文（如"上次说的那个"）。**记忆是给 Planner/生成器"读"的文本上下文，不是给 Agent 共享的对象**。

### Q116. 每次问答，记忆从哪里来？
**答案：** `_restore_memory` 顺序：① 内存没有则从 Redis 读 memory 快照恢复；② 最近历史缓存 >= 5 条直接用，否则从 Redis 补；③ 无 memory 有 history → `rebuild_from_history` 幂等重建；④ `format_context` 生成 memory_context。**Redis 是内存的补给站**。

### Q117. 用户手动停止的 run 会写记忆吗？
**答案：** 不会。stop 先发 `RUNTIME_CANCELLED` 再 `task.cancel()`，取消后不 emit completed/error，**半成品不持久化、不更新记忆**。这是"手动停止不持久化"缺点的直接体现——历史里看不到半成品，无法从停止点恢复。

### Q118. 记忆里 preference 变化怎么同步回数据库？
**答案：** callback 持久化时检查 `memory_data.preferences_dirty`，为 true 就把 preferences 写进 MySQL 的 qa_session 表（Java 侧 updatePreferences）。**偏好是跨重启存活的**，且下次 ask 时 Java 若发现 Redis 无记忆会把它随请求带给 Python 覆盖本地。

### Q119. 多轮追问（"然后呢""结果是多少"）怎么保证不跑偏？
**答案：** 两层：① memory_context 给 Planner 注入里程碑+事实+偏好；② **短追问补全**——问题 <10 字 + memory 有数值计算工具名 + 含"结果/继续/然后"等词时，自动把问题补全成完整链路描述（提示需要 retrieval→extractor→analysis→generator）。**防止 Planner 把短追问当独立问题规划成残缺 DAG**。

### Q120. AgentMemory 的空闲淘汰和 LRU 是什么？
**答案：** `_evict_if_needed`：① **idle_ttl=1800s**——会话 30 分钟未活跃就淘汰内存；② **max_sessions=1000**——内存超 1000 个 session 按 LRU 淘汰。**记忆是内存资源，必须有限**；淘汰后再次访问走 Redis 恢复/重建，无感知。

### Q121. 记忆写入 Redis 是谁干的？
**答案：** **Java 干的，Python 只读**。Python 的 redis_store.py 注释明确"只读封装，写入由 Java 负责"。流程：Python 执行完 → callback 把 memory_data 发给 Java → Java 写 Redis（QA_MEMORY_PREFIX + sessionId，带 TTL）。**单写者设计避免双端写 Redis 竞态**。

### Q122. 重启后 memory 怎么回来？会不会丢？
**答案：** 重启后内存空 → 下次该 session 问答时 `_restore_memory`：Redis 有快照就用快照，没有就发全量历史让 Python `rebuild_from_history` 重建。Redis 有 TTL、MySQL 是兜底完整记录。**只要 MySQL 没删，记忆理论上能重建**（这就是"崩溃从 Java 重建"的完整链路）。

# 八、安全与 MCP（Q123-136）

### Q123. CodeAgent 执行用户代码，怎么保证安全？
**答案：** 四道闸：① **独立子进程**执行（隔离崩溃）；② **模块白名单**——prompt 允许 json/math/datetime/collections/itertools/functools/operator/statistics/re/decimal/fractions/copy，**禁用 os/subprocess/socket/shutil**；③ **512MB 内存 + 60s 超时**硬限制；④ 运行环境还移除了 builtins 里的 compile/exec/eval。**执行的是用户文档里的真实代码，风险实打实，所以边界尽量收死。**

### Q124. 模块白名单有什么绕过风险？
**答案：** 有（缺点 7）。纯白名单挡得住"直接 import os"，挡不住 import 技巧（如通过 `__builtins__`、`__import__` 间接、或从白名单模块里 access 危险属性）。**所以"模块白名单本身有绕过风险"是已知边界**，真正彻底要 seccomp / 容器级隔离 / 网络与文件系统白名单。

### Q125. CodeAgent 画图怎么落地？图怎么传给前端？
**答案：** code 生成的 Python 里强制 matplotlib Agg + 中文字体（WenQuanYi Zen Hei）+ `plt.savefig('/app/generated/{uuid}.png')`，result 里带 `image_path`。Python 读文件转 base64 放 `CodeResult.image_data` → callback 把 base64 给 Java → Java 解码上传 MinIO（`charts/{uuid}.png`）→ 前端用返回的 URL 展示。**图存 MinIO，DB 只存 URL**。

### Q126. MCP server 是独立进程，它和主进程怎么通信？
**答案：** **stdio 通道**。主进程 `MCPClient`（stdio client → ClientSession → initialize）通过标准输入输出与 `MCPServer` 进程通信，`call_tool` 把工具名+参数发过去、收 result.content[0].text。MCPServer 持有 VectorStore + RAGEngine，注册 `search_documents`/`list_documents`/`calculate_sum`/`calculate_rank`/`read_all_rows` 五个工具。**进程间只走文本协议，内存完全隔离。**

### Q127. 为什么 MCP 要独立进程而不是在 Python 主进程里 import 函数？
**答案：** 三个原因：① **隔离**——工具崩溃/被杀不影响 Agent Runtime 主进程；② **生命周期**——工具可独立启动/重启，MCP server 崩了能重启而不用重启整个 AI 服务；③ **多语言**——工具将来可用 Java/Go 实现。安全边界：代码执行、数据库访问、文件访问都隔离在工具进程。

### Q128. 每个 run 都新建 MCP session？为什么？
**答案：** 是的。`run()` 里 `mcp_client.create_session()` 生成 uuid4 新 session，finally 里 `cleanup_session` 清理。**每 run 新建 + 用完即焚**是"无状态"的三条纪律之一——MCP session 是内存态，不跨 run 复用，所以不构成多实例的共享状态问题（缺点分析的代码证据：agent_orchestrator.py:55/122）。

### Q129. set_document_ids 是干嘛的？怎么隔离文档权限？
**答案：** `run()` 里有权限的 document_ids 时调 `set_document_ids` 把文档 ID 集合注入 MCP 进程（MCPState.document_ids）。后续搜索/计算工具只在这个 ID 集合内工作——**文档级权限在数据层隔离**，Java 侧 ask() 也只查 `selectByUserId(userId)` 把当前用户的文档传给 Python。双端收口。

### Q130. MCP 工具搜索次数和计算次数为什么设上限？
**答案：** 防止 LLM 在工具调用上空转烧 token：search 最多 2 次、agg 最多 8 次。LangChain Agent 循环里工具调用没有天然上限，**显式上限是"防 LLM 失控"的确定性闸门**。

### Q131. 敏感操作（文件系统/网络）为什么只能由固定工具做？
**答案：** Agent 的一切外部操作都收敛到 MCP 工具（检索、计算、读行）和 CodeAgent 的受限子进程。**用户/文档数据不直接暴露给 LLM 自由发挥**——LLM 只能"用工具"，不能"直接碰系统"。这是 Agent 框架的基本安全模型：能力即白名单。

### Q132. 如果 MCP server 挂了，主流程会怎样？
**答案：** 工具调用抛异常 → Agent run 抛异常 → task FAILED → 下游 SKIPPED → 走失败链路。不会崩主进程（stdio 通信失败只是调用异常）。**隔离的意义正在于此**：工具进程崩，主进程活着，能报错能重试。若 MCPClient 无法初始化，则应用启动失败（lifespan 里 connect）。

### Q133. CodeAgent 的结果如何被 generator 使用？
**答案：** code 产出 `code_result`（CodeResult：code/stdout/error/success/image_data），generator 通过 `port_bindings["code_result"]` 接收。qa.py 的 `_build_response` 里 `isinstance(code_result, CodeResult)` 拆出 image_urls/generated_code/stdout/error 放响应里。**代码执行结果 + 图表 + 原始输出一并回传**。

### Q134. 为什么 prompt 里要写死"画图必须 plt.savefig，不允许其他写操作"？
**答案：** 把文件写入**收敛到唯一允许的路径**（/app/generated/ 下的图表 PNG）。这是沙箱的**最小权限原则在 prompt 层的体现**——代码能写文件就只允许写图表目录。代码层 + 运行层（子进程/白名单）再兜底。**三层收紧同一件事**。

### Q135. 你觉得这套沙箱和 Docker 容器隔离比，差在哪？
**答案：** 差距在**内核级隔离**：没有 seccomp 限制系统调用、没有网络隔离、没有文件系统访问控制（只靠白名单+路径约定）。Docker 容器 + seccomp profile + 只读根文件系统 + 无网络 namespace 才是更可信边界。**当前是"进程级沙箱"够 demo、不够生产**——这是缺点 7 的完整表述。

### Q136. MCP 协议帮你避免了哪些安全问题？
**答案：** ① 工具调用参数是显式声明的（不把自由字符串当代码执行）；② 工具在独立进程，**LLM 无法 import 模块/访问文件系统绕过**；③ 工具白名单（五个工具）之外的行为 LLM 根本没有调用入口。**协议本身=能力边界**，比"给 LLM 一个 Python REPL"安全一个量级。

# 九、无状态架构与 Java 网关（Q137-152）

### Q137. "Python 无状态"具体指什么？
**答案：** 指 Python 进程**不持有跨请求存活的状态**：MCP session 每 run 新建用完即焚、AgentMemory 每 run 从 Java 重建、RuntimeEventBus 事件 run 结束即清理。**状态全部在外部存储（Redis/MySQL/MinIO/Java 内存），进程可以被杀/重启/复制而不丢数据。** 这正是"无状态 = 状态在外部存储，不在进程内存"的定义。

### Q138. 那 RuntimeEventBus 不是内存态吗？怎么算无状态？
**答案：** 它是**进程内瞬态**（per-run 事件流，run 结束就 cleanup），不承载跨 run 的业务状态。它属于"运行期瞬态"，不是"持久状态"。**无状态的边界是：业务状态必须可重建；事件流这种一次性瞬态不违反**。但它是多实例问题所在（见第 10 节）——事件消费者必须连到执行该 run 的实例。

### Q139. Java 网关在项目里具体做什么？
**答案：** 三块：① **鉴权**（LoginInterceptor + JWT，所有业务请求校验登录态，Python 不对外）；② **SSE 透传**（`/qa/runtime/{runId}` 用 SseEmitter 代理 Python 流，15s 心跳保活）；③ **持久化**（callback 收 Python 结果写 MySQL/Redis/MinIO + 会话/历史管理）。**前端只和 Java 打交道，Python 藏在后面**。

### Q140. Java 怎么鉴权 Python 的 callback？为什么需要？
**答案：** callback 带 `X-Callback-Token` 请求头，Java 比对配置里的 `ai-service.callback-token`，不匹配返回 403。**防止任何人伪装 Python 往数据库写假历史**。这是 Java 网关的安全边界之一——**认证入口统一在 Java，Python 服务不暴露给公网**。

### Q141. Java 的 SSE 透传具体怎么实现的？
**答案：** `proxySse`：new SseEmitter(300_000L)（5 分钟超时）→ 专用线程池 `sseExecutor.execute` 里用 Java HttpClient 连 Python `/qa/runtime/{runId}` → 逐行解析 `event:`/`data:` → `emitter.send` 转发给前端。**用专用有界线程池，避免阻塞公共 ForkJoinPool**。校验 Python 状态码，非 200 时发一条 runtime_error 而不是把错误体当 SSE 转发。

### Q142. 为什么 SSE 需要心跳？心跳发的是什么？
**答案：** 长 Planner 阶段（无事件可推）和 nginx 空闲超时都可能把连接掐断。Java 侧 `heartbeatScheduler` 每 15s 发一个 comment（`: ping`）保活；Python 侧 `stream_runtime` 的 queue 15s 无事件也发 `: ping\n\n`。**注释行不产生事件但维持 TCP/代理连接存活**（Java 代理不转发注释行）。

### Q143. SseEmitter 超时、错误、完成时怎么收尾？
**答案：** `onTimeout`/`onError`/`onCompletion` 三个回调都 `heartbeat.cancel(false)` 停心跳；转发循环里 emitter.send 失败就 break，finally 里也 cancel。**心跳任务不能泄漏**——连接断了继续发只会累积无用调度。

### Q144. Python 执行完成后，结果怎么到数据库？
**答案：** 不走 SSE，走 **Phase 2 callback**：`_run_and_emit` 在 `orchestrator.run` 成功后 `_callback_java` POST 完整 result（answer/sources/plan/agent_trace/memory_data/image_urls...）到 Java `/qa/callback`，Java 才写库。**SSE 只推实时状态，持久化单独走 callback**——两者生命周期不同（token 流瞬态、结果要留存）。

### Q145. callback 持久化的顺序和内容？
**答案：** ① memory_data → Redis（QA_MEMORY_PREFIX，TTL），preferences_dirty 则更新 MySQL；② 对话历史 → Redis List（rightPush + expire）；③ base64 图 → 解码上传 MinIO（charts/{uuid}.png）；④ QaHistory → MySQL（含 plan/agent_trace/generatedCode 的 JSON）；⑤ 会话历史缓存 → Redis（QA_SESSION_HISTORY_PREFIX）；⑥ 更新会话标题（前 50 字）。**Redis 当缓存、MinIO 存文件、MySQL 存真相**。

### Q146. callback 失败会怎样？
**答案：** `_callback_java` 返回 False → `_run_and_emit` 抛 `RuntimeError("callback 持久化失败")` → emit `RUNTIME_ERROR`。**持久化失败 = 整个 run 报错，不静默成功**。无 session_id 时（游客）视为成功不持久化。

**失败场景**：Java 服务挂了/网络不通（ConnectError）、超时（httpx 30s）、返回非 200 或业务码非 200。

**当前无重试**：单次 HTTP POST，失败就丢。dirty 标记只在成功时清除（`mark_synced`），但不会触发对上一轮的补写——下次请求只持久化当次结果。

**实际影响**：对话结果没写进 MySQL，用户刷新历史看不到这条问答；但 SSE 实时回答不受影响（答案已通过事件流推给前端）。

**解法方向**：指数退避重试（2-3 次，1s/2s/4s）覆盖 Java 短暂重启；失败后写入 Redis 死信队列，后台定时重试覆盖长时间故障。

### Q147. 前端历史页数据从哪来？命中怎么优化？
**答案：** Java `/qa/history`：**先查 Redis 会话历史缓存**（QA_SESSION_HISTORY_PREFIX List），命中直接返回；没命中查 MySQL，查完**回填 Redis**（带 TTL）。删除历史/会话时 `purgeSessionCache` 清三类 Redis key，避免缓存命中已删记录。**缓存先查 + 回填 + 失效，三级配套**。

### Q148. 会话（session）是怎么管理的？
**答案：** Java `/qa/session`（新建）、`/qa/sessions`（列表）、`/qa/session/{id}`（删除）都是 MySQL QaSession + CurrentUser 鉴权。session 存 userId/preferences/title，QaHistory 通过 sessionId 关联。Python 侧 session_id 只是字符串透传，**会话归属权在 Java**。

### Q149. 为什么 Python 不直接暴露公网？
**答案：** 安全收敛：Java 层统一 JWT 鉴权、文档权限（selectByUserId）、callback token 校验，Python 在 Docker 内网只被 Java 调用。**单一安全边界**——这也是简历里"鉴权收敛 Java 单一安全边界"的依据。Python 若直接暴露，每个端点都要自己鉴权，容易漏。

### Q150. Java ask() 转发前做了什么预处理？
**答案：** 查当前用户可访问文档（document_ids）→ 查 Redis 有无记忆快照：**无记忆时**把 MySQL 全量历史 + session preferences 一并发给 Python 重建记忆；有记忆只发 session_id 让 Python 从 Redis 读。**这个分支决定 Python 是"恢复"还是"重建"**。

### Q151. 双端（Java/Python）各自的心跳间隔为什么都是 15s？
**答案：** 15s 是经验值：大于 nginx 常见空闲超时但又不至于太频繁刷流量。Java 侧发给自己前端的客户端（SseEmitter），Python 侧发给自己代理方（Java 转发器）。**两端各自保活自己那一段链路**，都是 15s 窗口内无事件就补一个 ping。

### Q152. 这个架构里 Java 的"有状态"体现在哪？
**答案：** 登录会话、MySQL/Redis/MinIO 持久化、会话管理、SseEmitter 活动连接登记——全是跨请求存活的**业务状态**。它和 Python 形成镜像分工：**Java 管状态和安全，Python 管计算和智能**。这也正是"Python 无状态 + Java 有状态网关"分工的全部含义。

# 十、多实例 / 扩展性 / Redis 事件总线（Q153-168）

### Q153. 两个浏览器同时用 = 多实例吗？
**答案：** 不是。**浏览器是客户端，实例是服务端进程**。两个浏览器连同一个进程完全没问题。多实例 = 多个 Python 进程，负载均衡把请求分散——SSE 请求分到"没执行该 run"的实例就收不到事件。**单实例不暴露，多实例才暴露**。

### Q154. 多实例下 SSE 为什么坏？根因在哪？
**答案：** 根因是 `RuntimeEventBus` 是**进程内 pub-sub**（`run_id → 事件` 全在内存）。SSE 消费者必须连到"执行这个 run 的那个 Python 实例"。多实例后 Java 侧必须做 **sticky 路由**（run 固定打到某实例），否则分到别的实例就订阅不到。**粘滞没消失，只是从"状态粘滞"变成"连接路由粘滞"**。

### Q155. 两条解决方案是什么？
**答案：** ① **事件总线外置为 Redis**——事件搬出进程内存，任何 Java 实例订阅 Redis 都能拿到，观众不管分到哪个直播间都收到事件；② **Java 网关做 run 级 sticky 路由**——路由表在 Java 内存，run 固定打到执行实例。决策：Python 实例多→Redis；2-3 个+最小改动→sticky；延迟敏感→sticky。

### Q156. Redis 事件总线该用 pub/sub 还是 Streams？为什么？
**答案：** 用 **Streams 不用 pub/sub**。pub/sub 发完即焚，迟到订阅者丢历史；Streams 可 `XREAD` 从 0 读历史，**复刻进程内总线的"迟到订阅不丢事件"**（RuntimeEventBus 有 history 回放）。推荐 **Java 直接订阅 Redis**，否则又回到"Java 该连哪个 Python"的 circular 问题。

### Q157. Python 写 Redis 还叫"无状态"吗？
**答案：** 更无状态。无状态 = 状态在外部存储不在进程内存。事件从进程内存搬 Redis = **事件不跟进程共存亡** = 更无状态。Redis 是共享基础设施，所有 Java/Python 实例都能读写。**"写 Redis 变成有状态"是把存储介质误当状态本身**。

### Q158. Redis 里应该写什么？分几种流？
**答案：** 两种流必须分开：① **实时事件流** → `XADD run:{id}:events`（AGENT_STARTED/TOKEN_CHUNK 等），瞬态 TTL，Java XREAD → SseEmitter；② **完成状态** → **仍走 /qa/callback**（X-Callback-Token 鉴权），不进 Redis 事件流。混在一起 = 生命周期冲突（token 要删/结果要留）+ 鉴权边界消失 + Java 幂等负担。

### Q159. 是不是只有 SSE 受多实例影响？
**答案：** 是（代码证据）。MCP session 每 run uuid4 新建 + finally cleanup；AgentMemory 每 run 从 Java 重建（_restore_memory）。三条纪律：**每 run 新建 + 从 Java 重建 + 用完即焚**。边界：MCP session 若改 per-user 复用则也受影响；Java 层 SseEmitter 登记表同样有实例绑定。**判断标准：进程内存里的 run→连接/run→状态 对应表，多实例时都要外置。**

### Q160. sticky 和 Redis 各解哪一层？
**答案：** sticky 只解 Python 层（且自己挂在 Java 多实例上还要外置路由表）；Redis 把事件搬出进程内存，**两层同时解开**（Python 的 RuntimeEventBus + Java 的 SseEmitter 登记表）。所以"Redis 解两层，sticky 只解 Python 层"。

### Q161. 正在跑的 run 崩溃了能续命吗？
**答案：** 当前不能（已知边界）。要做 = **checkpoint**：每个节点/agent 完成时把执行状态（plan+completed+outputs+in_flight）序列化到 Redis，新实例读 checkpoint 重建 AgentContext 从断点续跑。粒度 = 每节点完成时，非每 token。**当前不做**：分钟级 run + 低崩溃率，收益不成比例；run 变长/变贵/要 SLA 才做。

### Q162. checkpoint 的难点在哪？
**答案：** ① **幂等**——已完成节点不能重跑（LLM 调用贵）；② **in-flight 节点**用"至少一次"重跑（可能重复调用，要接受）；③ **MCP session 也是内存态**要一并 checkpoint；④ **前端事件回放衔接**——续跑后事件流要能接上。三条纪律（每 run 新建）与 checkpoint 是冲突的，需要专门设计。

### Q163. 三层递进怎么讲？
**答案：** ① **SSE 串流** → Redis 事件总线解决；② **新 run 接管** → 无状态设计解决（从 Java 重建）；③ **正在跑的 run 续命** → 需要 checkpoint，当前不做。**"无状态边界在第二层、不含第三层"就是这个含义**。面试收口用这三层讲扩展性规划。

### Q164. 当前单实例为什么不加 Redis 事件总线？
**答案：** 收益不成比例。单实例下进程内总线简单高效（无网络开销、无 Redis 依赖、事件零延迟），Redis 事件总线只在"多实例分布"时才需要。**架构决策服从规模**——这正好回应"为什么有的层你没上微服务/事件总线"：不是不会，是规模不需要。

### Q165. 除了 SSE，还有哪些地方在多实例下要检查？
**答案：** 排查清单：RuntimeEventBus（run→事件）、_active_tasks（run→asyncio.Task，Python 内存）、Java SseEmitter 登记表、AgentMemory 进程内缓存（每 run 重建所以 OK）、MCP session（每 run 新建所以 OK）。**凡是"进程内存里的 run 级状态"都要审查**。

### Q166. 负载均衡把 SSE 请求分到别的实例，前端会怎样？
**答案：** 该实例的 EventBus 里没有这个 run_id → `subscribe` 返回 None → Python 立即回 `runtime_error`（"run not found"）→ Java 透传 → 前端收到错误。**不会永久挂起**（subscribe 对未知 run 返回 None 的设计就是为了不挂起），但体验是坏的。这就是必须 sticky 或 Redis 的原因。

### Q167. 假设上了 Redis 事件总线，Python 还需要 sticky 吗？
**答案：** 不需要 Python 层 sticky。事件发布到 Redis 后，**任意 Python 实例执行、任意 Java 实例转发**都能工作，run 不再绑定实例。但**checkpoint（run 续命）仍需**——执行状态不在 Redis 时崩溃就是从头再来。**Redis 解连接绑定，checkpoint 解执行续命，是两个问题**。

### Q168. 你会怎么给这个系统做扩容决策？
**答案：** 分级：单实例 → 完全不动（当前）；2-3 实例 → Java run 级 sticky（改动最小，路由表 Java 内存）；多实例 + 要 SLA → Redis Streams 事件总线（Java 直接订阅）；要崩溃续命 → checkpoint（收益 vs 成本权衡）。**扩容不是"无脑加 Redis"，是按规模选成本最低的方案**。

# 十一、LangGraph 对比与选型（Q169-182）

### Q169. 为什么不用 LangGraph？一句话概括。
**答案：** **图的来源不同 + 运行时职责不同 + Python 无状态架构**，抽象层不匹配：LangGraph 的图是开发者写死的静态代码，项目的图是 LLM 每轮动态生成的 DAG；LangGraph 的价值（cycles/time-travel/checkpointer）项目当前都不需要。**套两层框架没收益，还绕过自研校验。**

### Q170. LangGraph 的图和你的图本质区别？
**答案：** LangGraph 的图是 **Python 代码（静态拓扑）**，开发者手写节点/边；项目的图是 **LLM 输出的数据（动态拓扑）**，每轮生成、过六层校验 + 规则兜底。把动态图翻译成 LangGraph 静态定义 = 隔层翻译、绕过自研校验层。**一个"代码即图"，一个"数据即图"**。

### Q171. LangGraph 的核心价值为什么项目不需要？
**答案：** LangGraph 强在 cycles（图内循环）、time-travel（回溯重放）、human-in-the-loop、checkpointer（跨会话持久化）。项目：DAG 无环（拓扑排序一次扁平执行）、重试是 Controller 子图重执行（外层 max_iterations 循环，非图内环）、无 HITL、持久化在 Java 层。**它的强项恰好不是项目当前要解决的事**。

### Q172. 项目的重试（retry）算"图内环"吗？
**答案：** 不算。重试是 Controller 触发 `invalidate_subgraph` 把子图标记 RETRYING，外层 `for _ in range(max_iterations)` 循环重新调度——**是"控制流循环"不是"图结构上的环"**。图本身保持 DAG。LangGraph 的 cycles 是在图结构里画环，两者机制不同。

### Q173. LangGraph 的全局 State 和你的 AgentContext 差在哪？
**答案：** LangGraph 全局共享 State（所有节点读写同一个 dict）；项目是 **task 级隔离**：`AgentContext.outputs` 按 task_id 分桶（`key → {task_id: AgentOutput}`），并行分支靠 contextvar 隔离写冲突，按 merge_policy 合并。**共享内存态难以表达 task 级隔离上下文**，这是自研数据契约的动机之一。

### Q174. 为什么说"不用它 ≠ 它做不了"？
**答案：** 纠正误区：LangGraph **完全能做**多 Agent（Supervisor/Handoff/Swarm 是官方模式），它强在"静态图 + 动态路由"。不用它是**抽象层不匹配**（动态拓扑 + Python 无状态 + 自研数据契约），不是"它做不了"。**选型是"是否需要"，不是"能不能"**。

### Q175. 什么情况下你会改用 LangGraph？
**答案：** 标准 agent 工作流（ReAct/多 agent supervisor）、跨会话持久化（checkpointer）、图内循环的 Replanning、human-in-the-loop。README「后续优化」里的"动态 Replanning"若需图内环，LangGraph 是候选技术路线。**当前项目落在它弱项上，选型才合理**。

### Q176. 自研 vs LangGraph 的优劣势对比？
**答案：** LangGraph 优：生态、复杂控制流（循环/HITL/时间旅行）、交付快；缺：静态拓扑、共享 State 耦合、绑定 Python 进程态、加深黑盒依赖程度。自研优：动态 DAG、Capability 热插拔、确定性运行时兜底（六层校验+两级 Critic）、无状态跨语言、面试可深挖；缺：开发成本高、重复造轮子、无社区健壮性、缺 HITL/持久化/时间旅行、只覆盖 DAG 子集。

### Q177. 项目里为什么还保留 LangChain？
**答案：** LangChain（兄弟库）用于 **RAG/LLM 集成**（ChatOpenAI 客户端、LangChain Agent 包装 MCP 工具），编排层自研。**边界清晰：LangChain 管"和模型/工具打交道的胶水"，自研管"多 Agent 任务编排"**。不是排斥生态，是把生态用在合适层。

### Q178. 动态 DAG 相比 LangGraph 的静态图，代价是什么？
**答案：** 代价：每次执行都要重新校验（六层）、无法预编译优化、测试难（同问题两次 DAG 可能不同）、出问题难复现。**换来的是：任务结构随问题自适应，不用为每类问题写图**。这是"灵活 vs 可控"的经典权衡。

### Q179. 如果面试官问"你的 DAG 是 Planner 生成的，怎么保证不是乱来"？
**答案：** 三层保证：① **能力约束**——Planner prompt 注入可用 agent 清单 + 强规则（数值必 analysis、所有数据类必 extractor、非 chat 必 critic）；② **结构约束**——六层校验（agent 存在性/类型兼容/goal 可达/循环检测）拦非法图，失败 fallback；③ **内容兜底**——`_post_process_plan` 三条规则 + Critic 结果级审核。**LLM 的自由度被确定性层围住，这就是"信任但验证"。**

### Q180. 你会怎么给这个系统引入 LangGraph 而不重写？
**答案：** 把**执行器**保留（AgentCapability 声明不变），用 LangGraph 只替换**编排器**：把 Planner 产出的 DAG 翻译成 LangGraph 静态图（每轮生成后 translate），节点内部还是自研 Agent。**但这是"隔层翻译"得不偿失**——所以我更倾向：要继续用 LangGraph 就在新项目用，现有自研编排深挖即可。

### Q181. 面试官可能问你"为什么不直接用现成框架，非要自己写"？
**答案：** 理由三层：① **核心诉求不匹配**——动态 LLM 图 + 无状态跨语言，LangGraph 的静态图/进程态 checkpointer 不支持；② **可控性**——自研能深挖（面试内容来源），编排层透明可调；③ **学习价值**——框架黑盒拿不掉，自研才能讲清"规划/校验/执行"每一环。**重复造轮子的成本被"理解深度"抵消**。

### Q182. 你的架构跟 MetaGPT / AutoGen 这类多 Agent 框架比呢？
**答案：** 那些框架偏**角色扮演式多 Agent**（一个 Agent 扮演 PM/工程师对话协作）。项目偏 **Plan-and-Execute 流水线式**（Planner 拆 DAG，确定性运行时并行执行，Critic 把关）。区别：项目**不依赖 Agent 间自由对话**（不可控、费 token），而是**显式数据流 + 契约**——更确定、更省、更可测。**对话协作 vs 流水线执行**，是两种多 Agent 流派。

# 十二、架构缺点与演进方向（Q183-200）

### Q183. 你的项目有哪些缺点？（面试总起手式）
**答案：** 我会讲 3 个最有代表性的：① **无状态 Python vs 进程内事件总线**——多实例下 SSE 需要 Redis 外置或 sticky 路由；② **六层校验是结构校验不是语义校验**——保证可执行但不保证"分解得对"，是 Planner 能力决定的系统上限；③ **Critic 无量化评估**——没有 golden set，质量不可回归。**每个都跟解法，说明知道边界在哪。**

### Q184. 为什么"结构校验 ≠ 语义校验"是最深的一条？
**答案：** 因为它触及系统**上限**而非 bug：唯一把"用户问题"翻译成"任务"的是 Planner LLM，六层校验只保证"翻译出来的 DAG 能跑"，手写规则只补"已知场景的缺失"。**Planner 能力 = 任务分解的天花板，校验永远追不上 LLM 的错误空间**。这是所有 LLM 规划系统的共同宿命（OpenAI 也靠 heuristic 兜底），关键是你意识到边界在哪。

### Q185. 你准备怎么解决"结构校验 ≠ 语义校验"？
**答案：** 两条：① **执行中 Replanning**——把校验从"前置一次性"变"执行中反应式"，用中间产物验证规划（retrieval 没返回预期数据？当场调整子图），把"语义对错"从"猜"变"用真实数据验证"；② **结果级自动评估**——Critic 升级为答案对照问题的语义充分性评估 + golden set 离线评测。**这正是 README「后续优化」里的"动态 Replanning"，缺点后面跟解法且是既有规划，逻辑自洽。**

### Q186. 为什么 `_post_process_plan` 的三条规则是"打补丁"不是"设计"？
**答案：** 因为它们是**事后从真实失败里总结**的（"检测到数值问题但无 analysis，自动修正"），触发靠问题文本关键词而非"检查 LLM 生成的 DAG 哪里错了"——**根本不在检查规划质量**。规则 3 强制所有非 chat DAG 补 critic，纯形式检查。且规则要自己修规则防误判（裸"第"的注释）。**补丁完备性由开发者枚举能力决定，永远追不上 LLM 的错误空间**。

### Q187. "无状态 Python vs 进程内事件总线"为什么单实例下看不到？
**答案：** 单实例下所有 run 都在同一个 EventBus，SSE 消费者连的必然是执行实例，天然正确。**多实例 + 负载均衡才会把 SSE 请求分到非执行实例**。所以它不是 bug，是"规模没到不暴露"的架构取舍——**这正是面试要讲的：你知道它会在什么条件下暴露，以及解法**。

### Q188. 无队列/无背压/无并发上限这条怎么自我辩护？
**答案：** 承认 + 定性：请求直连 asyncio，多用户同时跑时进程资源和 token 消耗无保护；长 run（45-74s）全程占双端长连接。**但这是单机/小规模取舍**——没上 Celery/队列是因为当前并发量不需要。解法方向：任务队列 + 并发上限（信号量/限流）+ 全局退避重试。**是"规模没到"不是"没想到"**。

### Q189. SSE 单流单点 + 手动停止不持久化，这条怎么讲？
**答案：** 单流链条上 Java/Python/Nginx 任一处断开流就断，双端心跳只能"检测断开"不能"恢复"；手动停止的 run 不持久化（半成品历史看不到、无法恢复）。解法方向：**断点续传/持久化部分状态 + 心跳升级为自动重连**。这是"实时性和可靠性"的经典权衡，当前优先实时性。

### Q190. 防御性代码未被测试覆盖（并行检索隔离）有什么风险？
**答案：** `ctx_source_id`/`search_contexts` 标注"防御性保留：当前 planner 单检索 DAG 下实际不触发"——这套复杂并发隔离逻辑**从未被真实场景跑通**。一旦将来出现多检索分支，风险裸奔，而这恰是最难测的并发逻辑。解法：构造多检索分支的测试用例/集成测试覆盖。**"没测过的防御性代码 = 未来埋雷"是诚实的评估**。

### Q191. CodeAgent 沙箱缺层级，风险有多大？
**答案：** 已有：子进程 + 模块白名单 + 512MB/60s。缺：网络隔离、文件系统访问控制、seccomp/容器级隔离。模块白名单本身有绕过风险（import 技巧）。执行的是用户真实文档里的代码，风险实打实。解法：网络/文件系统白名单 + seccomp / 直接容器化。**当前够 demo、不够生产，是已知且可修的边界**。

### Q192. 动态 DAG 让测试和可观测性变难，怎么应对？
**答案：** 三难：同问题两次执行可能不同 DAG → 单测无法穷举；依赖真实 LLM API → CI 成本高不稳定；日志分散（Python/Java/前端）无统一 tracing。解法：**LLM 输出打桩/录制回放** + **OpenTelemetry 统一链路**。这是所有 LLM 应用测试的共同难题，不是项目特有。

### Q193. 领域覆盖窄只支持 DAG 子集，会造成什么？
**答案：** 无循环、无条件分支、无图内重规划——需要"迭代反思"的任务（写代码→debug→改，多轮修改文档）不支持。且 7 个领域 Agent 之外的用户意图，Planner 可能**强行拆出错误 DAG**，而校验拦不住语义错误。解法：动态 Replanning + 按需扩展领域 Agent。**是当前覆盖范围内的取舍，边界清晰**。

### Q194. 成本线性叠加这条，你怎么看？
**答案：** 每轮固定成本：Planner 1 次 + 每 Agent 至少 1 次 + Critic 1-2 次；45-74s 延迟绝大部分是 LLM 时间；换更贵模型成本线性上涨，重试再翻倍。解法：**token budget 复用 / 便宜模型兜底 / 结果缓存**。诚实点：这是 LLM 应用的本质成本，优化空间在"少调"和"调便宜"。

### Q195. 面试官如果追问"哪个缺点你最想先修"？
**答案：** **启发式兜底 + 防御性代码没测过**——因为这两个是"真正需要改进"的（其余大半是规模取舍）。防御性并发隔离没测过是埋在未来的雷，优先级最高：构造多检索分支测试用例。其次是 Critic 量化评估（golden set），因为它让整个质量体系可回归。

### Q196. "背不出缺点的项目 = 没深度的项目"怎么理解？
**答案：** 面试官怕的不是项目有缺点，是**项目没什么好问的**。能讲清 10 条缺点 + 每条解法，证明你是"想过怎么做的人"而不是"跑通 demo 的人"。对比对象是同届候选人（CRUD 管理系统），21 岁 solo 写完 Python 后端 + Java 网关 + 前端 + Docker 编排，复杂度已超 90% 校招项目。**心态锚点：讲缺点展示的是深度。**

### Q197. 如果现在让你重写，你最想改架构的哪一处？
**答案：** 我会把**事件总线外置 + 执行中 Replanning** 作为 v2 骨架：事件总线用 Redis Streams（Java 直接订阅，多实例就绪），执行层加"每节点完成后检查中间产物质量、不合格就地调整子图"（把语义校验从前置猜变成执行中验）。**这两条把当前最深的两条缺点（事件总线实例绑定 + 结构校验≠语义校验）从根上解决**。

### Q198. 项目里你觉得最骄傲/最复杂的部分？
**答案：** 两条：① **声明式 Capability + 动态 DAG 运行时**——加 Agent 只注册不改编排，六层校验 + 自动接线让"LLM 生成的图"可靠执行；② **无状态跨语言架构**——Python 崩了从 Java 重建，SSE 实时透传 + callback 双通道分离（实时和持久化生命周期解耦）。**都是"让 LLM 的自由度被确定性兜住"的工程实践。**

### Q199. 如果面试官问"这个项目有什么商业价值/应用场景"？
**答案：** 它是**通用 Agent Runtime 骨架**：换掉 7 个领域 Agent（注册新 capability）就能适配新领域（客服/财务分析/文档审计）。RAG 只是默认能力之一。**Planner 动态规划 + 确定性执行 + 沙箱代码 + 无状态网关** = 一个可插拔的企业知识 Agent 底座。价值在"框架可复用"而非"单个问答功能"。

### Q200. 用一句话总结这个项目。
**答案：** **LLM 决定做什么，确定性运行时保证怎么执行**——Planner 动态生成任务 DAG，六层校验 + Capability 契约 + 两级 Critic 把 LLM 的自由度围在确定性边界内，Python 无状态执行、Java 网关管状态与安全、SSE 实时透传全流程，是一个 Planner-centric 的 Agent Runtime Framework。

| 最该先修 | 防御性并发隔离没测过 + Critic 无 golden set |

# 附录：AgentContext / port_bindings 数据契约深挖（A1-A7）

> 面试高频追问区：顺着"Agent 怎么通信"往下挖，面试官通常连问一串。这一组把数据契约从"是什么"挖到"为什么可靠"。

## A1. AgentContext 和 SearchContext 有什么区别？

**答案：** 名字像但**一个在 Python 主进程、一个在 MCP 子进程**，作用域完全不同。
- **AgentContext**（`app/core/agent_context.py`）：**一个 run（一次问答）一个**，跨整个 DAG。管 Agent 与 Agent 之间的数据交换（question/plan/evidence/analysis/answer + SSE 的 run_id/event_bus + traces）。隔离靠 `_lock` + 三个 contextvar（`_task_id_var`/`_search_ctx_source_var`/`_task_objective_var`）。
- **SearchContext**（`app/core/rag_engine.py:12`）：**一个 MCP session 内、单个 Agent 的工具调用循环**里用，管工具与工具之间的状态接力（last_search_chunks/filtered/all_chunks/sources、search_count、agg_count）。让 `calculate_sum/rank/read_all_rows` 复用上次 `search_documents` 搜到的数据。存在 MCP server 的 per-session 状态里（`session.search_ctx` 共享 + `session.search_contexts[task_id]` 隔离），主进程碰不到。
- 一句话：**AgentContext 是主进程里"跨 Agent 传数据"的容器，SearchContext 是 MCP 进程里"跨工具传检索状态"的容器**。当前代码只有 SearchContext（旧文档提到的 AnalysisContext 已合并掉）。

## A2. AgentContext 的字段是写死的吗？

**答案：** 分两层——**固定骨架 + 动态数据**，Agent 间传的数据完全不是写死的。
- **固定字段**只有系统骨架：question/session_id/document_ids/history/memory_context/preferences/plan + run_id/event_bus/traces/steps/merge_policies/current_task_id 等。
- **Agent 数据全在动态 dict**：`outputs: key → {task_id: AgentOutput}`。evidence/analysis/answer/code_result 全不是 dataclass 字段，都是运行时 `set_output("evidence", ...)` 写进去的，key 由各 Agent 的 **capability.outputs 声明**驱动。
- 佐证：当前代码已没有 `set_evidence()`/`set_answer()` 这种固定 setter（v3 旧文档里有，重构后统一成泛型 `set_output(key, value)`）。**加新 Agent 声明新 output key，AgentContext 一行不用改**。
- 边界（面试主动讲）：容器是动态的，但**读取方按约定 key 取**——`_build_response` 写死 `get_output("answer")`、goal_outputs 校验按 key 查。**动态容器 + 约定 key**：扩展零成本，契约靠声明不靠编译期检查。

## A3. 数据传输的键和值是怎么命名的？

**答案：** 一条口诀：**产出的名字上游说了算（capability.outputs），输入端口名下游说了算（capability.inputs），谁和谁连由 port_bindings 决定**。
- **写入 context 的名字** = 上游 Agent 的 capability.outputs key = port_bindings 值里 `.` 后面的部分。当前实际产出名：retrieval→`document_bundle`/`retrieval_report`；extractor→`knowledge_objects`/`evidence`/`sources`；analysis→`analysis`；code→`code_result`；generator→`answer`；critic→`critique`/`need_retry`/`retry_target`。风格是 snake_case 语义名。
- **读取传给下游的名字** = 下游 Agent 的 capability.inputs key = port_bindings 的键。例如 generator 输入端口：`structured_knowledge`/`evidence_list`/`source_meta`/`analysis_result`/`code_result`；critic：`generated_answer`/`evidence_list`/`retrieval_report`/`analysis_result`。
- **两个名字不必相同**：`{"structured_knowledge": "task2.knowledge_objects"}` 就是一条"上游产出名 → 下游端口名"的映射。同一个产出可以喂给不同端口名（extractor 的 `evidence` 同时喂给 generator 和 critic 的 `evidence_list`）。
- **值**是数据对象本体（DocumentBundle/list[KnowledgeObject]/AnalysisResult/CodeResult/str...），类型由 capability.outputs 声明，包一层 AgentOutput(value/producer/version/timestamp)。

## A4. 为什么"这样"就能实现绑定？

**答案：** 因为存储按 task_id 分桶 + port_bindings 是全限定引用，读取天然无歧义。
- 存储结构 `outputs: key → {task_id: AgentOutput}`，`set_output` 时 `task_id = _task_id_var.get()`（每个 task 跑前 set 成 task.id），**并行分支各写各桶不互相覆盖**。
- 读取 `get_output_entry("knowledge_objects", task_id="task2")` 精确命中，**不是"随便谁产的这个 key"**。
- 再加三层前置保证：① 拓扑排序保证上游先 COMPLETED、数据必然已写入；② 六层校验保证引用合法（上游存在/是祖先/output_key 声明过/类型兼容/required 齐全）；③ `_auto_wire` 补缺失绑定。**所以执行时绑定必然可解析。**

## A5. 有重复怎么办？

**答案：** 三种情况，两种是设计内、一种是真实隐患。
- **多个上游写同一 key**（最可能）：`outputs["evidence"] = {task1: [...], task2: [...]}` 共存不覆盖。走 port_bindings 读=精确拿指定 task 的，重复不影响绑定；未限定读（`get_output(key)`）按 **merge_policy** 合并——append 拼接 / dedup 按 `dedup_key_func` 去重 / replace 最后一个赢。`validate_capabilities` 对同层多写打 warning（"多 task 将自动合并"）。**精确读靠 task_id，聚合读靠 merge_policy，两种读取并存。**
- **多个下游读同一输出**：纯只读 fan-out，各拿各的副本，无冲突。
- **重复 task_id**（隐患，诚实说）：六层校验**没显式查 id 唯一性**——`validate_structure` 里 `ids` 是 set 会静默塌缩、`plan_task_map` 后写覆盖先写、`set_output` 归同一桶后写赢。实际触发概率低（planner 按 task1/2/... 编号），解法是 `validate_structure` 加一行 `len(set(ids)) != len(tasks)`。**面试主动点出这个 gap 是加分项。**

## A6. port_bindings 什么时候生效？是纯代码实现吗？

**答案：** 三个时刻生效，机制全纯代码；**内容（谁连谁）是 LLM 生成的，执行/校验/兜底全确定性代码**。
- **① 规划期·校验**：`validate_port_bindings` 六层查格式/上游/祖先/output_key/端口/类型/必选，不合法整图 fallback。
- **② 执行期入口·补全**：`_auto_wire_port_bindings` 按 capability 类型匹配补缺失绑定。
- **③ 每个 task 执行前·取数**：`_run_plan_task` 开头按绑定从 context 精确取上游输出注入 kwargs——**生效机制 = 上游写完了，下游从 context 按 task_id + output_key 把自己的输入拿走**，不直接调上游函数。
- 一句话：**LLM 只负责"声明意图"，Runtime 负责让这句话真的成立。LLM 的自由度止步于声明，执行权全在代码**——这正是"LLM 决定做什么，Runtime 保证怎么执行"在数据层的体现。

## A7. Planner LLM 输出的 JSON 长什么样？

**答案：** 一个 TaskGraph JSON，prompt 强制"只返回 JSON"。结构（`_parse_task_graph` 定义）：
```json
{
  "goal": "对比两个实验的差异",
  "goal_outputs": ["answer"],
  "tasks": [
    {"id": "task1", "agent": "retrieval", "objective": "搜索所有相关实验文档", "depends_on": []},
    {"id": "task2", "agent": "extractor",
     "objective": "从所有实验文档中提取结构化信息", "depends_on": ["task1"],
     "port_bindings": {"knowledge_document": "task1.document_bundle"}},
    {"id": "task3", "agent": "generator",
     "objective": "对比实验差异并生成回答", "depends_on": ["task2"],
     "port_bindings": {"structured_knowledge": "task2.knowledge_objects",
                       "evidence_list": "task2.evidence", "source_meta": "task2.sources"}},
    {"id": "task4", "agent": "critic",
     "objective": "审核答案的准确性和完整性", "depends_on": ["task3"],
     "port_bindings": {"generated_answer": "task3.answer",
                       "evidence_list": "task2.evidence", "retrieval_report": "task1.retrieval_report"}}
  ]
}
```
- 字段：`goal`/`goal_outputs`/`tasks`；task 有 `id`/`agent`（必填，缺 agent 抛错）/`objective`/`depends_on`/`output_key`/`port_bindings`。
- 绑定值必须用真实 capability 的 output key（LLM 从 prompt 注入的能力清单学）；critic 的 control 字段不能由 Planner 写（校验层拦）。
- 解析容错：`extract_json` 自动剥 markdown 代码块；失败或缺 `tasks` → 抛 `PlannerError` → `_fallback_plan` 兜底。
- 之后：六层校验 → `_post_process_plan` 兜底 → `_auto_wire` 补绑定 → 拓扑调度执行。
