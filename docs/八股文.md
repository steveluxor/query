## 第一梯队：面试必问，结合你的项目讲

## 一、Python 基础（⭐⭐⭐ 必考）

### P1. 可变对象 vs 不可变对象？有什么影响？

**答案：** **不可变**：int、str、tuple、frozenset（改了变量名其实是创建新对象）；**可变**：list、dict、set（原地修改，所有引用都变）。影响：**默认参数**不能用可变对象（`def f(x=[])` 会共享同一 list）、dict/set 的 key 必须不可变（可变 key 哈希会变）。

### P2. 深拷贝 vs 浅拷贝？

**答案：** 浅拷贝 `copy.copy`：只复制外层，内层可变对象共享引用；深拷贝 `copy.deepcopy`：递归复制所有层。**陷阱：** 浅拷贝的内层 list 修改会互相影响。**JSON 序列化天然是深拷贝**（你项目里大量用 JSON 传数据就是安全的深拷贝）。

### P3. 生成器 vs 迭代器？为什么用生成器？

**答案：** 生成器（`yield` / 生成器表达式）是惰性求值的迭代器，**每次只产生一个值，不占内存**。用途：大文件逐行读、无限序列、管线处理（`(x for x in range(10**6))` 不一次建全 list）。**和项目：** 大数据 chunk 处理、流式输出思路一致——不一次全加载。

### P4. 装饰器是什么？怎么实现带参数的装饰器？

**答案：** 装饰器是**高阶函数**（接收函数返回函数），在不改原函数代码的情况下增强行为。带参数：三层嵌套（装饰器工厂 → 装饰器 → wrapper）。`@wraps` 保留原函数元信息。**用途：** 日志、计时、鉴权、缓存。

> **和项目：** base_agent.py 的 `execute` 就是给每个 Agent 包一层：计时 + 记录 AgentStep + 异常处理——典型装饰器思维。

### P5. GIL 是什么？影响哪些场景？

**答案：** GIL（Global Interpreter Lock）是 CPython 的全局解释器锁，**同一时刻只有一个线程在执行 Python 字节码**。影响：**CPU 密集型**任务多线程无法并行（只能串行跑，多核白搭）；**IO 密集型**任务不受影响（线程等 IO 时释放 GIL，其他线程可以跑）。

> **和项目：** FastAPI 是异步框架，遇到阻塞 IO（如 `httpx` 调用 LLM、`embedding` 推理）时用 `await` 挂起当前协程，事件循环去跑别的任务，这就是单线程实现高并发的原因。
> **解法：** CPU 密集用 `multiprocessing`（每个进程有独立 GIL）或调 C 扩展（numpy 等释放 GIL）；IO 密集用 asyncio 协程。

### P6. 协程 / 线程 / 进程的区别？各自适用场景？

**答案：**

| 维度 | 协程（asyncio） | 线程 | 进程 |
|---|---|---|---|
| 调度 | 用户态（事件循环，无上下文切换开销） | 内核态（有切换开销） | 内核态（切换开销最大） |
| 内存 | 共享（单线程内） | 共享（同进程） | 独立（进程间要 IPC） |
| 并发能力 | 万级 | 千级（受线程栈限制） | 百级 |
| 适用 | IO 密集型 | IO 密集型（同步库） | CPU 密集型 |
| 缺点 | 代码必须异步化，同步阻塞会卡死事件循环 | 有 GIL 限制 CPU 并行 | 创建/切换重，通信复杂 |

> **和项目：** Python 端全部用协程（FastAPI + async），但 MCP Server 里 `_execute_search` 是同步的，阻塞了事件循环（这是性能瓶颈，见 Q49）。解决用 `asyncio.to_thread` 丢线程池。

### P7. asyncio 事件循环原理？一个请求进来发生了什么？

**答案：** 事件循环是**单线程**，维护一个任务队列（ready queue）：
1. 请求到达，注册协程任务
2. 协程执行到 `await`（遇到 IO）→ 挂起，事件循环去执行下一个任务
3. IO 完成后，回调把任务放回 ready queue
4. 循环直到所有任务完成

**关键：await 是让出点（yield）**，不是阻塞。事件循环靠 `selectors`（epoll 等）监听多个 socket，谁有数据就唤醒谁。

> **和项目：** FastAPI 处理 SSE 长连接，一个连接就是一个协程，事件循环在等 SSE 数据时可以去跑别的请求，所以单进程能扛很多并发长连接。

### P8. `async def` 和 `def` 的区别？在 async 里调阻塞函数会怎样？

**答案：** `async def` 返回协程对象，内部可 `await`，由事件循环调度；`def` 是普通函数同步执行。**在 `async def` 里调用同步阻塞函数**（如 `requests.get`、`time.sleep`、CPU 密集计算）会**卡死整个事件循环**——所有并发请求都被冻结。要用 `await asyncio.to_thread(fn)` 或 `loop.run_in_executor` 丢线程池。

> **和项目：** MCP Server 的 `search_documents` 是 async tool 但内部同步调 `_execute_search`（含 Ollama embedding），阻塞事件循环。解法：`await asyncio.to_thread(...)`。

### P9. 线程池 / 进程池参数怎么定？

**答案：** 线程池 `ThreadPoolExecutor(max_workers=N)` 复用线程避免频繁创建销毁。N 的经验值：**IO 密集 = 2×CPU 核数 或更高**（取决于等什么 IO）；**CPU 密集 = CPU 核数**（多没用，GIL 锁死）。进程池 `ProcessPoolExecutor` 用于 CPU 密集。

> **和项目：** Java 端心跳线程池、Python 端 `asyncio.to_thread` 默认线程池都是这个思路。

### P10. Python 垃圾回收机制？

**答案：** 三层：① **引用计数**（对象引用数归零立即回收，主流）；② **标记-清除**（解决循环引用，标记不可达对象）；③ **分代回收**（对象分三代，频繁回收年轻代减少扫描量）。**弱引用** `weakref` 不增加计数（解决循环引用/缓存）。

### P11. `__new__` 和 `__init__` 的区别？什么时候用 `__new__`？

**答案：** `__new__` 是**静态方法**，负责**创建实例**（先执行，返回实例）；`__init__` 是**初始化方法**，负责**填充属性**（后执行）。用 `__new__`：实现单例、不可变类、元类编程。**单例：** `__new__` 里判断 `cls._instance is None`。

### P12. 列表去重几种方式？时间复杂度？

**答案：** ① `set(list)`：O(n)，无序，只能去重不可变类型；② 保持顺序：`list(dict.fromkeys(lst))`：O(n)；③ 列表推导 + `seen` set：O(n)；④ 双层循环：O(n²)，别用。**list 查找 O(n)，set/dict 查找 O(1)**——这是高频考点的核心。

## 二、Redis（⭐⭐⭐ 必考，你项目大量使用）

### P13. Redis 五种基本数据结构？各自适用场景？

**答案：**

| 结构 | 底层 | 适用场景 |
|---|---|---|
| **String** | SDS | 缓存、计数器、分布式锁、Session |
| **List** | 双向链表/压缩列表 | 消息队列（LPUSH+BRPOP）、时间线 |
| **Hash** | 哈希表/ziplist | **对象存储**（用户信息、购物车：field=商品id value=数量） |
| **Set** | 哈希表 | 去重、**点赞/关注**、共同好友（交集）、抽奖 |
| **ZSet** | 跳表+哈希表 | **排行榜**、延迟队列、限流（score=时间戳） |

> **和项目：** 📌 记忆/历史用 String（`qa:history:{session_id}` 存 JSON）；文档摘要缓存用 Hash 或 String。Redis 只读封装，写入由 Java 负责（`redis_store.py`）。

### P14. Redis 为什么快？单线程怎么还快？

**答案：**
1. **纯内存**操作（比磁盘快几个数量级）
2. **单线程**避免上下文切换 + 锁竞争
3. **IO 多路复用**（epoll）监听大量 socket
4. 高效数据结构（跳表、哈希表、SDS）
5. 客户端协议 RESP 简单

> **单线程怎么处理并发：** 命令排队依次执行，靠"命令天然原子"保证一致性，不需要锁。但**慢命令**（KEYS、大 key 操作、复杂 Lua）会阻塞其他命令——这是要避免的。

### P15. 缓存穿透 / 击穿 / 雪崩？怎么解决？

**答案：**

| 问题 | 描述 | 解决 |
|---|---|---|
| **穿透** | 查不存在的 key，每次都打到 DB | 布隆过滤器 + 缓存空值（短 TTL） |
| **击穿** | 热点 key 过期瞬间大量请求打 DB | **互斥锁**（Redisson 分布式锁，只有一个线程重建）+ 逻辑过期 |
| **雪崩** | 大量 key 同时过期 / Redis 宕机 | 过期时间加随机值 + 多级缓存 + 集群 |

> **和项目：** 文档摘要缓存（DocumentSummaryCache）就是"Redis 逻辑过期 + Java API 回源"，本质是防击穿的变体——缓存失效时回源重建。

### P16. 缓存一致性怎么保证？先更新 DB 还是先删缓存？

**答案：** 常用：**Cache Aside**（旁路缓存）——读：先查缓存，没有则查 DB 回填；写：先更新 DB，再删缓存（或更新缓存）。坑：
1. **先删缓存再写 DB**：并发下 DB 写前有人读回填旧数据，缓存变脏
2. **先写 DB 再删缓存**：偶发"更新和读"竞态导致缓存里是旧值，但窗口极小（读要刚好在写 DB 和删缓存之间）
3. 终极方案：**延时双删**（先删缓存 → 写 DB → 延时再删一次）或 **canal 订阅 binlog 异步删缓存**

> **和项目：** DocumentSummaryCache 用"Redis 逻辑过期 + Java API 回源"，Java 更新摘要后由回源逻辑保证一致，本质是规避了 Cache Aside 的竞态。

### P17. Redis 持久化：RDB 和 AOF 的区别？怎么选？

**答案：**

| 维度 | RDB（快照） | AOF（日志） |
|---|---|---|
| 方式 | 定期生成全量二进制快照 | 追加每一条写命令 |
| 恢复速度 | 快（直接加载快照） | 慢（重放所有命令） |
| 数据丢失 | 可能丢最近一次快照后的所有数据 | 最多丢 1 秒（appendfsync everysec） |
| 文件大小 | 紧凑 | 大（有 rewrite 压缩） |
| 适用 | 可容忍丢数据的缓存 | 不能丢数据的场景 |

> **和项目：** 现在 Redis 只存记忆/历史，丢了能从 MySQL 重建，用默认配置即可。如果向量库换到 Redis，必须开 AOF（向量没有 MySQL 副本，丢了要全量重新向量化）。**📌 AOF 本质是操作日志**：HSET 命令含向量二进制，重启时逐条重放重建内存状态，rewrite 压缩文件。

### P18. Redis 过期策略？内存满了怎么淘汰？

**答案：** 过期策略：**惰性删除**（访问时检查过期）+ **定期删除**（后台周期性扫一部分）。内存淘汰 8 种，常用：
- **allkeys-lru**：所有 key 按 LRU 淘汰（最常用，缓存场景）
- **volatile-lru**：只淘汰设置了 TTL 的
- **allkeys-random / volatile-random**：随机
- **noeviction**：满了直接报错（默认）

> **和项目：** AgentMemory 有空闲淘汰（idle_ttl=1800s）+ LRU 上限淘汰（max_sessions=1000），和 Redis 的淘汰思路一致——内存不够时按最近最少使用优先丢。

### P19. 分布式锁怎么实现？有哪些坑？

**答案：** 实现：`SET key value NX EX 30`（原子设置 + 过期）。释放时用 Lua 脚本校验"锁是自己的才删"（防误删别人的锁）。坑：
1. **业务没跑完锁就过期** → 看门狗续期（Redisson，每 1/3 TTL 续一次）
2. **锁值要用唯一标识**（UUID）防误删
3. **Redis 主从切换丢锁** → Redlock（多节点）或换 etcd/ZooKeeper

> **和项目：** 📌 如果给 Chroma `compact()` 加分布式锁，只锁三步，TTL 必须续期——数据量大时 compact 可能跑几十秒，锁提前释放等于没锁（见 Q51）。

### P20. Redis 事务 / Pipeline / Lua 的区别？

**答案：**
- **事务 MULTI/EXEC**：命令排队一次执行，但有命令失败不会回滚（继续执行剩余）
- **Pipeline**：一次性发送多条命令减少 RTT，**不保证原子**（只是批处理）
- **Lua 脚本**：**真正的原子**——单线程执行整个脚本，中间不插入其他命令。适合"读-判断-写"复合逻辑

> **和项目：** 购物车"读数量+判断+写回"用 Lua 保原子（这就是你原来 Q44 的原理）。释放锁用 Lua 校验（见 P19）。

### P21. Redis 主从 / 哨兵 / 集群？

**答案：**
- **主从复制**：主写从读，异步复制（可能丢数据）
- **哨兵（Sentinel）**：监控主节点，挂了自动把从提升为主（高可用，不用手切）
- **Cluster**：数据分片（16384 个槽），支持水平扩展，每个节点存部分数据；客户端直连任意节点路由

> **和项目：** 单实例 + AOF 就够当前规模。多实例部署或高可用时上哨兵/集群，这也是 Q35 排查清单里"Redis 独立服务天然安全"的原因。

## 三、MySQL（⭐⭐⭐ 必考，Java 端持久化）

### P22. 为什么用 B+ 树做索引？不用 B 树 / 红黑树？

**答案：**
- **B+ 树**：所有数据在叶子节点，非叶子只存 key（矮胖，IO 次数少）；叶子节点有链表（范围查询高效，`SELECT ... BETWEEN` 顺序扫）
- **B 树**：非叶子也存数据，树更高，范围查询要中序遍历（慢）
- **红黑树**：二叉树，深度太大（百万数据 log2N≈20 层），而 B+ 树 3-4 层就能覆盖百万数据

> **核心：B+ 树把磁盘 IO 次数压到最低**（3-4 次），每次读一个节点=一次 IO。

### P23. 事务 ACID 是什么？隔离级别有哪些？

**答案：**

| 特性 | 含义 |
|---|---|
| A 原子性 | 要么全成功要么全失败（undo log） |
| C 一致性 | 事务前后数据满足约束 |
| I 隔离性 | 并发事务互不干扰（锁 + MVCC） |
| D 持久性 | 提交后数据不丢（redo log） |

**四种隔离级别（从低到高）：**
1. **读未提交**（脏读）
2. **读已提交**（解决脏读，有不可重复读）— Oracle 默认
3. **可重复读**（解决不可重复读，MVCC）— **MySQL 默认**
4. **串行化**（全锁，最安全最慢）

> **MVCC（多版本并发控制）：** 每条记录有版本号，读事务看到的是"自己开始时的快照"，读写不互斥，实现可重复读。

### P24. 脏读 / 不可重复读 / 幻读？

**答案：**
- **脏读**：读到别的事务**未提交**的数据（读未提交才有）
- **不可重复读**：同一事务两次读同一行，值变了（读已提交才有）——另一个事务提交了更新
- **幻读**：同一事务两次查询，**行数变了**（另一个事务插入了新行，可重复读下依然可能，靠间隙锁解决）

### P25. 索引失效的场景？SQL 怎么优化？

**答案：** 索引失效：
1. **对索引列做函数/运算**（`WHERE YEAR(create_time)=2024`）
2. **左模糊**（`LIKE '%abc'`，最左匹配失效）
3. **隐式类型转换**（`WHERE phone = 138...` 字符串列传数字）
4. **OR 连接非索引列**
5. **`!=` / `NOT IN`**
6. **最左前缀原则破坏**（联合索引 `(a,b,c)`，只查 b 用不上）

**优化：** EXPLAIN 看 type/rows/key；避免 `SELECT *`；分页优化（延迟关联）；**大表加索引、小表不用**。

### P26. 覆盖索引？索引下推？联合索引最左前缀？

**答案：**
- **覆盖索引**：索引包含查询所需全部列，不用回表（避免二次 IO），`EXPLAIN` 里 `Using index`
- **索引下推（ICP）**：MySQL 5.6+，把 where 过滤条件下推到索引层（少回表）
- **最左前缀**：联合索引 `(a,b,c)` 能用到 `a`、`a,b`、`a,b,c`，但**跳过的列之后用不上**（`a,c` 只能用到 a）

### P27. 你项目里 SQL 用在哪？有没有优化经验？

**答案：** Java 端存会话、消息、文档元数据（MyBatis）。优化经验：
- 文档列表按 document_id 查，建唯一索引
- 消息按 session_id 查，建联合索引 `(session_id, id)`
- 分页用 limit + 索引覆盖

> 如果没实际优化过，诚实说：**"当前单用户数据量小，没遇到瓶颈；但我懂索引原理和 EXPLAIN 用法，真到量会按索引优化"**。

### P28. 数据库锁：行锁 / 表锁 / 间隙锁？

**答案：**
- **表锁**：锁整表（并发低，MyISAM 用）
- **行锁**：锁一行（InnoDB，并发高）
- **间隙锁（Gap Lock）**：锁一个范围（防止幻读），锁的是"区间"不是具体行
- **死锁**：两个事务互相持有对方需要的锁 → InnoDB 检测到自动回滚一个

### P29. redo log / undo log / binlog 的区别？

**答案：**
- **redo log**：InnoDB 的物理日志，记录"对数据页做了什么修改"（崩溃恢复用，保证 D）
- **undo log**：InnoDB 的逻辑日志，记录"修改前的值"（回滚 + MVCC 快照读用，保证 A/I）
- **binlog**：MySQL Server 层的逻辑日志，记录 SQL（主从复制、数据恢复用）

### P30. 大表分库分表？什么时候才需要？

**答案：** 单表数据量过亿 / 单库瓶颈时才考虑。**垂直拆分**（按业务拆表/字段）、**水平拆分**（按取模/范围分表）。代价：跨库 join 变难、分布式事务、全局主键（雪花算法）。**诚实点：单用户项目数据量小，这是"没到需要"不是"不会"。**

## 四、Docker / Linux（⭐⭐⭐ 必考，你项目 7 个容器）

### P31. 容器 vs 虚拟机？

**答案：**

| 维度 | 容器 | 虚拟机 |
|---|---|---|
| 隔离 | 进程级（共享宿主内核） | 硬件级（独立内核） |
| 启动 | 秒级 | 分钟级 |
| 资源 | 只占运行所需 | 固定分配 |
| 安全 | 弱（内核共享） | 强 |
| 适用 | 微服务、CI/CD、dev 环境 | 需要完整 OS、强隔离 |

> **和项目：** 9 个服务各一个容器（mysql/redis/rabbitmq/minio/ollama/python-ai/stream-consumer/java/nginx），靠 Compose 编排 + 内部网络 `rag-network` 通信。

### P32. Dockerfile 优化？镜像怎么变小？

**答案：**
1. **多阶段构建**：编译阶段和运行阶段分离（如 Go 编译后拷二进制进 slim 镜像）
2. **合并 RUN**：`RUN apt-get install ... && rm -rf ...` 减少层数
3. **基础镜像选 slim/alpine**
4. **.dockerignore** 排除无关文件
5. **利用层缓存**：依赖复制在前，代码复制在后（代码改时依赖层不重建）

### P33. Docker 网络模式？

**答案：**
- **bridge**（默认）：容器有自己的 IP，容器间通过名访问，宿主可映射端口
- **host**：容器直接共享宿主网络栈（无隔离，性能好）
- **none**：无网络
- **container**：共享另一个容器的网络

> **和项目：** 📌 全部走 bridge 网络 `rag-network`，容器间用服务名通信（`http://python-ai:8000`），端口映射只是暴露给宿主机调试用（见 Q53）。**端口映射和容器间通信是两回事**——容器间走 Docker DNS，不走宿主机端口。

### P34. 端口映射怎么回事？`"3307:3306"` 什么意思？

**答案：** `宿主机端口:容器内端口`。`3307:3306` = 宿主机 3307 → 容器 3306。外部访问 `localhost:3307` 到达容器内的 MySQL 3306。容器间通信不需要端口映射（直接服务名+容器内端口）。

> **关键认知：** 端口映射只是"宿主机 ↔ 容器"的通道。**容器 ↔ 容器**走 Docker 内部网络（DNS 解析服务名），和端口映射无关。

### P35. 数据卷 volume 和 bind mount 区别？

**答案：**
- **volume（命名卷）**：由 Docker 管理，存在 `/var/lib/docker/volumes/`，推荐（可备份、跨容器共享、不依赖宿主路径）
- **bind mount**：直接挂宿主目录，改动实时生效（适合开发热更新）

> **和项目：** `chroma-data:/app/chroma_db` 就是命名卷——向量库持久化，容器重建不丢。这也暴露了向量库本质是"文件资源"，多容器共享时就是单写者问题（见 Q51）。

### P36. Docker Compose 的 depends_on 和 healthcheck？

**答案：** `depends_on` 只保证**启动顺序**，不保证**服务就绪**（MySQL 进程起来了但还没准备好接受连接）。**healthcheck** 才是真正等就绪：定期执行命令（如 `mysqladmin ping`），`condition: service_healthy` 表示"等它健康了才启动"。你项目里 python-ai 等 ollama healthy、stream-consumer 等 python-ai healthy，都是这个机制。

### P37. Linux 常用命令？怎么排查问题？

**答案：** 排查三件套：`top`（CPU/内存）、`df -h`（磁盘）、`ps aux`（进程）。日志：`tail -f`、`grep`。网络：`netstat -tlnp`、`curl`。**和 Docker：** `docker logs -f <container>`、`docker exec -it <container> bash` 进容器排查。

## 五、LLM / Transformer（⭐⭐⭐ 必考，你的核心方向）

### P38. Transformer 结构讲一下？Attention 机制是什么？

**答案：** Transformer = Encoder + Decoder，核心是 **Self-Attention**：
1. 输入 token → Embedding + **位置编码**（模型没有顺序概念，要注入位置信息）
2. 每个 token 生成 **Q（查询）、K（键）、V（值）** 三个向量
3. **Attention 分数** = Q 和所有 K 的点积（表示"这个 token 该关注谁"）→ softmax 归一化 → 加权求和 V
4. 公式：`Attention(Q,K,V) = softmax(QKᵀ/√d) V`
5. **多头注意力**：多组 QKV 并行，捕获不同子空间的关系

> **直觉：** "注意力"就是模型自己决定"生成这个词时，该看句子里的哪些词"。Q 是我要什么，K 是别人有什么，V 是别人的内容。

### P39. token 是什么？为什么输入要分 token？

**答案：** token 是文本切分的最小单位，可能是词/子词/字符。**BPE（字节对编码）**：从字符开始，反复合并出现频率高的相邻对，直到词表大小达标。**作用：** 控制词表大小（全英文单词几百万，BPE 后几万）、OOV（未登录词）问题解决（没见过的新词能拆成见过的子词）。

> **和项目：** token 数量直接决定 LLM 成本——你的 token 预算、prompt 瘦身（Extractor 精简输出）都是为了省 token。

### P40. temperature / top_p 影响什么？

**答案：**
- **temperature**：采样时的随机性。越高越随机（发散），越低越确定（收敛）。0 时贪心取概率最高
- **top_p（核采样）**：只从累积概率超过 p 的 token 里采样，动态筛选候选集

> **和项目：** 你项目里分类/规划用 `temperature=0`（要确定性 JSON），生成回答用 `temperature=0.1`（要稳定质量），Critic 用更高 temperature（要多样性判断）。

### P41. 上下文窗口是什么？超出怎么办？

**答案：** 上下文窗口 = 模型一次能处理的 token 上限（输入+输出）。超出处理方式：
1. **截断**（丢最老的历史，最粗暴）
2. **摘要压缩**（把旧对话总结成几句）
3. **滑动窗口**（保留最近的 N 条）
4. RAG 检索（只注入相关的）

> **和项目：** 📌 你的 AgentMemory 就是"里程碑压缩 + 事实提取 + fact 裁剪"——本质是把无限历史压缩进有限上下文，这就是上下文窗口管理的一种实现。

### P42. Embedding 是什么？相似度怎么算？

**答案：** Embedding 把文本映射成向量（如 768 维 float 数组），**语义相近的文本向量距离近**。相似度计算：
- **余弦相似度**：`cos = A·B / (|A||B|)`，范围 [-1,1]，关注方向不关注长度
- **欧氏距离**：直接算距离，关注绝对位置
- 余弦距离 = 1 - 余弦相似度

> **和项目：** 你的 Chroma 用 `SCORE_THRESHOLD=0.92`（余弦距离），embedding 由 Ollama 的 `nomic-embed-text` 生成，检索时 query 也向量化，算距离排 Top-K。

### P43. HNSW / FAISS 是什么？为什么向量检索要用它们？

**答案：** 向量库暴力比对 O(N) 太慢，需要**近似最近邻（ANN）**索引：
- **FAISS**：Meta 的向量检索库，提供多种索引（IVF 倒排、HNSW、PQ 量化）
- **HNSW（分层可导航小世界）**：多层图结构，上层稀疏下层密集，检索从顶层往下跳（类似二分查找），复杂度 O(log N)
- **PQ（乘积量化）**：把向量切块压缩，省内存

> **和项目：** Chroma 底层就是 HNSW。文档量小时暴力扫也快，量大才需要 ANN——这也是"向量库天花板"讨论的一部分。

### P44. RAG 的完整流程？检索的痛点？

**答案：** 文档 → 切片 → embedding → 向量库 → 用户问题 embedding → 相似度检索 Top-K → 拼进 prompt → LLM 生成。**痛点：**
1. **切片质量**：切太碎丢语义，切太大塞入无关
2. **召回准确率**：语义相似 ≠ 相关（你的 `SCORE_THRESHOLD + 文件名回退 + 摘要过滤` 就是在解决召回）
3. **重排（rerank）**：Top-K 后用小模型重新排序提精度
4. **幻觉**：检索结果里没有答案，模型硬编

> **和项目：** 你的项目针对痛点做了多层优化：阈值过滤（防低质召回）、关键词补充（语义+字面双通道）、多样性选取（防重复）、文件名回退（防漏）、摘要相关性过滤（防无关泄漏）——这就是面试讲 RAG 深度的素材。

### P45. LLM 幻觉是什么？怎么缓解？

**答案：** 模型生成不基于事实的内容（编造、张冠李戴）。原因：训练目标是"下一个 token 最可能"不是"说真话"；知识有时效性；长尾知识没学到。**缓解：**
1. **RAG**：给模型提供真实依据（你有证据来源）
2. **限定范围**：prompt 里要求"只基于给定材料回答，不知道就说不知道"
3. **Critic 校验**：二次检查回答是否与证据一致（你的 RuleValidator 查数值一致性就是反幻觉）
4. 降低 temperature（减少随机编造）

### P46. 什么是微调？和 prompt engineering / RAG 的区别？

**答案：** 微调 = 在预训练模型上用小数据集继续训练（更新权重）。**区别：**
- **Prompt engineering**：不改权重，靠指令引导（快、便宜、改 prompt 即可）
- **RAG**：不改权重，靠外部知识（解决时效/私域知识）
- **微调**：改权重（让模型学特定风格/领域格式/工具调用）

**选择：** 先 prompt → 不够再 RAG → 还不行才微调（贵、需数据、需避免灾难性遗忘）。**你的项目全用 prompt + RAG，没微调——这是合理的轻量选择。**

### P47. LoRA 是什么？为什么省资源？

**答案：** LoRA（低秩适配）：冻结原模型权重，只训练**低秩矩阵分解**的小适配器（参数量减少 99%+），推理时合并权重。省显存、省时间、可插拔（多个 LoRA 共存）。**对比：** 全参微调成本高且容易遗忘；LoRA 效果好成本低，是主流。

### P48. 什么是 Function Calling / Tool Use？和 MCP 什么关系？

**答案：** Function Calling = LLM 输出结构化的函数调用意图（函数名+参数），而不是自由文本，由框架执行再喂回结果。**MCP（Model Context Protocol）** 是**标准化**工具调用协议——定义了"模型 ↔ 工具"的统一接口（工具定义、调用、结果返回），避免每个框架各写一套。**你的项目用 MCP 做工具协议，就是让 Agent 通过 MCP 调检索/计算工具，LLM 决定调哪个工具。**

### P49. 说下你项目里 LLM 是怎么被调用的？（链路）

**答案：** 前端提问 → Java → Python FastAPI → **Planner LLM**（拆 DAG）→ 各 Agent 执行（内部再调 LLM：检索判断、知识提取、生成回答）→ **Critic LLM**（审核）→ 结果返回。LLM 由 `llm_factory.py` 统一创建，DeepSeek API 调用，配置 temperature/max_tokens/timeout。Retry 机制：Critic 判不合格 → `retry_target` 精准重跑子图。

## 六、Spring Boot / Java（⭐⭐⭐ 必考，你的 Java 网关）

### P50. IoC / DI / AOP 是什么？

**答案：**
- **IoC（控制反转）**：对象创建权交给 Spring 容器，而不是 new。容器管理 Bean 生命周期
- **DI（依赖注入）**：容器把依赖自动注入（构造器/Setter/字段注入）
- **AOP（面向切面）**：把横切逻辑（日志、鉴权、事务）抽出来，在方法前后织入。核心：动态代理（JDK 动态代理 / CGLIB）

> **和项目：** Java 网关的鉴权拦截器、`@RestControllerAdvice` 全局异常、SSE 事件都用 Spring 生态。

### P51. Bean 的生命周期？

**答案：** 实例化 → 属性填充 → Aware 接口回调（BeanNameAware 等）→ **BeanPostProcessor**（前置）→ 初始化方法（@PostConstruct / InitializingBean）→ **BeanPostProcessor**（后置）→ 使用 → 销毁（@PreDestroy / DisposableBean）。

### P52. Spring Boot 自动装配原理？

**答案：** `@SpringBootApplication` = `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan`。自动装配靠 **SpringFactoriesLoader**：读 `META-INF/spring.factories`，加载所有 `AutoConfiguration` 类，再按条件注解（`@ConditionalOnClass` 等）按需生效。

### P53. 拦截器 / 过滤器 / AOP 的区别？

**答案：**
- **Filter（过滤器）**：Servlet 规范，Web 层最外层（编码、跨域、登录校验）
- **Interceptor（拦截器）**：Spring MVC 层，只拦 Controller（`preHandle`/`postHandle`），拿得到 Handler
- **AOP（切面）**：Spring 容器层，最内层，可以对任意方法织入（事务、日志、权限）

> **和项目：** Java 网关的鉴权放拦截器（拦所有 Controller），`X-Callback-Token` 校验放特定接口。

### P54. MyBatis `#{}` 和 `${}` 区别？SQL 注入怎么防？

**答案：** `#{}` **预编译占位符**（`?`，防注入，类型安全）；`${}` 是**字符串拼接**（有注入风险，不要用在外来输入）。**防注入：** 永远用 `#{}`，动态排序/表名等必须拼接时做白名单校验。

### P55. HashMap 原理？JDK8 有什么优化？

**答案：** 数组 + 链表（哈希冲突时链地址法）。JDK8 优化：链表长度 ≥8 且数组 ≥64 时**转红黑树**（O(n)→O(log n)）；头插改**尾插**（解决并发扩容成环）；扩容容量翻倍 + 高低位分离。**默认容量 16，负载因子 0.75，扩容阈值 12。** 线程不安全（并发用 ConcurrentHashMap，分段锁→CAS+同步）。

### P56. ArrayList vs LinkedList？

**答案：** ArrayList 底层数组，**随机访问 O(1)**，尾部增删 O(1)，中间增删 O(n)（移动元素），扩容拷贝；LinkedList 底层双向链表，**头尾增删 O(1)**，中间增删 O(n)（遍历定位），随机访问 O(n)。**实际开发 ArrayList 为主**（局部性友好、内存紧凑），LinkedList 用得少。

### P57. synchronized 和 ReentrantLock 的区别？

**答案：** synchronized 是关键字（JVM 层，monitor），自动释放锁；ReentrantLock 是 API（AQS），需手动 lock/unlock，支持**可中断、超时、公平锁、多条件 Condition**。性能上 JDK6 优化后两者接近。**死锁排查：** `jstack` 看线程栈。

### P58. JVM 内存结构？

**答案：** ① **堆**（对象实例，GC 主战场）；② **栈**（每个线程一个，存局部变量/方法调用）；③ **方法区/元空间**（类信息、常量）；④ **程序计数器**（字节码行号）；⑤ **本地方法栈**。**GC 主要管堆。**

### P59. 线程池参数？拒绝策略？

**答案：** 核心参数：**corePoolSize**（常驻线程）、**maxPoolSize**（最大）、**queueCapacity**（等待队列）、**keepAliveTime**（非核心线程空闲存活）、**ThreadFactory**、**RejectedExecutionHandler**。执行流程：核心线程 → 队列 → 满则新线程到 max → 满则拒绝。**拒绝策略：** AbortPolicy（抛异常，默认）/ CallerRunsPolicy（调用者线程执行）/ DiscardPolicy（丢弃）/ DiscardOldest（丢最旧）。**线程数经验：** CPU 密集 = CPU 核数；IO 密集 = 核数 × (1 + IO等待/CPU计算)。

## 七、HTTP / 网络（⭐⭐⭐ 必考，你项目核心链路）

### P60. HTTP/1.0 / 1.1 / 2.0 区别？

**答案：**
- **1.0**：无连接，每次请求新建连接
- **1.1**：**持久连接**（默认 keep-alive）+ 管线化（HTTP 层）+ Host 头（一个 IP 多域名）
- **2.0**：**多路复用**（一个 TCP 连接并发多个请求，解决队头阻塞）+ 二进制分帧 + 头部压缩（HPACK）+ 服务端推送

### P61. SSE 原理？和 WebSocket 的区别？

**答案：** SSE = HTTP 长连接 + 服务端单向推送。浏览器发普通 GET 请求，服务端不结束响应，持续 `text/event-stream` 格式推数据。WebSocket 是**全双工**（双向），需协议升级握手。

| 维度 | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务端→客户端） | 双向 |
| 协议 | 标准 HTTP（不需要升级） | 需 `Upgrade` 握手 |
| 代理穿透 | Nginx 天然支持 | 需专门配置 |
| 重连 | 浏览器自动重连 | 需自己实现 |
| 适用 | AI 流式输出、通知 | 聊天、游戏 |

> **和项目：** 📌 前端不需要向服务端推数据（只发一次问题），所以选 SSE 而不是 WebSocket——单向就够、走标准 HTTP、Nginx 直接支持（见 Q53）。

### P62. 长轮询 / SSE / WebSocket 三选一？

**答案：**
- **长轮询**：前端周期发请求，服务端挂起直到有数据。实现简单但浪费请求
- **SSE**：一个长连接推到底，服务端单向，浏览器自动重连
- **WebSocket**：双向实时，但要协议升级 + 代理配置

判断：**AI 回答生成（单向流式）→ SSE；聊天（双向）→ WebSocket；历史方案兼容 → 长轮询**。

### P63. HTTP 状态码？你项目里用过哪些？

**答案：** 常用：**200** 成功、**201** 创建、**301/302** 重定向、**400** 参数错误、**401** 未认证、**403** 无权限、**404** 不存在、**429** 限流、**500** 服务器错、**502/504** 网关错。**和项目：** LLM 并发超限报 429；你的异常处理把 BizException 映射 400，未捕获异常 500。

### P64. Cookie vs Session vs Token（JWT）？

**答案：**
- **Cookie**：浏览器存储的 key-value，自动随请求带（有过期、可被禁用）
- **Session**：服务端存储会话数据，返回 SessionId 存 Cookie（有状态，分布式要共享 Session）
- **JWT**：无状态 token，服务端不存 Session，每次签名校验（适合分布式，可跨域）

> **和项目：** Java 网关用 JWT 做鉴权（无状态，适合多实例），`X-Callback-Token` 是服务间调用的固定 token。

### P65. 跨域 CORS 是什么？怎么解决？

**答案：** 浏览器同源策略（协议+域名+端口任一不同就跨域），跨域请求被浏览器拦截。**解决：** 服务端返回 `Access-Control-Allow-Origin` 头（CORS）、JSONP（GET 老方案）、代理转发（Nginx/后端代发，**你项目走 Nginx 反向代理天然避免跨域**）。

### P66. TCP 三次握手 / 四次挥手？

**答案：** 三次握手（建连）：SYN → SYN+ACK → ACK（双方确认收发能力）。四次挥手（断连）：FIN → ACK → FIN → ACK（确保数据发完，半关闭状态）。**为什么三次不是两次：** 防止旧连接请求延迟到达导致误建连接（客户端连续两次 SYN，第一个被丢弃，第二个才是对的）。

### P67. TCP vs UDP？

**答案：** TCP 面向连接、可靠（确认/重传/排序/流控）、有状态、慢；UDP 无连接、不可靠、无状态、快。**适用：** TCP 用于网页/文件/消息（要可靠）；UDP 用于音视频/游戏/直播（可容忍丢包，要低延迟）。**你的 SSE 走 TCP**（要可靠有序），心跳走应用层 15s 保活。

### P68. HTTPS 怎么建立？和 HTTP 区别？

**答案：** 加密传输 = HTTP + TLS。握手过程：ClientHello（支持的加密套件）→ ServerHello + 证书 → 客户端验证证书（CA 信任链）→ 协商对称密钥（RSA/ECDHE 非对称加密传输密钥）→ 之后用对称密钥加密通信。区别：HTTPS 有**加密 + 完整性校验 + 身份认证**。

### P69. 输入 URL 到页面显示全过程？

**答案：** DNS 解析（浏览器缓存→系统→hosts→本地 DNS→根/权威）→ TCP 三次握手 → TLS 握手（HTTPS）→ 发 HTTP 请求 → 服务器处理返回 → 浏览器解析 HTML/CSS/JS → 构建 DOM/CSSOM → 渲染 → 关闭/keep-alive。

## 八、消息队列（⭐⭐ 你已用 RabbitMQ）

### P70. 消息队列解决什么问题？消息丢失/重复消费怎么办？

**答案：** 解决：**异步解耦**（上传文档后立即返回，后台慢慢处理）、**削峰填谷**（高并发先入队再消费）、**可靠通信**（消费者挂了消息还在）。

**消息丢失三环节：**
1. **生产者**：开启 confirm 模式（发送确认）
2. **MQ**：持久化（队列 + 消息 durable）
3. **消费者**：手动 ack（处理成功才确认，失败重投）

**重复消费：** 消费方做**幂等**（数据库唯一约束 / Redis 去重 / 业务表状态判断）。

> **和项目：** 你的 stream-consumer 就是 RabbitMQ 消费者，下载文件 → 向量化 → 更新状态 → ack。如果消费者崩溃消息会重投，向量化本身要幂等（add_documents 先删旧再写新，天然幂等）。

### P71. RabbitMQ 概念：Exchange / Queue / Binding / RoutingKey？

**答案：** 生产者 → **Exchange**（交换机）→ 按 **RoutingKey** 路由 → **Queue**（队列）→ 消费者。Exchange 类型：**direct**（精确匹配 RoutingKey）、**fanout**（广播给所有绑定的队列）、**topic**（通配符匹配）。你的 stream-consumer 声明 exchange + queue + binding，用的就是这套。

### P72. 顺序消息 / 延迟消息 / 死信队列？

**答案：**
- **顺序消息**：单队列单消费者 / 分区键路由到同一队列（Kafka 按 key hash 到同一 partition）
- **延迟消息**：TTL + 死信队列（消息过期进死信，再消费）/ RabbitMQ 延迟插件 / 定时任务扫
- **死信队列（DLX）**：消息被拒绝/过期/超限后转投死信队列，用于"消费失败隔离 + 重试"

## 九、设计模式（⭐）

### P73. 单例模式？为什么要用？

**答案：** 全局只有一个实例。**用途：** 数据库连接池、配置对象、线程池。**实现：** 饿汉（类加载即创建）/ 懒汉（首次用才创建，要加锁防并发创建）/ 双重检查锁 / 枚举（最优）。**你项目里的例子：** MinIO client 单例、RedisStore 客户端、VectorStore（MCP Server 进程内单例）。

### P74. 观察者模式？和发布订阅的区别？

**答案：** 观察者：主题直接持有观察者列表，状态变通知所有观察者（松耦合）。发布订阅：中间多一层**消息代理**（Broker），发布者和订阅者完全解耦（你项目的 RuntimeEventBus 就是发布订阅——run 产生事件，前端订阅，中间是事件总线）。

### P75. 策略模式？状态模式？区别？

**答案：** 策略：运行时替换算法（如不同的 embedding 策略、不同搜索策略）。状态：状态改变行为（如 DAG 任务 PENDING→RUNNING→COMPLETED 不同状态不同行为）。**区别：** 策略是"我主动选算法"，状态是"状态驱动行为变化"。

### P76. 工厂模式？为什么要用？

**答案：** 创建对象不直接 new，交给工厂（简单工厂/工厂方法/抽象工厂）。**好处：** 解耦创建与使用、扩展时不用改调用方（开闭原则）。**你项目里的例子：** `llm_factory.py`（创建不同 LLM）、Agent 按注册表工厂创建。

## 十、操作系统 / 计算机基础（⭐ 加分）

### P77. 进程和线程的区别？

**答案：** 进程是资源分配的基本单位（独立内存、独立地址空间），线程是 CPU 调度的基本单位（同进程内共享内存）。**切换开销：** 进程切换要换地址空间（TLB 失效），线程切换只换栈/寄存器。**通信：** 进程间用管道/信号/共享内存/消息队列（你项目里 MCP stdio 就是进程间通信），线程间用锁/信号量（同进程内共享变量）。

### P78. 死锁的四个必要条件？怎么避免？

**答案：** ①**互斥**（资源独占）②**占有且等待** ③**不可剥夺** ④**循环等待**。**避免：** 打破任一条件——加锁顺序一致（打破循环）、一次申请所有资源、加超时（可剥夺）。**检测：** 资源分配图有环。**排查：** `jstack` 看线程栈（Java）、`ps`/gdb（进程）。

### P79. 虚拟内存 / 分页是什么？

**答案：** 虚拟内存 = 进程看到连续虚拟地址空间，操作系统映射到物理内存，不常用的页换出到磁盘（swap）。**分页：** 虚拟地址 → 页表 → 物理页框；页表太大用**多级页表** + **TLB**（快表缓存）加速。**缺页中断：** 访问的页不在内存 → 触发加载。

### P80. 用户态 / 内核态？怎么切换？

**答案：** 用户态：受限执行用户程序（不能直接碰硬件/内核内存）；内核态：完整权限（内核代码、驱动）。**切换时机：** 系统调用（syscall）、中断、异常。**开销：** 每次切换要保存/恢复上下文（寄存器、栈），所以**频繁 syscall 有性能损耗**——这也是"避免每次请求都建新连接"（连接池/keep-alive）的原因之一。

## 十一、算法与数据结构（⭐ 必须能手撕）

### P81. 时间/空间复杂度怎么分析？常见复杂度排序？

**答案：** O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ)。**分析方法：** 只看最高阶项、忽略常数、循环嵌套相乘。**常见：** 二分 O(log n)、快排/归并 O(n log n)、双循环 O(n²)、递归若 T(n)=2T(n/2)+O(n) 则是 O(n log n)（主定理）。

### P82. 快排原理？最坏/最好复杂度？

**答案：** 选基准 → 分区（小于基准左、大于右）→ 递归。**平均/最好 O(n log n)，最坏 O(n²)**（基准选到最大/最小，退化有序数组）。**优化：** 随机选基准 / 三数取中 / 小数组插排。**空间 O(log n)**（递归栈）。

### P83. 二分查找？注意什么？

**答案：** 有序数组找目标，O(log n)。**坑：** 边界条件（`left < right` vs `<=`）、**mid 溢出**（`left + (right - left)/2` 而不是 `(left+right)/2`）、死循环（mid 更新必须收敛）、重复元素定位（找左边界/右边界）。

### P84. BFS / DFS 区别？什么时候用哪个？

**答案：** BFS 用队列，逐层扩散，**找最短路径**（无权图）；DFS 用栈/递归，一路到底回溯，**找所有路径 / 拓扑排序 / 连通性**。**复杂度 O(V+E)**。**和项目：** 你的 DAG 依赖检测（`get_descendants` BFS）、校验器拓扑排序——就是图算法在项目里的应用。

### P85. 哈希表原理？怎么解决冲突？

**答案：** 哈希函数把 key 映射到数组下标，O(1) 平均。**冲突解决：** ①**链地址法**（JDK8 HashMap，链表→红黑树）；②**开放寻址**（线性探测/二次探测，遇到占位往后找）；③**再哈希**。**扩容：** 负载因子超阈值翻倍重哈希。

### P86. 栈和队列？怎么互相实现？

**答案：** 栈 LIFO（括号匹配、函数调用、浏览器后退）；队列 FIFO（任务队列、消息队列）。**两个栈实现队列：** push 全进 stack1，pop 时把 stack1 全倒进 stack2，stack2 pop 就是队首（摊还 O(1)）。**两个队列实现栈**同理（一个存一个倒）。
